# AX-WMS 포팅 매뉴얼

## 1. 문서 목적

이 문서는 AX-WMS(`S14P31S209`)를 GitLab 소스 클론 이후 빌드, 실행, 배포, 시연할 수 있도록 정리한 포팅 매뉴얼이다.

- 프로젝트 구조: `web` / `api` / `ai` / `infra`
- 제출 폴더명: `exec`
- 소스코드는 GitLab clone 기준으로 재현하며, `exec`에는 포팅 문서와 DB 덤프 등 실행 보조 산출물만 둔다.
- 배포 방식: GitLab CI/CD에서 Docker image 빌드 및 GHCR push 후 EC2에서 `docker compose`로 기동
- 운영 진입점: EC2 systemd Nginx
- 외부 공개 URL
  - Production: `https://k14s209.p.ssafy.io`
  - Staging: `https://k14s209.p.ssafy.io:8443`

## 2. 프로젝트 구조

```bash

```

```powershell
cd api
.\gradlew.bat bootRun
```

확인 URL:

- Swagger UI: `http://localhost:8100/api/swagger-ui.html`

참고:

- Flyway migration은 `api/src/main/resources/db/migration` 기준으로 적용된다.
- jOOQ generated source가 없거나 stale하면 `bootRun`, `test`, `build` 진입점에서 필요한 codegen을 선행한다.
- schema 변경 후 빠르게 확인하려면 `./gradlew jooqGenerate`를 실행한다.

## 11. 배포 방식

### 11.1 GitLab Pipeline 단계

파일 기준: `.gitlab-ci.yml`

| Stage | Job | 설명 |
|---|---|---|
| `validate` | `infra_validate` | `infra/compose.deploy.yml` 렌더링 검증 |
| `test` | `web_ci` | `pnpm lint:web`, `pnpm build:web` |
| `test` | `ai_ci` | `pytest ai/tests -q` |
| `build` | `api_ci` | `./gradlew clean test bootJar` |
| `image` | `api_image` | API image build/push |
| `image` | `web_image` | Web image build/push |
| `image` | `ai_image` | AI image build/push |
| `deploy` | `deploy_dev` | `dev` push 시 staging 배포 |
| `deploy` | `deploy_prod` | `master` push 시 production 배포 |

### 11.2 브랜치별 동작

| 이벤트 | 동작 |
|---|---|
| 작업 브랜치 push | 변경 영역 CI 실행 |
| `dev` 또는 `master` 대상 MR | 변경 영역 CI 실행 |
| `dev` push | 이미지 빌드 후 staging 배포 |
| `master` push | 이미지 빌드 후 production 배포 |

### 11.3 EC2 디렉토리 구조

```text
/opt/axwms/
├── staging/
│   ├── .env
│   ├── compose.deploy.yml
│   └── remote-deploy.sh
└── production/
    ├── .env
    ├── compose.deploy.yml
    └── remote-deploy.sh
```

### 11.4 원격 배포 흐름

1. GitLab CI가 서비스별 Docker image를 GHCR에 push한다.
2. CI가 EC2의 `/opt/axwms/{staging|production}`으로 `compose.deploy.yml`, `remote-deploy.sh`를 복사한다.
3. EC2에서 `remote-deploy.sh`를 실행한다.
4. 스크립트가 GHCR login 후 `api`, `web`, `ai`, `ai_worker` image를 pull한다.
5. 기존 app container를 제거하고 `postgres`, `redis`, `qdrant`, `neo4j`, `api`, `web`, `ai`, `ai_worker`를 `up -d`로 기동한다.
6. Nginx 설정 파일과 snippet을 동기화한 뒤 `nginx -t`를 통과하면 reload한다.

수동 확인 명령:

```bash
cd /opt/axwms/staging
docker compose --env-file .env -f compose.deploy.yml -p axwms-staging ps

cd /opt/axwms/production
docker compose --env-file .env -f compose.deploy.yml -p axwms-production ps
```

## 13. 배포 시 특이사항

- `WEB_IMAGE`, `API_IMAGE`, `AI_IMAGE`는 서버 `.env`에 두지 않고 CI에서 SSH 실행 환경 변수로 주입한다.
- `staging`과 `production`은 같은 EC2를 사용할 수 있으므로 host port와 Docker volume name을 반드시 분리한다.
- Web/API container는 `127.0.0.1`에 bind되어 Nginx를 통해서만 외부 접근한다.
- AI container는 compose 기준 `0.0.0.0:${AI_HOST_PORT}:8200`으로 노출된다.
- `/api/internal/**`은 AI가 API callback에 사용하는 내부 경로이므로 Nginx에서 외부 접근을 차단한다.
- Production의 FastAPI 문서 페이지는 `ENVIRONMENT=production`일 때 비활성화된다.
- `JWT_SECRET`은 API와 AI에 같은 값을 주입해야 AI가 API 내부 callback 인증 흐름과 일관되게 동작한다.

## 14. 시연 시나리오

### 14.1 사전 준비

1. Web, API, AI, DB, Redis, Qdrant, Neo4j가 정상 실행 중인지 확인한다.
2. Seed 또는 DB dump가 적용되어 사용자/부서/팀/업무일지 데이터가 존재하는지 확인한다.
3. 시연 계정으로 로그인한다.

| 역할 | 이메일 |

| 팀원 | `u005@ibank.local` 이후 |

비밀번호는 적용한 seed 또는 DB dump의 계정 정책을 따른다.

### 14.2 기본 업무 흐름

1. 브라우저에서 서비스 접속
   - 로컬: `http://localhost:3000`

   - Production: `https://k14s209.p.ssafy.io`
2. `/login` 화면에서 시연 계정으로 로그인한다.
3. 대시보드(`/`)에서 내 업무, 팀 현황, 바로가기 영역을 확인한다.
4. 좌측 메뉴에서 `조직/부서`로 이동해 부서 목록과 상세 정보를 확인한다.
5. `팀` 메뉴로 이동해 팀 목록, 팀 상세, 팀원 구성을 확인한다.
6. `업무일지` 메뉴로 이동해 업무일지 목록을 확인한다.
7. 업무일지 상세 화면에서 요청/지시, 수행 내용, 상태, 첨부파일, AI 요약 정보를 확인한다.

2. 팀, 제목, 요청/지시, 수행 내용, 중요도, 기간 등을 입력한다.

6. 결과가 없거나 실패한 경우 재시도 버튼을 눌러 AI pipeline을 다시 호출한다.

## 15. 트러블슈팅

### 15.1 API가 DB에 연결되지 않음

- `docker compose -f infra/compose.local.yml ps`로 `postgres` 상태를 확인한다.
- 로컬 API 기본 DB port는 `5434`이다.
- `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD` 값을 확인한다.

### 15.2 jOOQ 또는 Flyway 실패

- Docker가 실행 중인지 확인한다.
- migration SQL 문법 오류를 확인한다.
- schema 변경 후 `cd api && ./gradlew jooqGenerate`로 codegen을 먼저 검증한다.

### 15.3 Web에서 API 호출 실패

- `web/.env`의 `NEXT_PUBLIC_API_BASE_URL`을 확인한다.
- 로컬 API는 `http://localhost:8100/api`이다.
- 배포 환경에서는 동일 origin `/api`로 라우팅되므로 절대 URL 설정이 없어도 된다.

### 15.4 AI 호출 실패

- `GEMINI_API_KEY` 또는 `GEMINI_API_KEYS`가 실제 key인지 확인한다.
- `PGVECTOR_DSN`의 port가 로컬 compose 기준 `5434`인지 확인한다.
- Qdrant `6333`, Neo4j `7687`, Redis `6379`가 실행 중인지 확인한다.

### 15.5 배포는 성공했지만 외부 접속이 안 됨

- EC2 내부에서 container 상태를 확인한다.

```bash
docker compose --env-file /opt/axwms/staging/.env -f /opt/axwms/staging/compose.deploy.yml -p axwms-staging ps
```

- Nginx 설정을 검증한다.

```bash
sudo nginx -t
sudo systemctl status nginx
```

- 보안그룹/방화벽에서 `80`, `443`, `8080`, `8443` 포트가 열려 있는지 확인한다.

### 15.6 GitLab 배포 job에서 SSH 실패

- `SSH_PRIVATE_KEY`가 GitLab Variables에 정상 등록되어 있는지 확인한다.
- private key 마지막 줄 개행 누락 또는 CRLF 오염 여부를 확인한다.
- `SSH_KNOWN_HOSTS`가 `ssh-keyscan <EC2_HOST>` 결과와 일치하는지 확인한다.
