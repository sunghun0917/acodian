# 업무일지 인덱싱 Celery 전환 설계

상태: 2026-10-26 사용자의 구현 시작 지시로 승인. 구현 계획에 따라 진행하며 별도 요청 없이 커밋·푸시하지 않는다.

## 1. 목적과 합의

Spring이 Outbox에서 직접 실행하던 업무일지 인덱싱을 AI 서버의 Redis 메시지 브로커와 Celery로 옮긴다. Outbox는 원본 변경과 전달 의도를 같은 DB 트랜잭션으로 저장하고, 폴러는 HTTP 접수까지만 책임진다. 실행 실패 재시도는 Celery가 맡는다.

사용자가 정한 경계:

- 이번 개발은 인덱싱에 한정한다. 요약·태깅 파이프라인과 첨부파일 요약의 실행 방식은 변경하지 않는다.
- 수정 중간 버전을 모두 처리할 필요는 없다. 실행 시점의 최신 업무일지 내용으로 색인하면 된다.
- 기존 업무일지별 잠금과 최신 DB 원본 조회 동작을 유지한다.
- 작업자는 우선 하나로 운영한다. 여러 작업자 대응과 CDC 구현은 후속 작업이다.
- 전달 경로는 Spring → AI HTTP 접수 → Redis → Celery로 선택했다.
- CDC 이전 기준선을 수집하고, CDC 이후에도 같은 실행 경로와 조건으로 비교한다.

앞서 논의한 전체 AI 완료 표시의 재정의와 태깅 완료 후 색인 실행 보장은 이번 인덱싱 전환에서 구현하지 않는다. 이번에 엄격히 구분할 것은 인덱싱의 접수 성공과 실제 실행 성공이다.

## 2. 현재 코드에서 확인한 사실

| 경로 | 현재 동작 |
|---|---|
| `WorklogAiPostProcessTrigger` | 생성 후처리 의도를 BEFORE_COMMIT에서 보존 |
| `WorklogAiPostProcessService` | 파일 요약·본문 파이프라인은 접수 성공, LIGHT_INDEX는 실제 색인 성공 후 완료 단계 기록 |
| `WorklogLightIndexTrigger`, `WorklogLightDeleteTrigger` | 수정·삭제 트랜잭션에서 Light Outbox에 의도 보존 |
| `WorklogLightOutboxRepository` | 업무일지별 단일 행에 최신 의도 병합, 삭제 우선, `revision`·선점 정보·점유 기한으로 전달 작업 선점 |
| `WorklogLightOutboxWorker` | 원격 재색인·삭제가 끝날 때까지 대기하고 실패하면 Outbox에서 재시도 |
| AI `/light/worklogs-v4/index`, `/reindex`, `/delete` | 현재는 실행 결과를 동기로 반환하고 내부 토큰 검증 |
| `LightWorklogIndexService` | 업무일지 잠금 안에서 원본 조회 및 색인·재색인·삭제 수행 |
| `worklog_mutation_locks` | 같은 프로세스·이벤트 루프 안의 `asyncio.Lock`; 분산 잠금 아님 |
| `celery_app` | Redis 메시지 브로커와 결과 저장소 사용. 실행 후 수신 확인 및 작업자 프로세스 종료 시 재전달 설정 적용 |
| Compose | 로컬 작업자는 `concurrency=1`, 배포 작업자는 명시적인 동시 실행 수 제한 없음 |
| `Worklog`의 기존 `@Version` | 업무 수정 충돌을 감지하는 낙관적 잠금용. 이번 색인 요청 순번으로 재사용하지 않음 |

색인 요청은 이전 본문 복사본이 아니라 업무일지 ID를 전달한다. 서비스가 실제 실행할 때 살아 있는 최신 원본을 조회한다. 따라서 단일 실행 경로에서 W2 완료 후 W1을 재실행하면 최신 원본을 다시 처리한다. W1 당시 본문을 복원하지 않는다.

## 3. 검토한 방식과 선택

| 대안 | 장단점 | 선택 |
|---|---|---|
| 기존 HTTP 접수를 통해 Celery 발행 | 현재 내부 HTTP 연동과 인증을 활용한다. Spring이 Celery 메시지 형식을 몰라도 된다. HTTP 전달 구간은 유지된다. | 사용자 선택 |
| Spring에서 Redis에 Celery 메시지 직접 발행 | HTTP 구간은 줄지만 Java와 Celery 프로토콜·작업 계약의 결합이 생긴다. | 제외 |
| CDC에서 작업 전달 | 폴러를 교체할 수 있으나 실행 전환과 동시에 바꾸면 성능 효과를 분리하기 어렵다. | 후속 비교 단계 |

작업 크기는 API·AI·배포 설정을 연결하는 프로젝트 수준이다. 다음 세부사항은 사용자 확정 사항과 구별한 설계자 제안이며, 이 문서 승인 대상으로 둔다.

## 4. 대상과 비대상

대상은 현재 최초 색인·재색인·삭제의 기존 기능을 유지하면서 모든 색인 변경을 하나의 Celery 실행 경로로 모으는 것이다. 생성 후처리는 LIGHT_INDEX의 전달·완료 연결부만 수정한다. 수정·삭제용 Light Outbox는 전달 전용으로 축소한다.

비대상:

- 요약·태깅·파일 요약의 작업 구성, 완료 조건 및 재시도 개편.
- 태깅 결과 생성 때문에 발생하는 추가 색인 트리거의 신설.
- 전체 AI 처리 완료 UI/알림 정책의 재정의.
- CDC, 다중 색인 작업자, 분산 잠금, 새 업무일지 원본 버전 컬럼.
- 별도 작업 관리 RDB 서버, Kafka, 새 범용 워크플로 엔진.

## 5. 전달과 실행 계약

```text
업무일지 변경 + Outbox 의도 저장 (같은 업무 DB 트랜잭션)
  → Spring 폴러가 짧게 선점
  → 내부 인증 HTTP 접수
  → Redis에 Celery 작업 발행 성공 확인
  → HTTP 202와 taskId 반환
  → 해당 Outbox 의도를 전달 완료 처리

Celery에서 색인 작업을 한 번에 하나씩 실행
  → 업무일지 잠금
  → 최신 DB 원본 조회
  → 기존 LightRAG 색인/재색인/삭제 서비스
  → 성공 또는 최종 실패 결과를 API에 통보
```

DB 트랜잭션을 HTTP 또는 AI 실행 동안 유지하지 않는다. 브로커 발행이 실패하면 HTTP 성공을 반환하지 않는다. HTTP 응답 유실 시 재발행할 수 있으므로 정확히 한 번 전달을 가정하지 않는다.

기존 API 경로의 동기 실행을 작업자와 병행하지 않는다. 내부 색인 요청은 비동기 접수 계약으로 전환하며 모든 API 클라이언트·배치 호출자·테스트를 함께 갱신한다. 수동 재구축 도구도 같은 큐로 보내거나 작업자를 중지한 유지보수 시간에만 실행한다.

기본 메시지는 업무일지 한 건을 대상으로 한다:

- `requestId`: 변경 의도마다 생성해 Outbox에 보존하는 UUID. 전달 재시도에서는 동일 값을 사용.
- `worklogId`와 `operation`: INDEX / REINDEX / DELETE.
- 측정용 생성·발행 시각과 추적 식별자. 본문·요약·태그 복사본은 싣지 않는다.

기존 일괄 호출 계약은 접수 단계에서 건별 작업으로 분할한다. 일부 발행 뒤 실패하면 전체 접수 실패로 응답하고 재전달을 허용한다. 재전달된 작업도 최신 원본 처리 규칙을 따른다.

작업자는 FastAPI의 애플리케이션 초기화·종료 처리가 자동으로 실행된다고 가정하지 않는다. LightRAG 연동 객체·DB 연결 풀·캐시의 초기화와 종료를 작업자 수명 주기에 연결하고 자식 프로세스 생성 전의 연결을 공유하지 않는다. 기존 다른 작업의 `asyncio.run()`을 그대로 복제해 이벤트 루프에 묶인 연동 객체를 서로 다른 루프에서 재사용하지 않는다. 구체적인 작업자 프로세스별 비동기 실행기 구성은 구현 계획에 맡기되 연속된 두 작업과 작업자 재시작을 실제로 검증한다.

`requestId`는 전달·결과 대응과 관측을 위한 식별자이며, Celery 작업 ID에 같은 값을 사용한다고 중복 실행이 차단되는 것은 아니다. 현재 Outbox의 `revision`은 행 삭제 후 재사용될 수 있으므로 영구적인 원본 버전이나 전역 작업 ID로 사용하지 않는다.

## 6. 단일 실행과 최신 내용

설계자 제안은 색인 전용 큐를 만들고 기존 `ai_worker` 하나가 기존 큐와 색인 큐를 함께 소비하되 `concurrency=1`로 운영하는 것이다. 작업자 서비스를 추가하지 않는다. 색인 큐를 소비하는 다른 작업자는 두지 않는다. 로컬과 배포 설정을 동일하게 고정한다. 작업 미리 가져오기 설정과 다른 AI 작업 정책은 변경하지 않는다. 긴 색인이 요약·태깅 작업도 지연시킬 수 있다는 처리량 한계는 기준선에 포함한다. 별도 색인 작업자 분리는 후속 운영 결정이다.

최초 색인·재색인·삭제가 모두 이 경로를 사용해야 한다. 단지 작업자 인스턴스가 하나라는 사실이나 기존 `asyncio.Lock`만으로 프로세스 간 직렬화가 확보되었다고 판단하지 않는다.

W1/W2 처리:

1. W1 실패 후 W2가 먼저 실행될 수 있다. 선입선출에 따른 완료 순서를 약속하지 않는다.
2. W2는 실행 당시 최신 원본을 읽어 색인한다.
3. W1 재시도 역시 실행 당시 최신 원본을 읽는다. 중복 비용은 허용하되 과거 요청의 복사본으로 덮어쓰지 않는다.
4. 이미 삭제된 업무일지에 늦은 INDEX/REINDEX가 들어와도 문서를 재생성하지 않는다. 최신 원본 부재에 맞춰 기존 색인을 정리하는 수렴 동작으로 통일한다.
5. 실행 도중 원본이 변경되면 해당 트랜잭션이 남긴 후속 요청이 최신 내용을 반영한다. 그 요청이 성공할 때까지 이전 내용이 보일 수 있다.

새로운 원본 버전 컬럼 없이 기존 최신 조회 방식을 유지한다. 이는 모든 중간 상태의 처리, 실시간 일관성, 오래된 작업 비용의 제거를 보장하는 설계가 아니다.

## 7. 접수와 실행 완료의 분리

HTTP 202를 색인 완료로 취급하면 기존 생성 후처리의 LIGHT_INDEX 계약이 깨진다. 이를 방지하기 위해 다음을 설계자 제안으로 둔다.

- 기존 업무 DB의 업무일지에 최신 색인 `requestId`, 현재 실행의 `executionId`, 실행 상태(PENDING / RUNNING / COMPLETED / FAILED), 마지막 오류·완료 시각을 최소한으로 보존한다. 독립 실행 큐나 별도 RDB는 만들지 않는다.
- 요청 의도를 만들 때 최신 requestId와 PENDING을 원본/Outbox와 함께 저장한다. Outbox 병합 시 새 의도에는 새 requestId를 부여한다.
- 작업자는 색인 변경 전에 내부 시작 API로 새 executionId를 등록한다. API가 오래된 requestId 또는 이미 COMPLETED인 동일 요청이면 실행 생략을 응답하여 색인을 생략한다. 시작 등록이 확인되지 않으면 색인에 진입하지 않는다. 현재 요청의 중복/재시도 실행이면 새 executionId로 교체하고 RUNNING으로 기록한다. 이는 실행 횟수 예약이나 분산 잠금이 아니라 결과의 권위를 구분하는 단일 실행 환경의 식별자다.
- 작업자는 실제 성공 또는 재시도 소진을 내부 인증이 적용된 결과 통보 API로 전달한다. API는 requestId와 executionId가 모두 현재 값과 일치할 때만 상태를 갱신한다. 늦게 온 W1의 결과나 동일 요청의 이전 실행 결과 모두 최신 결과를 덮어쓰지 못한다.
- 같은 requestId가 중복 실행되어 서로 반대인 결과를 만들면 가장 최근에 시작 등록된 실행의 결과를 인정한다. 예전 실행의 성공 결과가 늦게 도착해도 현재 실행의 실패를 뒤집지 않는다. 이미 성공 반영된 요청은 다음 중복 실행 시작을 차단한다. 같은 executionId의 최종 결과는 최초 한 번만 반영하고 동일 결과 재통보는 성공 응답한다. 모순된 결과 재통보는 상태를 변경하지 않고 운영 오류로 기록한다.
- 상태 갱신은 조건부 DB 트랜잭션으로 처리하며 같은 결과 통보의 반복은 멱등하게 수용한다. PENDING 갱신이 늦은 HTTP 응답 때문에 완료 상태를 되돌리지 않도록 PENDING은 접수 전 원본 트랜잭션에서만 설정한다.
- 색인 완료와 결과 통보 재시도를 분리한다. 결과 통보 실패 때문에 비싼 색인을 매번 다시 실행하지 않는다. 결과 통보에는 상태와 오류 코드만 담고 비밀정보·본문은 포함하지 않는다.

생성 후처리는 기존 행에 LIGHT_INDEX의 requestId와 접수 사실을 연결한다. 접수 사실과 완료 단계 기록을 분리하고, 202만으로 LIGHT_INDEX를 완료 처리하거나 성공 알림을 만들지 않는다. 실행 대기 중 작업 선점 상태나 DB 트랜잭션을 유지하지 않는다. 결과가 통보되면 연결된 요청 ID 및 현재 executionId가 일치할 때만 색인 단계 완료·실패를 반영하고 기존 종료 로직을 재개한다. 다른 단계의 기존 성공 정보와 재시도는 유지한다. 색인 요청이 새 것으로 대체되면 연결도 함께 이동시키거나 취소하여 오래된 결과를 기다리는 행이 남지 않게 한다. 완료 단계 기록과 결과 알림에도 같은 식별자 검사를 적용하고 동일 결과 통보로 중복 알림을 만들지 않는다.

여기의 결과 상태는 업무 결과 관측용이며 Celery 실행 횟수·예약 시각을 관리하는 두 번째 작업 큐가 아니다. Celery 작업 상태는 운영 진단에 사용하고 사용자에게 표시하는 상태의 유일한 근거로 삼지 않는다.

## 8. 장애와 재시도

| 실패 지점 | 담당과 처리 |
|---|---|
| DB 롤백 | 원본과 의도 모두 롤백, 작업 발행 없음 |
| HTTP/브로커 발행 실패 | Outbox 전달 재시도 |
| 발행 성공 후 HTTP 응답/Outbox 완료 유실 | 중복 전달 가능; 최신 원본 재처리 허용 |
| 작업자 종료·일시 네트워크/AI/저장소 장애 | Celery 재전달 또는 횟수를 제한하고 대기 시간을 늘리는 재시도 |
| 색인 서비스가 HTTP 성공과 함께 개별 실패를 반환 | 작업이 이를 실행 실패로 판정; 정상 성공으로 종료하지 않음 |
| 인증·설정 오류 또는 재시도 소진 | FAILED 결과 통보와 운영 로그; Spring이 자동으로 실행 재시도를 되살리지 않음 |
| 결과 통보 일시 실패 | 결과 통보 전달만 재시도, 실행 결과 유지 |
| Redis 장애로 승인된 작업 자체가 유실 | Outbox가 이미 정리됐으면 자동 복구 보장 없음; 영속성 확인과 탐지·수동 재접수 필요 |

기존 AI 재시도 보조 함수의 예외 분류는 색인 서비스의 반환 오류와 시간 초과를 모두 포괄하는지 확인 후 재사용한다. 구체적인 재시도 상한·대기 간격·실행 시간 제한은 구현 계획에서 현재 운영 값에 맞춰 제시한다. 무한 재시도는 하지 않는다.

기존 실행 후 수신 확인 및 작업자 프로세스 종료 시 재전달 설정을 유지한다. 실제 색인 시간이 브로커의 미확인 작업 재전달 제한 시간과 충돌하지 않는지 검증한다. 시간 초과 응답 뒤에도 백그라운드 색인 쓰기가 계속될 수 있는지 확인하고, 이전 쓰기가 살아 있는 상태로 다음 작업을 진행하지 않도록 종료 경계를 검증한다.

자동 재조정기는 이번에 추가하지 않는다. 오래 PENDING인 요청을 조회·경고하고 관리자가 현재 업무일지에 새 요청을 만드는 복구 절차를 제공한다. Redis 영속성 정책과 최대 복구 공백을 측정 보고서에 명시한다.

## 9. 전환과 호환성

작업자와 API를 무작정 섞어서 배포하지 않는다. 색인 폴러/접수 신규 유입을 일시 정지하고 기존 동기 색인 실행이 종료됐는지 확인한 뒤 새 계약을 적용한다. 원본 변경은 Outbox에 계속 보존할 수 있다. 단일 큐 소비자 기동 후 폴러를 재개한다.

기존 데이터에는 안정적인 requestId를 부여하고 남아 있는 생성 후처리 LIGHT_INDEX 단계와 Light Outbox를 새 접수 계약에 맞게 연결한다. 이미 완료한 요청을 모두 다시 색인하지 않는다. 새 작업 접수·결과 계약과 내부 인증, 로컬·배포 환경 변수·큐 라우팅·문서를 함께 수정한다.

롤백 시에는 새 큐 실행 중인 작업을 먼저 배출/중지하고 그 뒤 동기 실행을 복구한다. 두 실행 경로를 동시에 가동하지 않는다. 데이터와 미전달 의도를 지우는 방식으로 롤백하지 않는다.

## 10. 측정과 검증

### 비교군

- R0: 현재 Spring 동기 색인 실행. 참고용만 사용.
- R1: Outbox 폴러 → HTTP 접수 → Redis → 단일 Celery 실행. 이번 기준선.
- R2: CDC 전달 → 동일 HTTP 접수/Redis/Celery 실행. 후속 단계.

R1과 R2의 주 비교는 DB 변경에서 브로커 접수까지의 전달 지연이다. CDC가 HTTP를 우회하도록 바뀌면 전달 경로 변경 효과가 섞였음을 별도 기록한다. 요약·태깅 정책이나 색인 작업자 수를 동시에 바꾸지 않는다.

### 관측값

requestId, worklogId, operation, 전달 시도 ID, Celery 실행 시도 ID를 연결해 기록한다. 발행마다 같은 작업 ID가 생길 수 있으므로 작업 ID만으로 중복 건수를 집계하지 않는다.

시점은 의도 생성, DB 커밋 관측, 브로커 발행 확인, 작업자 시작, 색인 완료, 결과 통보 반영을 구분한다. 의도 생성 시각을 정확한 DB 커밋 시각으로 표현하지 않는다. 커밋 후 애플리케이션 관측값과 CDC의 원본 커밋 정보의 정확도 차이를 보고한다. 서버 시각을 동기화하고 프로세스 내부 실행 시간은 시스템 시각 변경에 영향을 받지 않는 단조 시계로 측정한다.

측정치는 구간별 p50/p95/p99, 접수·완료 처리량, 적체 건수와 최장 대기 시간, 폴링 쿼리 횟수·DB CPU/I/O, 전달자와 작업자의 자원 사용, 중복 실행·누락·최종 상태 불일치, 장애 후 복구 시간이다. 큐 깊이에는 예약·실행 중 작업을 별도로 표시한다.

같은 입력 데이터와 입력률, 폴링 주기·배치 크기, 실행 슬롯, Redis 영속성, 재시도 설정을 고정한다. 전달 실험은 모의 색인으로 변동을 줄이고 실제 LightRAG 실행은 별도 검증한다. 후속 CDC 채택 기준은 전달 지연·DB 부담 감소와 추가 운영 비용의 비교이며 숫자를 실측 전에 성과로 단정하지 않는다.

### 필수 시나리오

1. 원본 롤백 및 커밋 직후 전달 프로세스 종료.
2. Redis 발행 실패, 발행 성공 후 HTTP 응답 유실, Outbox 완료 기록 전 종료.
3. W1 실패 → 수정 → W2 완료 → W1 재시도: 최종 색인은 최신 DB 원본과 일치.
4. 색인 도중 수정 및 삭제: 후속 작업으로 최신 상태에 수렴하고 삭제 문서를 복원하지 않음.
5. 작업자 강제 종료·재시작, 실행 시간 초과, 개별 문서 실패, 재시도 소진.
6. 오래된 결과 통보·중복 결과 통보·결과 통보 장애: 최신 상태를 되돌리지 않으며 접수를 완료로 오인하지 않음. 같은 requestId에서 실행 A 성공 결과 통보 지연 → 실행 B 최종 실패 → A 성공 결과 통보 도착도 B의 실패를 유지하고, 성공 반영 후 재전달된 동일 요청은 색인을 생략함.
7. 최초 생성 후처리의 다른 단계 성공 정보 보존과 LIGHT_INDEX 실제 완료 전 성공 처리 방지.
8. 내부 인증 누락·불일치, 잘못된 operation/ID, 브로커 발행 실패 시 잘못된 202 방지.
9. 평상시·집중 유입 및 장애 복구 후 적체 해소 측정.

## 11. 구현 계획에 맡기는 사항과 승인 경계

구체적인 스키마와 DTO 이름, 결과 통보 API 경로, 큐 이름, 재시도 횟수, 측정 지표 수집 도구는 기존 프로젝트 관례에 맞춰 구현 계획에서 결정한다. 기존 Javadoc·인가·실패 경로 테스트와 AI 모듈 규칙을 따른다. 새 의존성은 기본적으로 추가하지 않는다.

계획은 API 전달·결과 계약, AI 작업·수명 주기, 단일 실행 배포, 회귀 검증·기준선 측정 순으로 나눈다. 실제 제품 코드는 이 문서 승인 후 `superpowers:writing-plans`로 계획을 작성한 다음 다룬다. 사용자 요청 없는 커밋·푸시는 하지 않는다.

승인된 설계자 제안은 생성·수정·삭제 경로 통합, 색인 전용 단일 실행 큐, 기존 업무 DB에 최소 결과 상태 저장, 내부 결과 통보 API, Redis 유실 시 자동 재조정 대신 탐지·수동 복구다. 구체적인 구현과 검증 결과는 구현 계획과 완료 보고서에 기록한다.
