# 프론트엔드 2인 협업 규칙

이 문서는 AX-WMS 프론트엔드 개발자 2명이 각자 브랜치를 나눠 작업할 때 충돌을 줄이기 위한 최소 기준이다.

## 1. 기본 원칙

- 실행 코드는 `apps/web`에 둔다.
- 저장소 문서에는 오래 유지할 기준만 남긴다.
- 한 작업은 한 사람이 주도하되, 공유 코드 변경은 사전에 합의한다.
- 진행 상황 공유는 이슈, MR/PR 설명, 코멘트를 우선 사용한다.

## 2. 작업 분담 원칙

- 가능한 한 라우트 단위로 나눠서 작업한다.
- 예시: 한 명은 `worklog`, 다른 한 명은 `user`, `team`처럼 도메인 폴더 기준으로 나눈다.
- `apps/web/src/app/_common`은 공용 영역이므로, 수정 전 반드시 상대와 공유한다.
- 공용 파일을 동시에 수정해야 하면 한 명이 먼저 반영하고, 다른 한 명은 그 기준에 맞춰 이어서 수정한다.

## 3. 문서 유지 규칙

- 새 작업 시작 전 `docs/web/ownership.md`에 담당 범위를 반영한다.
- 자주 바뀌는 진행 상황이나 임시 메모는 repo 문서에 남기지 않는다.
- PR 단위에서만 필요한 설명은 문서가 아니라 PR 본문에 남긴다.
- 장기적으로 유지할 프론트 규칙이 굳으면 추후 `docs/web/code-convention.yaml`로 옮긴다.

## 4. 파일 충돌 최소화 규칙

- 한 작업은 가능한 한 하나의 도메인 폴더 안에서 끝내는 것을 우선한다.
- 공통 컴포넌트, 공통 훅, 공통 유틸 수정은 작은 단위로 자주 공유한다.
- 큰 리팩토링은 기능 작업과 분리한다.
- 요청 범위를 넘는 정리성 수정은 하지 않는다.

## 5. 공유 코드 수정 규칙

- `_common/components`, `_common/hooks`, `_common/service`, `_common/store`, `_common/utils` 변경은 작업 시작 전에 상대에게 알린다.
- 공통 타입이나 유틸 이름을 바꾸면 PR 설명에 영향 범위를 함께 적는다.

## 6. 네이밍/구조 공통 규칙

- React 컴포넌트 파일명은 `camelCase`
- React 컴포넌트 export 이름은 `PascalCase`
- 예약 파일명은 `page.tsx`, `layout.tsx`, `middleware.ts` 유지
- 도메인 코드는 각 라우트 폴더 아래 `_components`, `_hooks`, `_service`, `_types`에 둔다
- 공통 코드는 `apps/web/src/app/_common`에 둔다

## 7. 두 사람이 특히 조심할 것

- 둘 다 동시에 `_common`을 크게 건드리지 않는다.
- 한 사람이 폴더 구조를 바꾸는 동안 다른 사람은 같은 영역 기능 개발을 피한다.
- 구두 합의만 하지 말고, 최소한 PR 또는 메신저에 변경 포인트를 남긴다.
