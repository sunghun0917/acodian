# Sidebar 피드백 및 수정 정리

- 작성일: 2026-04-21
- 파일명: `2026-04-21-sidebar-feedback.md`
- 대상 파일:
  - `web/src/app/_common/components/layout/sidebar.tsx`
  - `web/src/app/_common/components/layout/sidebar.config.ts`
  - `web/src/app/_common/components/layout/sidebar.utils.ts`

## 목적

최근 Sidebar 구현에 대해 받은 피드백을 정리하고, 실제로 반영한 수정 사항과 아직 후속 검토가 필요한 항목을 문서로 남긴다.

## 받은 피드백 요약

### 1. 메뉴 그룹 클릭 시 자동 이동 동작

- 메뉴 그룹을 클릭하면 첫 번째 하위 메뉴로 자동 이동하는 동작이 현재 UX 의도와 맞는지 확인이 필요하다는 의견이 있었다.
- 일반적인 패턴은 그룹을 클릭하면 하위 목록만 펼쳐지고, 사용자가 원하는 하위 메뉴를 직접 고르는 경우가 많기 때문에 현재 작업 중인 화면에서 갑자기 페이지가 이동하면 당황할 수 있다는 우려가 있었다.

### 2. `openGroup` 초기값을 `useEffect`로 맞추는 구조

- 기존 구조는 `openGroup = null`로 먼저 렌더링한 뒤, `useEffect`에서 `pathname`을 보고 활성 그룹을 다시 계산하는 방식이었다.
- 이 경우 처음 렌더링 후 한 번 더 상태를 갱신해야 하므로, 불필요한 추가 렌더링이 발생하고 사이드바가 뒤늦게 펼쳐지는 것처럼 보일 수 있다는 피드백이 있었다.

### 3. `getNestedCreateSubmenu`의 하드코딩

- `/department/create`, `/team/create`, `/user/create`를 함수 안에서 직접 분기하고 있어, 이후 도메인이 늘어나면 유지보수 비용이 커질 수 있다는 의견이 있었다.
- 경로 패턴이나 메뉴 설정 데이터 기반으로 조금 더 범용적으로 풀 수 있는지 검토가 필요하다는 제안이 있었다.

## 검토 결과

### 메뉴 그룹의 열림 상태는 사용자 토글 상태보다 현재 경로의 결과에 가깝다

현재 Sidebar의 UX는 다음 기준을 가진다.

- 사용자가 상위 메뉴를 클릭하면 첫 번째 서브메뉴로 이동한다.
- 같은 상위 메뉴를 다시 눌러도 닫히지 않는다.
- 현재 사용자가 어느 섹션에 있는지 시각적으로 보여주는 역할이 있다.

이 기준에서는 `openGroup`을 별도의 state로 들고 있는 것보다, `pathname`에서 현재 열려 있어야 할 그룹을 직접 계산하는 쪽이 더 자연스럽다고 판단했다.

즉 Sidebar의 열림 상태는 "토글 결과"라기보다 "현재 경로의 파생값"으로 보는 것이 맞다.

## 반영한 수정 사항

### 1. `openGroup` state 제거

기존에는 `useState`와 `useEffect`를 사용해 활성 그룹을 동기화했다.

- 제거한 것:
  - `useState`
  - `useEffect`
  - `openGroup`
  - `setOpenGroup`

변경 이유:

- 현재 경로만으로 어느 그룹이 열려 있어야 하는지 계산할 수 있기 때문이다.
- 초기 렌더링 이후 한 번 더 상태를 맞추는 흐름이 불필요했다.

### 2. `pathname` 기반 파생값으로 활성 그룹 계산

`sidebar.utils.ts`에 `getActiveGroupLabel(pathname)` 함수를 두고, 현재 경로를 기준으로 열려 있어야 할 그룹 라벨을 계산하도록 변경했다.

적용 방식:

- `Sidebar` 컴포넌트에서 `usePathname()`으로 현재 경로를 읽는다.
- `getActiveGroupLabel(pathname)`으로 활성 그룹을 계산한다.
- 각 메뉴 그룹의 `isOpen`은 `activeGroupLabel === item.label`로 판별한다.

효과:

- 처음 렌더링부터 올바른 그룹이 열린 상태로 표시된다.
- 라우트 변경 시 별도 `effect` 없이 자동으로 최신 상태를 반영한다.
- 불필요한 추가 렌더링과 깜빡임 가능성을 줄였다.

### 3. Sidebar 파일 역할 분리

기존에는 메뉴 데이터, 타입, UI, 경로 계산 로직이 `sidebar.tsx` 한 파일에 함께 들어 있었다.

현재는 다음처럼 역할을 분리했다.

- `sidebar.tsx`
  - 메인 Sidebar 렌더링
  - `pathname`과 `router` 사용
  - 각 메뉴 항목 렌더링
- `sidebar.config.ts`
  - `NavItem`, `NavSubItem` 타입 정의
  - `navItems` 메뉴 설정 데이터
- `sidebar.utils.ts`
  - `getActiveGroupLabel`
  - `getNestedCreateSubmenu`

이 분리는 `_common/hooks`, `_common/constants` 같은 앱 전역 공용 폴더로 빼는 대신, Sidebar 전용 로직을 같은 `layout` 레벨에 두는 방식으로 정리했다.

### 4. 상위 메뉴 클릭 동작 유지

상위 메뉴를 클릭했을 때 첫 번째 서브메뉴로 이동하는 동작 자체는 현재 구조에 남겨두었다.

다만 변경된 점은 다음과 같다.

- 예전처럼 상태를 직접 열고 닫지 않는다.
- 현재 경로가 이미 같은 그룹을 가리키고 있으면 추가 상태 변경은 하지 않는다.
- 열림 여부는 오직 경로 기준으로만 결정한다.

현재 구현 기준 동작:

- 닫힌 그룹을 클릭하면 첫 번째 하위 메뉴로 이동한다.
- 이미 열려 있는 그룹을 다시 클릭해도 닫히지 않는다.

## 아직 후속 검토가 필요한 항목

### 1. 자동 이동 UX 유지 여부

현재 코드는 상위 메뉴 클릭 시 첫 번째 하위 메뉴로 이동하도록 유지되어 있다.

다만 리뷰에서 나온 우려처럼, 사용자가 현재 화면을 벗어나지 않고 하위 메뉴 구조만 보고 싶을 수 있기 때문에 아래 두 방향 중 어떤 UX가 맞는지 추가 합의가 필요하다.

- 현재처럼 그룹 클릭 시 첫 번째 하위 메뉴로 이동
- 그룹 클릭 시 펼치기만 하고, 실제 이동은 하위 메뉴 클릭 시 수행

### 2. `getNestedCreateSubmenu` 일반화

현재는 명시적으로 다음 경로를 분기하고 있다.

- `/department/create`
- `/team/create`
- `/user/create`

이 구조는 당장은 명확하고 안전하지만, 도메인이 늘어날 때마다 함수 수정이 필요하다.

향후 검토 방향:

- 메뉴 설정 데이터 기반으로 `create` 하위 메뉴를 함께 정의
- 경로 규칙 기반으로 보다 일반화된 라벨 계산 방식 도입

현재 단계에서는 지나친 일반화보다 명시적 분기가 더 안전하다고 판단해 유지했다.

## 정리

이번 수정의 핵심은 다음 두 가지다.

1. Sidebar의 열림 상태를 state가 아닌 `pathname`의 파생값으로 전환했다.
2. Sidebar 전용 데이터와 계산 로직을 `config`, `utils` 파일로 분리했다.

그 결과 현재 Sidebar는 "사용자 토글 상태를 기억하는 컴포넌트"라기보다, "현재 사용자의 위치를 기준으로 섹션을 보여주는 네비게이션 컴포넌트"에 더 가깝게 정리되었다.

추가 UX 변경 여부는 자동 이동 동작 유지 여부와 함께 후속 논의가 필요하다.
