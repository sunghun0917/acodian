01. 먼저 보는 전체 지도

현재 큐와 Worker 구성

같은 Redis에 두 큐를 사용하며 각 큐는 별도 Celery Worker 컨테이너가 처리합니다. API 스케줄러는 Spring Boot에서 Outbox를 읽어 AI 서버에 요청하는 작업입니다.

일반 AI: ai_general

ai_worker가 파일 요약, 업무 요약, 태그 생성, 업무 임베딩을 처리합니다. 동시 실행 수는 1입니다.

색인: worklog_index

ai_index_worker가 색인·재색인·삭제와 색인 결과 전달 작업을 처리합니다. 동시 실행 수는 1입니다.

일반 AI 작업과 색인은 서로 기다리지 않습니다. 색인이 AI 태그 저장보다 먼저 원본을 읽으면 그 태그 관계는 다음 재색인까지 그래프에 없을 수 있습니다. 태그 저장만으로 재색인을 요청하지 않는 동작을 수용했습니다.

기존 celery 큐는 구독하지 않습니다. 이전 작업이 남아 있다면 별도 소비자가 필요합니다. 색인 락은 프로세스·이벤트 루프 범위이므로 색인 Worker를 늘려도 분산 쓰기 안전성이 보장되지 않습니다.

실선 순서로 이해하되 사용자 응답과 AI 실행은 같은 동기 요청이 아닙니다.

① 사용자 → API

인증·검증 후 업무 원본과 Outbox를 같은 트랜잭션에 반영합니다.

② API → AI HTTP

API 스케줄러가 Outbox를 선점해 AI 서버에 작업을 접수합니다.

③ AI → Redis → Worker

AI 서버가 Celery 작업을 발행합니다. 202는 접수일 뿐 완료가 아닙니다.

④ Worker → DB들 → API

색인 또는 삭제 후 결과를 보존하고 API에 콜백하여 상태를 갱신합니다.

색인 정책: 최초 색인·수정 재색인·삭제 정리의 개별 활성화 설정은 제거됐습니다. 색인 대상이 실제로 바뀌면 재색인을 요청하며, 삭제 시 내부 토큰이 비어 있으면 원본 삭제 전에 거부합니다. 파일 요약·업무 파이프라인의 별도 활성화 설정은 유지됩니다.

업무 원본 PostgreSQL

업무·태그·선행 업무·상태 이력 및 두 Outbox, 인덱스 요청·실행 상태의 기준 DB.

LightRAG PostgreSQL

업무 원본과 분리된 LightRAG 문서/KV와 문서 처리 상태.

Qdrant

임베딩 모델이 만든 청크·엔티티·관계 벡터를 workspace별로 저장.

Neo4j

엔티티 노드와 관계 엣지 등 그래프를 workspace 범위로 저장.

Redis + 결과 파일

Redis는 Celery 작업 전달에 사용. 결과 콜백은 AI 결과 디렉터리에 보존 후 전달.

02. 등록: 원본 저장부터 작업별 결과까지

① 저장

업무 원본과 SUMMARY·TAG·파일별 FILE_SUMMARY 및 Light INDEX 의도를 같은 트랜잭션에 저장합니다.

② 선점과 접수

각 Outbox를 SKIP LOCKED로 선점하고 attempts와 lease를 설정한 후 AI 큐에 전달합니다.

③ 실행

Worker는 최신 요청의 유효한 선점을 확인하고 일반 작업과 색인을 독립적으로 실행합니다.

④ 결과

AI가 결과를 보관·콜백하면 API는 최신 요청·실행·입력을 검증하고 작업별 상태와 알림을 커밋합니다.

03. 수정: 최신 의도로 재색인

① 원본 변경

본문 변경은 진행 중 요약·태그를 최신 입력 요청으로 교체합니다.

② REINDEX

색인 대상이 바뀌면 업무당 Light Outbox의 revision을 증가시키고 새 요청을 저장합니다.

③ 결과 적용

최신 요청·실행 결과만 반영하며 이전 결과는 무시합니다.

04. 삭제: 색인 정리

① 삭제

업무 삭제와 Light DELETE 의도를 함께 기록합니다. DELETE가 다른 색인 의도보다 우선합니다.

② 정리

Worker가 팀 사본과 전역 사본을 정리합니다. 팀 삭제에 실패하면 전역 소유권을 남깁니다.

③ 결과

현재 실행의 결과만 적용하고 실패 시 한도 내에서 재시도합니다. 삭제된 업무의 색인 실패도 작성자가 수동 재시도할 수 있습니다.

05. 인덱싱 내부: 데이터가 실제로 바뀌는 순서

색인 내부 시퀀스: 저장소별 데이터 생성

위에서 아래로 시간 순서입니다. 실선은 호출·변경, 점선은 응답입니다. 가로로 스크롤할 수 있습니다.

workspace별 쓰기에는 S 락을 사용합니다. W/S는 프로세스·이벤트 루프 범위의 락이며 여러 저장소를 묶는 트랜잭션이 아닙니다.

시퀀스 텍스트로 읽기
  1. 색인 Worker → 색인 서비스: ① 실행 시작: 업무별 W 락
  2. 색인 서비스 → 업무 DB: ② 현재 업무·태그·선행 업무 조회
  3. 업무 DB → 색인 서비스: ③ 원본 행과 관계 반환
  4. 색인 서비스 → 전역 workspace: ④ 이전 소유권 확인 및 STAGING
  5. 색인 서비스 → 팀 workspace: ⑤ 이전·현재 팀 사본 정리
  6. 색인 서비스 → 전역 workspace: ⑥ 이전 전역 사본 정리
  7. 색인 서비스 → 전역 workspace: ⑦ 전역 본문 입력 → 청크·native 상태 저장
  8. 전역 workspace → Neo4j / Qdrant: ⑧ 본문 추출 그래프·벡터 반영
  9. 색인 서비스 → 전역 workspace: ⑨ 확정 Custom KG 및 indexed_team_id 저장
  10. 전역 workspace → Neo4j / Qdrant: ⑩ 확정 엔티티·관계 반영
  11. 색인 서비스 → 팀 workspace: ⑪ 팀 본문·확정 Custom KG 저장
  12. 팀 workspace → Neo4j / Qdrant: ⑫ 팀 그래프·벡터 반영
  13. 색인 서비스 → 전역 workspace: ⑬ 전역 metadata COMPLETED 기록 및 확인
  14. 색인 서비스 → 색인 Worker: ⑭ 결과 반환
W와 S: W는 업무 ID 단위, S는 workspace 쓰기 단위의 애플리케이션 락입니다. 둘 다 현재 asyncio.Lock 기반으로 단일 프로세스·이벤트 루프 범위이며 Redis 분산 락이 아닙니다. S는 전체 과정을 한 번에 잠그는 것이 아니라 각 쓰기 연산마다 획득합니다.
W 획득

① 원본 읽기와 입력 문서 생성

업무 원본 PostgreSQL에서 현재 데이터를 읽습니다. 텍스트 문서는 업무 ID·제목·요청 내용·업무 내용으로 구성합니다. 별도의 Custom KG는 업무·작성자·팀·태그·직접 선행 업무와 확정 관계를 구성합니다.

공개 게이트 및 복구 준비

② 이전 소유권 확인 → STAGING → 기존 사본 삭제

이전 팀 ID를 확인하고 전역 문서 공개 게이트를 닫습니다. 이전 팀과 현재 팀의 기존 사본, 전역 사본을 정리합니다. 재시도 시 부분 산출물이 남아 native 중복 필터에 의해 건너뛰는 것을 방지하기 위한 순서입니다.

③ 전역 본문과 Custom KG 삽입

전역 보상 대상을 먼저 등록하고 ainsert로 본문을 색인해 native 문서 상태 processed를 확인합니다. 이후 확정 관계 Custom KG를 삽입하고 indexed_team_id를 저장합니다.

↓

④ 팀별 본문과 확정 KG 삽입

팀 보상 대상을 등록하고 소속 팀 workspace에서 본문과 Custom KG를 색인합니다. 팀 KG에는 다른 팀 선행 업무의 제목·관계를 복사하지 않습니다.

↓
공통 완료 게시

⑤ 전역 COMPLETED 기록·읽기 확인 → W 해제

전역과 팀 반영이 끝난 후 전역 문서 metadata를 COMPLETED로 바꾸고 저장 결과를 확인합니다. 검색은 별도의 현재 DB·소유권 검증도 수행합니다. processed는 LightRAG native 처리 상태이고 COMPLETED는 이 프로젝트의 공개 게이트입니다.

텍스트 경로

문서 → 청크 → LLM 엔티티·관계 추출 → 임베딩 모델 → Qdrant 벡터 및 Neo4j 그래프. 고·저수준 키워드는 주로 검색 질문 처리에서 구분하며 Qdrant/Neo4j에 각각 대응하는 이름이 아닙니다.

확정 관계 경로

원본 DB → WORKLOG, USER, TEAM, TAG 및 AUTHORED_BY, BELONGS_TO, HAS_TAG, DEPENDS_ON → Custom KG. LLM 추측 관계와 출처가 다릅니다.

06. 실패 · 보상 · 재시도

자동 재시도

전달 또는 일시 실행 실패는 단일 attempts 한도 내에서 backoff 후 Outbox가 재선점합니다. 기본 한도는 4회입니다.

부분 보상

색인 실패·취소 시 부분 산출물을 정리합니다. timeout·강제 종료·저장소 오류에서는 부분 데이터가 남을 수 있습니다.

결과 재전달

결과를 파일에 보관한 뒤 콜백합니다. 전송 실패 시 보관 결과만 재전송하며 ACK 후 삭제합니다. API가 영구 4xx(408/429 제외)로 거절하면 재전송을 멈추고 파일을 지우며, 작업은 lease 만료 회수로 FAILED가 됩니다.

수동 재시도

시도 한도 소진, 치명적 오류 또는 lease 만료는 FAILED와 알림으로 끝납니다. 작성자는 새 요청으로 실패 작업을 재시도할 수 있습니다.

원격 쓰기 한계

timeout 후 전송된 외부 쓰기는 계속될 수 있으며 프로세스 내부 잠금은 다중 Worker 직렬화를 보장하지 않습니다.

07. 상태 변화

PENDING → RUNNING

최신 요청이 선점되고 AI 실행 시작이 승인됩니다.

COMPLETED / FAILED

현재 실행의 성공 또는 최종 실패를 반영하고 작업별 알림을 저장합니다.

새 요청

수정이나 수동 재시도는 새 요청을 만들며 오래된 실행의 결과는 현재 상태를 바꾸지 않습니다.

검색 흐름

검색 시퀀스: 후보 검색부터 답변까지

위에서 아래로 시간 순서입니다. 실선은 호출·변경, 점선은 응답입니다. 가로로 스크롤할 수 있습니다.

허용 팀이 []이면 API는 AI를 호출하지 않습니다. 후보가 모두 제외되면 LLM 호출 없이 빈 결과를 반환합니다. 내부 SSE도 검증 후 토큰을 전달합니다.

시퀀스 텍스트로 읽기
  1. 사용자 → API 서버: ① 시맨틱 검색 요청
  2. API 서버 → API 서버: ② 사용자 가시성으로 허용 팀 계산
  3. API 서버 → AI 검색 서비스: ③ 내부 query: allowed_team_ids
  4. AI 검색 서비스 → LightRAG 저장소: ④ 허용 팀 또는 전역에서 후보 검색
  5. LightRAG 저장소 → AI 검색 서비스: ⑤ 후보 출처에서 업무 ID 추출
  6. AI 검색 서비스 → LightRAG 저장소: ⑥ 전역 processed + COMPLETED 확인
  7. AI 검색 서비스 → 업무 DB: ⑦ 현재 업무·팀·삭제 여부·허용 범위 확인
  8. 업무 DB → AI 검색 서비스: ⑧ 현재 원본과 관계 반환
  9. AI 검색 서비스 → LightRAG 저장소: ⑨ indexed_team_id·팀 processed·전역 완료 재확인
  10. AI 검색 서비스 → LLM: ⑩ 검증된 현재 DB 내용으로 답변 생성
  11. LLM → AI 검색 서비스: ⑪ 답변 반환
  12. AI 검색 서비스 → API 서버: ⑫ 답변과 검증된 references
  13. API 서버 → 사용자: ⑬ JSON 응답

전사·팀 후보 검색 → 공통 COMPLETED·현재 DB·소유권 검증 → 일반/SSE 생성 · 응답 캐시 비활성

예시로 따라가기 · 재고 조회 API 개선 검색

업무 1001은 팀 101, 업무 2002는 팀 202 소속이라고 가정합니다. 가상 예시이며 실제 모델 응답을 고정하지 않습니다.

  1. API는 사용자의 가시성으로 allowed_team_ids를 계산합니다. [101]이면 팀 101만 검색하고, null이면 전역에서 검색합니다. []이면 사용자 API는 AI를 호출하지 않습니다.
  2. LightRAG는 답변이 아니라 후보 ID를 찾습니다. 전사·팀 모두 공통 전역 processed+COMPLETED를 요구합니다.
  3. 업무 DB에서 현재 생존·팀을 읽고 색인 당시 소유권·현재 팀 native processed·전역 완료 재확인을 수행합니다. 업무 1001이 삭제·이동·미완료 상태면 답변 문맥에서 제외합니다.
  4. 통과한 현재 DB 본문·태그·작성자·팀·검증된 직접 선행 관계로 문맥을 구성해 답변합니다. 직접 선행 업무도 별도로 같은 공개·권한 검증을 거치며 허용된 경우 references에 포함될 수 있습니다. 일반 JSON과 내부 SSE 모두 같은 검증을 거칩니다.

전사·팀 모두 응답 캐시는 임시 비활성화입니다. no_results만 정상 빈 결과이며 다른 failure는 오류로 보고합니다. SSE는 검증 전 토큰을 내보내지 않지만, 이후 동시 삭제를 매 토큰 재검증하거나 이미 전송한 토큰을 회수하지 않습니다.

직접 선행 업무 후보가 100개를 초과하거나 확정 관계 문맥이 12,000자를 초과하면 빈 결과가 아니라 오류입니다. 내부 query/stream SSE는 사용자 REST 검색의 프록시가 아닙니다. SSE 문맥 검색·생성 시작·토큰 수신에는 전체 시간 제한을 적용합니다.

색인 저장소의 튜플과 데이터 흐름

같은 업무가 업무 DB, LightRAG PostgreSQL, Neo4j, Qdrant에 서로 다른 형태로 존재합니다. 이 저장소들은 하나의 DB 트랜잭션으로 묶이지 않습니다.

① 업무 DB에서 현재 원본 읽기
tb_worklog (1001, team_id=101, 제목, 본문, ...)
+ 태그 + 접근 가능한 선행 업무
↓ 문서 ID worklog-1001 · 출처 worklog://1001
② LightRAG PostgreSQL: 문서와 처리 상태
lightrag_doc_full: (workspace, id=worklog-1001, content, ...)
lightrag_doc_status: (workspace, id=worklog-1001, status, chunks_list,
  metadata={indexing_status: STAGING/COMPLETED, indexed_team_id: 101}, ...)
indexed_team_id는 전역 문서의 색인 당시 팀 소유권입니다. native 처리 상태와 metadata의 공개 게이트는 다른 값입니다. 예시는 workspace마다 metadata가 동일하다는 뜻이 아닙니다.
↓ 청크 분할 · 엔티티와 관계 추출
③ 본문과 출처 추적
lightrag_doc_chunks: (workspace, 청크 ID, 본문, 문서/캐시 연결, ...)
lightrag_full_entities / lightrag_full_relations: 문서별 엔티티·관계 목록
lightrag_entity_chunks / lightrag_relation_chunks: 엔티티·관계와 출처 청크 연결
lightrag_llm_cache: 추출 및 응답 캐시
위 값은 저장 데이터의 개념이며 SQL 전체 컬럼 정의는 아닙니다.
↓ 그래프·벡터 기록 및 전역/팀 완료 확인
④ Neo4j와 QdrantNeo4j에는 엔티티와 관계 그래프, Qdrant에는 검색용 벡터가 기록됩니다. 전역과 팀 workspace를 구분합니다. 완료 게이트가 열려야 검색 후보로 사용할 수 있습니다.
↓ 후보를 가져온 뒤 현재 원본 재검증
⑤ 검색 문맥 생성허용 팀, 전역 완료, 현재 업무·팀의 삭제 여부 및 색인 당시 팀 소유권을 확인합니다. 통과한 업무의 현재 DB 본문으로 답변 문맥을 만듭니다. 여러 저장소의 동일 시점 snapshot은 보장하지 않습니다.

LightRAG 라이브러리 테이블의 상세 열은 설치 버전과 DB를 확인해야 합니다. 예시 ID·팀·내용은 실제 데이터가 아닙니다.

근거: LightRAG PostgreSQL 저장·조회 의미, 수정·삭제 Outbox DDL, 등록 Outbox DDL, 색인 상태 DDL, 등록 복구 DDL, V24 Outbox 역할 분리. 전환 주의: V24는 두 Outbox 중 하나라도 행이 남아 있으면 중단하며 자동 삭제하지 않습니다. 기존 작업의 처리·폐기는 배포 전에 별도로 결정해야 합니다.
