01. 먼저 보는 전체 지도

현재 큐와 Worker 구성

같은 Redis에 두 큐를 사용하며 각 큐는 별도 Celery Worker 컨테이너가 처리합니다. API 스케줄러는 Spring Boot에서 Outbox를 읽어 AI 서버에 요청하는 작업입니다.

일반 AI: ai_general

ai_worker가 파일 요약, 업무 요약, 태그 생성, 업무 임베딩을 처리합니다. 동시 실행 수는 1입니다.

색인: worklog_index

ai_index_worker가 색인·재색인·삭제와 색인 결과 전달 작업을 처리합니다. 동시 실행 수는 1입니다.

일반 AI 작업과 색인은 서로 기다리지 않습니다. 색인이 AI 태그 저장보다 먼저 원본을 읽으면 그 태그 관계는 다음 재색인까지 그래프에 없을 수 있습니다. 태그 저장만으로 재색인을 요청하지 않는 동작을 수용했습니다.

기존 celery 큐는 구독하지 않습니다. 이전 작업이 남아 있다면 별도 소비자가 필요합니다. 색인 락은 프로세스·이벤트 루프 범위이므로 색인 Worker를 늘려도 분산 쓰기 안전성이 보장되지 않습니다.

실선 순서로 이해하되 사용자 응답과 AI 실행은 같은 동기 요청이 아닙니다.

① 사용자 → API

인증·검증 후 업무 원본과 Outbox를 같은 트랜잭션에 반영합니다.

② API → AI HTTP

API 스케줄러가 Outbox를 선점해 AI 서버에 작업을 접수합니다.

③ AI → Redis → Worker

AI 서버가 Celery 작업을 발행합니다. 202는 접수일 뿐 완료가 아닙니다.

④ Worker → DB들 → API

색인 또는 삭제 후 결과를 보존하고 API에 콜백하여 상태를 갱신합니다.

색인 정책: 최초 색인·수정 재색인·삭제 정리의 개별 활성화 설정은 제거됐습니다. 색인 대상이 실제로 바뀌면 재색인을 요청하며, 삭제 시 내부 토큰이 비어 있으면 원본 삭제 전에 거부합니다. 파일 요약·업무 파이프라인의 별도 활성화 설정은 유지됩니다.

업무 원본 PostgreSQL

업무·태그·선행 업무·상태 이력 및 두 Outbox, 인덱스 요청·실행 상태의 기준 DB.

LightRAG PostgreSQL

업무 원본과 분리된 LightRAG 문서/KV와 문서 처리 상태.

Qdrant

임베딩 모델이 만든 청크·엔티티·관계 벡터를 workspace별로 저장.

Neo4j

엔티티 노드와 관계 엣지 등 그래프를 workspace 범위로 저장.

Redis + 결과 파일

Redis는 Celery 작업 전달에 사용. 결과 콜백은 AI 결과 디렉터리에 보존 후 전달.

02. 등록: 원본 저장부터 결과 집계까지

등록 시퀀스: Light INDEX 요청부터 색인 완료까지

색인 경로를 위에서 아래로 표시합니다. 일반 AI 요청은 위 분기 차트처럼 별도 Outbox에서 독립 실행됩니다. 실선은 호출·변경, 점선은 응답입니다. 가로로 스크롤할 수 있습니다.

실패 시 재시도·결과 재전달 또는 등록 후처리 최종 중단이 발생할 수 있습니다. 상세 조건은 실패·재시도 항목을 확인하세요.

시퀀스 텍스트로 읽기
  1. 사용자 → API 서버: ① 업무일지 등록 요청
  2. API 서버 → 업무 DB: ② 원본·일반/색인 Outbox 저장, PENDING (같은 트랜잭션)
  3. 업무 DB → API 서버: ③ 커밋
  4. API 서버 → 사용자: ④ 등록 응답: worklogId (색인 완료 전)
  5. API 스케줄러 → 업무 DB: ⑤ Light Outbox 선점: token / lease
  6. API 스케줄러 → AI 서버 / 큐: ⑥ Light INDEX 요청
  7. AI 서버 / 큐 → API 스케줄러: ⑦ 202 접수: 결과는 아직 없음
  8. AI 서버 / 큐 → 색인 Worker: ⑧ 큐에서 색인 작업 실행
  9. 색인 Worker → API 서버: ⑨ start(request ID, execution ID)
  10. API 서버 → 업무 DB: ⑩ 현재 요청이면 RUNNING 기록
  11. API 서버 → 색인 Worker: ⑪ 시작 승인 또는 거부
  12. 색인 Worker → 업무 DB: ⑫ 현재 업무 원본 조회
  13. 색인 Worker → LightRAG 저장소: ⑬ 전역 본문·확정 KG → 팀 본문·확정 KG
  14. 색인 Worker → LightRAG 저장소: ⑭ 양쪽 성공 후 전역 COMPLETED 게시
  15. 색인 Worker → API 서버: ⑮ 결과 보존 후 result 콜백
  16. API 서버 → 업무 DB: ⑯ 현재 request / execution 검증 후 결과 반영
  17. API 스케줄러 → 업무 DB: ⑰ 등록 후처리 집계: 전체 완료 시 Outbox 정리

일반 AI Outbox는 파일 요약·본문 파이프라인을 요청하고, Light Outbox는 최초 INDEX를 별도로 전달합니다. 두 경로의 실행 순서는 보장되지 않습니다. 등록 결과 알림은 일반 AI 요청의 접수 결과와 최신 색인 결과를 집계하며, 일반 AI의 실제 Worker 완료까지 기다리는 것은 아닙니다. 색인 대기 중 일반 요청이 실패하면 실패 단계는 보존하고, 성공·실패 알림 모두 최신 색인 종료를 기다립니다. 완료 전 업무가 삭제되면 등록 결과 알림을 보내지 않습니다. 등록 응답은 색인 완료를 기다리지 않습니다.

AI → API 콜백

⑧ 결과 보존 → 검증 → 상태·Outbox 집계

API는 일치하는 Light Outbox 행과 최신 request ID·execution ID의 RUNNING 결과만 반영합니다. 색인 성공 시 Light 행을 삭제하고 등록 집계를 깨웁니다. 일반 Outbox는 일반 AI 접수 결과와 최신 색인 상태를 함께 집계해 결과 알림을 보냅니다. 최초 INDEX의 최종 실패는 자동 전달을 중단하며 수동 재요청이나 새로운 색인 의도로 재개할 수 있습니다.

03. 수정: 변경 감지와 재색인

파일과 본문은 별도 경로: 수정 때 새 파일이 추가되면 파일 요약 기능이 활성화된 경우 커밋 후 파일별 요약을 직접 요청합니다. 제목·요청 내용·업무 내용·태그·선행 업무가 실제 변경되면 재색인 Outbox를 기록합니다. 파일만 바뀌었다는 이유로 이 재색인 경로가 실행되지는 않습니다. 현재 수정 경로는 업무 요약·태그 생성 파이프라인을 자동 재요청하지 않습니다.

수정 시퀀스: 변경 감지와 재색인

위에서 아래로 시간 순서입니다. 실선은 호출·변경, 점선은 응답입니다. 가로로 스크롤할 수 있습니다.

재색인 대상이 아닌 변경이면 ③ 이후 색인 경로는 실행되지 않습니다. 실패하면 Outbox를 보존하고 재시도합니다.

  4. 업무 DB → API 서버: ④ 커밋
  5. API 서버 → 사용자: ⑤ 수정 응답 (재색인 완료 전)
  6. API 스케줄러 → 업무 DB: ⑥ Outbox 선점: revision / token / lease
  7. API 스케줄러 → AI 서버 / 큐: ⑦ /reindex 요청
  8. AI 서버 / 큐 → API 스케줄러: ⑧ 202 접수
  9. API 스케줄러 → 업무 DB: ⑨ 결과 대기: 행은 유지
  10. AI 서버 / 큐 → 색인 Worker: ⑩ 큐 작업 실행
  11. 색인 Worker → API 서버: ⑪ start: 요청·실행 검증

  13. 색인 Worker → 업무 DB: ⑬ 현재 원본 및 팀 조회
  14. 색인 Worker → LightRAG 저장소: ⑭ STAGING → 이전 사본 정리 → 전역·팀 재색인

  16. 색인 Worker → API 서버: ⑯ 결과 보존 후 result 콜백
  17. API 서버 → 업무 DB: ⑰ 현재 실행이면 결과 반영; 성공 시 해당 Outbox 삭제

③ 최신 수정 의도 저장

④ 재색인 요청과 접수 대기

↓
Celery · 최신 원본

⑤ 문서 락 → 현재 원본 조회 → 재구성

현재 살아 있는 원본을 읽고 기존 팀·전역 사본을 정리한 뒤 최신 데이터로 전역과 팀을 다시 인덱싱합니다. 원본이 이미 없거나 소프트 삭제된 경우에는 저장된 소유권을 이용해 잔존 문서를 정리합니다. 정리에 성공하면 Worker는 해당 요청을 완료로 통보하며, 원본을 새로 색인했다는 뜻은 아닙니다.

↓
콜백

⑥ 현재 요청·실행만 반영

성공 시 해당 request ID의 Light Outbox 행을 삭제합니다. 최종 실패는 상태를 FAILED로 기록하고 해당 Outbox 의도를 보존·백오프합니다. 늦게 도착한 이전 요청/실행 결과는 무시합니다.

04. 삭제: 원본 소프트 삭제와 인덱스 정리

삭제 시퀀스: 원본 소프트 삭제와 색인 정리

위에서 아래로 시간 순서입니다. 실선은 호출·변경, 점선은 응답입니다. 가로로 스크롤할 수 있습니다.

팀 삭제 실패 시 전역 소유권을 남깁니다. 원본은 소프트 삭제 상태로 남으며 저장소 간 원자적 롤백은 보장하지 않습니다.

05. 인덱싱 내부: 데이터가 실제로 바뀌는 순서

색인 내부 시퀀스: 저장소별 데이터 생성

위에서 아래로 시간 순서입니다. 실선은 호출·변경, 점선은 응답입니다. 가로로 스크롤할 수 있습니다.

workspace별 쓰기에는 S 락을 사용합니다. W/S는 프로세스·이벤트 루프 범위의 락이며 여러 저장소를 묶는 트랜잭션이 아닙니다.

시퀀스 텍스트로 읽기
  1. 색인 Worker → 색인 서비스: ① 실행 시작: 업무별 W 락
  2. 색인 서비스 → 업무 DB: ② 현재 업무·태그·선행 업무 조회
  3. 업무 DB → 색인 서비스: ③ 원본 행과 관계 반환
  4. 색인 서비스 → 전역 workspace: ④ 이전 소유권 확인 및 STAGING
  5. 색인 서비스 → 팀 workspace: ⑤ 이전·현재 팀 사본 정리
  6. 색인 서비스 → 전역 workspace: ⑥ 이전 전역 사본 정리
  7. 색인 서비스 → 전역 workspace: ⑦ 전역 본문 입력 → 청크·native 상태 저장
  8. 전역 workspace → Neo4j / Qdrant: ⑧ 본문 추출 그래프·벡터 반영
  9. 색인 서비스 → 전역 workspace: ⑨ 확정 Custom KG 및 indexed_team_id 저장
  10. 전역 workspace → Neo4j / Qdrant: ⑩ 확정 엔티티·관계 반영
  11. 색인 서비스 → 팀 workspace: ⑪ 팀 본문·확정 Custom KG 저장
  12. 팀 workspace → Neo4j / Qdrant: ⑫ 팀 그래프·벡터 반영
  13. 색인 서비스 → 전역 workspace: ⑬ 전역 metadata COMPLETED 기록 및 확인
  14. 색인 서비스 → 색인 Worker: ⑭ 결과 반환
W와 S: W는 업무 ID 단위, S는 workspace 쓰기 단위의 애플리케이션 락입니다. 둘 다 현재 asyncio.Lock 기반으로 단일 프로세스·이벤트 루프 범위이며 Redis 분산 락이 아닙니다. S는 전체 과정을 한 번에 잠그는 것이 아니라 각 쓰기 연산마다 획득합니다.

공통 완료 게시

⑤ 전역 COMPLETED 기록·읽기 확인 → W 해제

전역과 팀 반영이 끝난 후 전역 문서 metadata를 COMPLETED로 바꾸고 저장 결과를 확인합니다. 검색은 별도의 현재 DB·소유권 검증도 수행합니다. processed는 LightRAG native 처리 상태이고 COMPLETED는 이 프로젝트의 공개 게이트입니다.

텍스트 경로

문서 → 청크 → LLM 엔티티·관계 추출 → 임베딩 모델 → Qdrant 벡터 및 Neo4j 그래프. 고·저수준 키워드는 주로 검색 질문 처리에서 구분하며 Qdrant/Neo4j에 각각 대응하는 이름이 아닙니다.

확정 관계 경로

원본 DB → WORKLOG, USER, TEAM, TAG 및 AUTHORED_BY, BELONGS_TO, HAS_TAG, DEPENDS_ON → Custom KG. LLM 추측 관계와 출처가 다릅니다.

06. 실패 · 보상 · 재시도

등록 트랜잭션 실패

업무 원본과 일반 AI·Light Outbox의 DB 기록이 함께 롤백됩니다. 별도 파일 저장소 작업까지 DB 트랜잭션만으로 원자적이라고 가정하지 않습니다.

AI 접수 실패

API worker가 Outbox 오류·시도 횟수·다음 시각을 기록하고 재전달합니다. AI의 큐 발행 실패는 503으로 반환됩니다. 접수 성공 후에도 결과가 없으면 대기 기한 경과 후 복구 경로가 동작합니다.

인덱싱 중 실패

보상 목록에 등록된 workspace를 역순(팀 → 전역)으로 삭제합니다. COMPLETED 시도 중 실패했다면 우선 공개 게이트를 다시 닫습니다. 보상 실패는 별도 오류로 보고하며 성공으로 숨기지 않습니다. 완료 게시를 시도한 후에는 전역 게이트를 다시 닫는 데 실패하면 삭제를 진행하지 않고, 팀 정리에 실패하면 전역 소유권을 남깁니다. 보상은 이전 인덱스를 복원하는 것이 아니라 부분 산출물 정리입니다.

Celery 재시도

재시도 가능한 인덱싱 예외는 최대 5회 재시도(최초 포함 최대 6회), 지수 대기. 설정 오류·내부 토큰 관련 치명적 오류는 제외됩니다. 시작 통지 자체는 별도 제한 재시도이며 모든 오류가 동일한 정책은 아닙니다. 색인 실행 제한은 기본 300초이고, 보상은 별도 작업으로 기본 120초까지 기다립니다. Celery 강제 종료 기본 540초는 보상과 결과 보관·전달 여유를 포함하도록 설정 검증됩니다.

최종 실패 후

AI가 FAILED 결과를 보존·콜백합니다. Light Outbox의 최초 INDEX 최종 실패는 terminal_failed=true로 자동 선점을 중단하고 등록 집계도 정지할 수 있습니다. REINDEX·DELETE 실패는 의도를 보존하고 백오프로 재전달합니다. 새 INDEX/REINDEX 의도는 등록 집계 정지를 해제합니다.

콜백 전달 실패

AI의 결과 파일을 유지하고 재전달합니다. 이미 보존된 결과가 있으면 인덱싱을 반복하기보다 결과 전달을 시도합니다. 결과 파일 보존 자체가 실패하는 경우도 있으므로 전달 성공을 무조건 보장한다고 단정하지 않습니다.

검색 시퀀스: 후보 검색부터 답변까지

위에서 아래로 시간 순서입니다. 실선은 호출·변경, 점선은 응답입니다. 가로로 스크롤할 수 있습니다.

허용 팀이 []이면 API는 AI를 호출하지 않습니다. 후보가 모두 제외되면 LLM 호출 없이 빈 결과를 반환합니다. 내부 SSE도 검증 후 토큰을 전달합니다.

  4. AI 검색 서비스 → LightRAG 저장소: ④ 허용 팀 또는 전역에서 후보 검색
  5. LightRAG 저장소 → AI 검색 서비스: ⑤ 후보 출처에서 업무 ID 추출
  6. AI 검색 서비스 → LightRAG 저장소: ⑥ 전역 processed + COMPLETED 확인
  7. AI 검색 서비스 → 업무 DB: ⑦ 현재 업무·팀·삭제 여부·허용 범위 확인

  9. AI 검색 서비스 → LightRAG 저장소: ⑨ indexed_team_id·팀 processed·전역 완료 재확인

  11. LLM → AI 검색 서비스: ⑪ 답변 반환

예시로 따라가기 · 재고 조회 API 개선 검색

업무 1001은 팀 101, 업무 2002는 팀 202 소속이라고 가정합니다. 가상 예시이며 실제 모델 응답을 고정하지 않습니다.

  1. API는 사용자의 가시성으로 allowed_team_ids를 계산합니다. [101]이면 팀 101만 검색하고, null이면 전역에서 검색합니다. []이면 사용자 API는 AI를 호출하지 않습니다.
  2. LightRAG는 답변이 아니라 후보 ID를 찾습니다. 전사·팀 모두 공통 전역 processed+COMPLETED를 요구합니다.
  3. 업무 DB에서 현재 생존·팀을 읽고 색인 당시 소유권·현재 팀 native processed·전역 완료 재확인을 수행합니다. 업무 1001이 삭제·이동·미완료 상태면 답변 문맥에서 제외합니다.
  4. 통과한 현재 DB 본문·태그·작성자·팀·검증된 직접 선행 관계로 문맥을 구성해 답변합니다. 직접 선행 업무도 별도로 같은 공개·권한 검증을 거치며 허용된 경우 references에 포함될 수 있습니다. 일반 JSON과 내부 SSE 모두 같은 검증을 거칩니다.

전사·팀 모두 응답 캐시는 임시 비활성화입니다. no_results만 정상 빈 결과이며 다른 failure는 오류로 보고합니다. SSE는 검증 전 토큰을 내보내지 않지만, 이후 동시 삭제를 매 토큰 재검증하거나 이미 전송한 토큰을 회수하지 않습니다.

직접 선행 업무 후보가 100개를 초과하거나 확정 관계 문맥이 12,000자를 초과하면 빈 결과가 아니라 오류입니다. 내부 query/stream SSE는 사용자 REST 검색의 프록시가 아닙니다. SSE 문맥 검색·생성 시작·토큰 수신에는 전체 시간 제한을 적용합니다.

DB 튜플 구조: 무엇이 한 행인가?

튜플은 테이블의 한 행입니다. 업무 1001을 예로 들며, 아래 열은 흐름을 이해하는 데 필요한 주요 열입니다. 전체 열 목록은 연결된 DDL을 확인하세요.

업무 DB · 원본
tb_worklog의 한 행은 업무일지 하나입니다. 업무 내용과 최신 색인 요청 상태를 보관합니다.
↓ 업무 ID로 연결
업무 DB · 전달할 작업
일반 AI 요청·등록 결과 집계: tb_worklog_ai_post_process_outbox
등록·수정·삭제 색인: tb_worklog_light_outbox
각 테이블에서 worklog_id가 기본키이므로 업무당 각 테이블에 최대 한 행입니다.
↓ AI가 원본을 읽고 색인
LightRAG 전용 PostgreSQL · 색인 자료
workspace와 문서 ID로 전역·팀 자료를 구분합니다. 그래프는 Neo4j, 벡터는 Qdrant에 별도로 저장됩니다.

DB 변경 흐름: 한 업무를 끝까지 따라가기

아래는 이해를 위한 가상 행입니다. R1·R2·R3와 E1은 실제 UUID를 짧게 표시한 것입니다. 일부 열과 비동기 중간 단계는 생략했습니다.

1. 등록: 원본과 후처리 요청을 기록

① 등록 트랜잭션
tb_worklog: (worklog_id=1001, team_id=101, is_deleted=false,
  light_index_request_id=R1, light_index_execution_id=NULL, light_index_status=PENDING)
tb_worklog_ai_post_process_outbox: (worklog_id=1001, payload={...},
  completed_stages={}, pending_failed_stages={})
tb_worklog_light_outbox: (worklog_id=1001, operation=INDEX,
  revision=1, request_id=R1, terminal_failed=false)
↓ 후처리와 AI 색인 요청
② 실행 승인
tb_worklog: (..., light_index_request_id=R1,
  light_index_execution_id=E1, light_index_status=RUNNING)
현재 요청 ID를 확인한 뒤 실행 ID를 기록합니다.
↓ 전역·팀 색인 완료 후 결과 콜백
③ 결과 반영
tb_worklog: (..., light_index_status=COMPLETED, light_index_error=NULL,
  light_index_completed_at=결과 시각)
tb_worklog_light_outbox: 해당 R1 행 삭제
일반 AI Outbox: 일반 접수 결과와 최신 색인 상태를 집계
등록 Outbox는 다른 후처리 단계까지 완료되면 정리됩니다. 콜백은 현재 R1/E1과 RUNNING을 확인해야 반영됩니다.

2. 수정: 최신 요청으로 교체하고 재색인

① 색인 대상 내용 변경
tb_worklog: (worklog_id=1001, work_content=수정된 내용,
  light_index_request_id=R2, light_index_execution_id=NULL, light_index_status=PENDING)
tb_worklog_light_outbox: (worklog_id=1001, operation=REINDEX,
  revision=1, request_id=R2, attempts=0)
기존 Light Outbox 행이 있으면 revision을 올려 최신 요청으로 갱신합니다. 모든 수정이 재색인을 유발하는 것은 아닙니다.
↓ 선점 → AI 접수 → 결과 대기
② 처리 중
Outbox 선점: claim_token=토큰, lease_until=선점 만료 시각
접수 후: claim_token=NULL, lease_until=NULL, next_attempt_at=결과 대기 기한
접수는 완료가 아닙니다. 새 요청이 들어오면 이전 revision의 작업이 새 행을 완료 처리하지 못합니다.
↓ 현재 요청·실행의 성공 콜백
③ 성공
tb_worklog: (..., light_index_request_id=R2, light_index_status=COMPLETED)
tb_worklog_light_outbox: 해당 R2 행 삭제

3. 삭제: 원본 표시와 색인 정리는 별개

① 삭제 요청 트랜잭션
tb_worklog: (worklog_id=1001, is_deleted=true,
  light_index_request_id=R3, light_index_execution_id=NULL, light_index_status=PENDING)
tb_worklog_light_outbox: (worklog_id=1001, operation=DELETE,
  revision=1 또는 기존 revision+1, request_id=R3)
기존 REINDEX가 대기 중이어도 DELETE 의도가 우선합니다.
↓ 팀 색인부터 삭제 → 전역 색인 삭제
② 저장소 정리소유권으로 이전 팀을 찾고 팀·전역의 문서별 자료를 정리합니다. 공유 엔티티·관계는 다른 문서의 출처를 고려합니다. 일부 저장소 실패는 전체 원상 복구를 뜻하지 않습니다.
↓ 현재 요청·실행의 성공 콜백
③ 성공
tb_worklog: (worklog_id=1001, is_deleted=true, light_index_status=COMPLETED)
tb_worklog_light_outbox: 해당 R3 행 삭제
원본 행은 남고 검색에서 제외됩니다. 정리 실패 시 Outbox는 남아 재전달될 수 있습니다.

4. 실패와 늦게 도착한 결과

실패
tb_worklog: (..., light_index_status=FAILED, light_index_error=오류)
Light Outbox: (..., attempts 증가, last_error=오류,
  next_attempt_at=백오프 후 시각, claim_token=NULL, lease_until=NULL)
등록 후처리는 별도 복구 정책과 terminal_failed를 사용합니다.
↓ 이전 R1/E1 콜백이 R2 이후 도착
오래된 결과는 무시현재 요청 ID와 실행 ID 및 RUNNING 상태가 맞지 않으면 결과를 적용하지 않습니다. Outbox의 claim token·revision 검사도 별도로 작동합니다.

색인 저장소의 튜플과 데이터 흐름

같은 업무가 업무 DB, LightRAG PostgreSQL, Neo4j, Qdrant에 서로 다른 형태로 존재합니다. 이 저장소들은 하나의 DB 트랜잭션으로 묶이지 않습니다.

① 업무 DB에서 현재 원본 읽기
tb_worklog (1001, team_id=101, 제목, 본문, ...)
+ 태그 + 접근 가능한 선행 업무
↓ 문서 ID worklog-1001 · 출처 worklog://1001
② LightRAG PostgreSQL: 문서와 처리 상태
lightrag_doc_full: (workspace, id=worklog-1001, content, ...)
lightrag_doc_status: (workspace, id=worklog-1001, status, chunks_list,
  metadata={indexing_status: STAGING/COMPLETED, indexed_team_id: 101}, ...)
indexed_team_id는 전역 문서의 색인 당시 팀 소유권입니다. native 처리 상태와 metadata의 공개 게이트는 다른 값입니다. 예시는 workspace마다 metadata가 동일하다는 뜻이 아닙니다.
↓ 청크 분할 · 엔티티와 관계 추출
③ 본문과 출처 추적
lightrag_doc_chunks: (workspace, 청크 ID, 본문, 문서/캐시 연결, ...)
lightrag_full_entities / lightrag_full_relations: 문서별 엔티티·관계 목록
lightrag_entity_chunks / lightrag_relation_chunks: 엔티티·관계와 출처 청크 연결
lightrag_llm_cache: 추출 및 응답 캐시
위 값은 저장 데이터의 개념이며 SQL 전체 컬럼 정의는 아닙니다.
↓ 그래프·벡터 기록 및 전역/팀 완료 확인
④ Neo4j와 QdrantNeo4j에는 엔티티와 관계 그래프, Qdrant에는 검색용 벡터가 기록됩니다. 전역과 팀 workspace를 구분합니다. 완료 게이트가 열려야 검색 후보로 사용할 수 있습니다.
↓ 후보를 가져온 뒤 현재 원본 재검증
⑤ 검색 문맥 생성허용 팀, 전역 완료, 현재 업무·팀의 삭제 여부 및 색인 당시 팀 소유권을 확인합니다. 통과한 업무의 현재 DB 본문으로 답변 문맥을 만듭니다. 여러 저장소의 동일 시점 snapshot은 보장하지 않습니다.

LightRAG 라이브러리 테이블의 상세 열은 설치 버전과 DB를 확인해야 합니다. 예시 ID·팀·내용은 실제 데이터가 아닙니다.

근거: LightRAG PostgreSQL 저장·조회 의미, 수정·삭제 Outbox DDL, 등록 Outbox DDL, 색인 상태 DDL, 등록 복구 DDL, V24 Outbox 역할 분리. 전환 주의: V24는 두 Outbox 중 하나라도 행이 남아 있으면 중단하며 자동 삭제하지 않습니다. 기존 작업의 처리·폐기는 배포 전에 별도로 결정해야 합니다.
