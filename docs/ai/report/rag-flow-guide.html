등록 흐름

원본 + 등록 Outbox 커밋 → 워커 선점 → AI 직접 색인 → 성공 기록·재시도

등록 전용 Outboxtb_worklog_ai_post_process_outbox에 입력과 성공 단계를 보존합니다. 성공한 색인은 자동 재시도에서 반복하지 않습니다.

색인 경로만 표시다른 등록 후처리와 추가 요청 상세는 생략했습니다. 실제 제품 동작은 변경하지 않았습니다.

전체 결과로 완료 판정색인 성공은 해당 단계의 성공 기록입니다. Outbox 제거와 결과 알림은 전체 등록 후처리 결과를 기준으로 처리합니다.

예시로 따라가기 · 업무일지 1001 등록

가상 데이터 · 독립 시나리오 각 탭은 별개의 시작 상태를 가정합니다. 실제 API 호출이나 DB 변경은 실행하지 않습니다.

등록 입력: 팀 101, 제목 “재고 조회 API 개선”, 본문 “재고 조회 API의 응답 구조를 정리했다.” 등록 후 발급된 업무일지 ID를 1001로 가정합니다.

  1. 업무 DB + 등록 Outbox: 새 업무일지 1001과 등록 후처리 작업을 같은 트랜잭션에 기록합니다. 저장이 함께 커밋되면 사용자는 등록 응답을 받으며, AI 완료까지 기다리지 않습니다.
  2. 워커 → 전역 색인: 워커가 작업을 선점하고 AI에 1001 색인을 요청합니다. AI는 최신 업무 DB 원본을 읽어 전역 본문을 색인하고 processed를 확인한 뒤 확정 KG를 반영합니다. 문서·청크는 PG, 벡터는 Qdrant, 그래프는 Neo4j에 반영됩니다.
  3. 색인 당시 팀 기록 → 팀 사본: 전역 PG doc-status에 metadata.indexed_team_id=101을 기록한 뒤 팀 101 workspace에도 본문·KG를 반영합니다. 이 값은 업무 원문 snapshot이 아니라 이후 삭제에 필요한 팀 소유권입니다.
  4. 결과: 전역·팀 색인이 성공하면 indexed=true 결과와 검색 캐시 버전 갱신을 반영합니다. API는 성공 단계를 기록하고, 나머지 등록 후처리까지 완료됐는지 확인해 작업 완료·알림을 처리합니다.

중간 실패라면? 팀 색인에서 실패해도 앞서 반영된 전역 데이터가 자동 롤백되지는 않습니다. 실패 단계는 재시도 대상이며, 색인 단계의 성공과 등록 후처리 전체의 완료는 구분합니다.

수정 흐름

DB 수정 + Outbox 기록 → 워커 선점 → AI에서 기존 문서 삭제·재색인 → 완료·재시도

예시로 따라가기 · 업무일지 1001 본문 수정

가상 데이터 · 독립 시나리오 업무일지 1001이 팀 101에 이미 저장·색인된 상태에서 시작합니다. 다른 탭의 예시를 먼저 실행할 필요는 없습니다.

변경 전 → 후: 제목은 “재고 조회 API 개선” 그대로, 본문은 “재고 조회 API의 응답 구조를 정리했다.” → “페이지 단위 조회와 응답 필드를 정리했다.”로 바꿉니다.

  1. 업무 DB 수정 + REINDEX: 본문이 색인 입력이므로 업무 DB를 수정하면서 재색인 Outbox를 기록합니다. 커밋 후 사용자에게 수정 결과를 먼저 응답합니다.
  2. 기존 색인 정리: AI는 업무 1001의 변경 락 W를 유지하면서 PG metadata의 indexed_team_id=101을 확인합니다. 기존 팀 101 문서를 먼저 지우고 전역 문서를 지우며, 삭제 오류와 레코드 잔존을 확인합니다.
  3. 최신 본문으로 다시 색인: 삭제에 성공한 문서만 업무 DB에서 다시 읽습니다. 바뀐 본문으로 전역 본문·KG를 만들고 팀 소유권과 팀 사본을 다시 반영합니다.
  4. 결과: 색인 성공 결과를 받은 API가 해당 Outbox 작업을 완료 처리하고, 검색 캐시 버전도 갱신됩니다. 이후 팀 검색의 현재 원문에는 “페이지 단위 조회와 응답 필드를 정리했다.”가 사용됩니다.

팀 문서 삭제가 실패하면? 해당 문서의 전역 소유권을 보존하고 삽입을 중단해 재시도합니다. 업무 DB 수정까지 되돌리거나 이미 삭제한 이전 색인을 자동 복원하는 흐름은 아닙니다.

삭제 흐름

DB 소프트 삭제 + Outbox 기록 → 워커 선점 → AI에서 팀·전역 문서 삭제 → 완료·재시도

예시로 따라가기 · 업무일지 1001 삭제

가상 데이터 · 독립 시나리오 “재고 조회 API 개선” 업무일지 1001이 팀 101의 전역·팀 workspace에 색인돼 있다고 가정합니다. 다른 탭의 등록·수정 예시와 독립적입니다.

  1. 업무 DB 소프트 삭제 + DELETE: 업무 원본을 소프트 삭제하면서 삭제 Outbox를 같은 트랜잭션에 기록합니다. 사용자 삭제 응답은 AI 저장소 정리의 완료를 뜻하지 않습니다.
  2. 원본 대신 저장된 소유권 확인: 원본이 이미 삭제됐더라도 전역 PG doc-status의 metadata.indexed_team_id=101로 색인 당시 팀을 찾습니다. 삭제된 업무의 현재 원문을 복원해서 읽는 단계가 아닙니다.
  3. 팀 먼저 → 전역 나중: 팀 101 workspace에서 1001을 지운 뒤 전역 workspace에서도 정리합니다. PG 삭제 오류를 전파하고 레코드 잔존을 검사하며, 벡터·그래프·문서 상태 정리 결과를 확인합니다.
  4. 결과: 삭제 성공 결과에 따라 캐시 버전을 갱신하고 API의 삭제 Outbox 작업을 완료 처리합니다. 삭제된 업무는 현재 업무 DB 재검증을 거치는 팀 검색 문맥에서도 제외됩니다.

팀 정리가 실패하면? 전역 소유권을 먼저 지우지 않고 실패를 반환해 재시도합니다. 여러 저장소에 걸친 삭제 전체가 하나의 트랜잭션으로 롤백되는 것은 아닙니다.

검색 흐름

허용 팀으로 사전 격리 · 전사 범위만 Redis 응답 캐시 사용

예시로 따라가기 · “재고 조회 API는 어떻게 개선했어?”

가상 데이터 · 독립 시나리오 검색할 업무는 아직 삭제되지 않은 상태입니다. 삭제 탭 예시의 다음 단계가 아닙니다. 아래 답변 문구는 실제 LLM 실행 결과가 아닌 설명용 예시입니다.

검색 대상: 업무일지 1001은 팀 101의 “재고 조회 API 개선”, 본문은 “재고 조회 API의 응답 구조를 정리했다.”입니다. 별도로 팀 202에는 업무일지 2002 “재고 장애 대응”이 있으며, 둘 다 processed 상태라고 가정합니다.

  1. 허용 범위 계산: API가 질문자의 가시성을 확인한 결과를 allowed_team_ids=[101]로 가정합니다. 팀 202는 허용 범위에 없으며, 팀 검색은 Redis 응답 캐시를 우회합니다.
  2. 후보 검색: 팀 101 workspace에서만 검색하고, 후보의 provenance로 업무일지 1001을 찾았다고 가정합니다. 같은 “재고” 주제라도 팀 202의 2002를 검색 문맥에 섞지 않습니다.
  3. 현재 상태 재검증: PG의 processed 상태와 업무 DB의 현재 원본을 확인합니다. 1001이 미삭제·팀 101 소속일 때만 현재 본문과 접근 가능한 선행업무를 답변 문맥에 넣습니다.
  4. 답변·참조: 허용 문맥으로 답변을 생성합니다. 설명용 답변은 “재고 조회 API의 응답 구조를 정리했습니다.”, 참조는 업무일지 1001입니다. API 사용자는 REST JSON 응답을 받습니다.

전사 검색이라면? 권한 계산 결과가 allowed_team_ids=null인 경우만 Redis exact → semantic 캐시를 확인합니다. 캐시 hit이면 답변·참조를 반환하고, miss이면 전역 LightRAG 검색을 진행합니다. 팀 202도 검색 대상이 될 수 있지만 반드시 결과에 포함되는 것은 아닙니다. 전사는 위 팀별 재검증 경로와 구분합니다.

빈 범위·오래된 후보라면? 허용 팀이 []이면 API는 AI를 호출하지 않으며 AI 내부도 빈 결과로 종료합니다. 팀 후보가 미완료이거나 현재 삭제·다른 팀 소속이면 문맥에서 제외합니다. 팀 검색 실패를 전사 검색으로 우회하지 않습니다.

그래프는 가로로 밀어서 볼 수 있습니다. 각 선의 화살표 방향을 따라 읽어주세요.

W는 업무 전체, S는 각 변경 단계W는 획득부터 해제까지 유지합니다. S는 해당 변경 단계마다 획득·해제합니다. 검색은 W·S를 사용하지 않으며 다중 저장소의 동일 시점 snapshot을 보장하지 않습니다.

AI 락은 프로세스 내부용W·S는 같은 이벤트 루프에서만 공유됩니다. 원본 DB의 @Version, Outbox의 선점·lease와는 다른 보호 장치입니다.

현재 구현의 실행·복구 경로인덱싱 설정 활성화 기준이며 운영 부하는 측정하지 않았습니다. 재색인 삭제 실패는 해당 문서의 삽입을 중단합니다. 이전 색인은 자동 복원하지 않습니다. PG 삭제 오류 전파·잔존 레코드 후조건을 확인하며 팀 삭제 실패 시 전역 소유권을 보존합니다.

PostgreSQL로 옮긴 책임PGKVStorage는 본문·청크·추출/응답 캐시·삭제 추적을, PGDocStatusStorage는 상태와 metadata를 저장합니다. 전역 doc_status.metadata.indexed_team_id만 색인 당시 팀 소유권으로 보존합니다. 앱 전용 원본 snapshot·schema marker는 저장하지 않습니다.

서로 다른 저장소Qdrant는 벡터, Neo4j는 그래프, 업무 원본 DB는 현재 업무 데이터, Redis는 검색 응답 캐시입니다. PG의 LightRAG 내부 캐시와 Redis 응답 캐시는 별개입니다. 전역·팀은 workspace로 구분합니다.

마이그레이션 · 최신성 한계JSON 일괄 이관이 아니라 새 workspace 전체 재색인으로 전환합니다. 팀 검색도 과거 색인과 최신 원문이 섞일 수 있으며 다중 SQL·저장소의 동일 시점 snapshot을 보장하지 않습니다.

팀 검색의 결과 범위허용 팀별 top_k 후보를 합치므로 전사 단일 검색의 global top-k와 같은 계약이 아닙니다. 현재 DB에서 소속·삭제 여부가 확인된 업무와 접근 가능한 선행업무만 문맥에 사용합니다.

사용자 REST ≠ 내부 SSE사용자는 GET /api/worklogs/search/semantic의 JSON 응답을 받습니다. AI 내부 POST /ai/light/worklogs-v4/query/stream SSE는 사용자 API 프록시가 없습니다. 검색·문맥 구성 완료 후 토큰 생성을 시작합니다.

전사 캐시 조건allowed_team_ids=null일 때만 Redis exact → semantic 조회·저장을 사용합니다. hit는 검색을 생략하며 팀 목록은 캐시를 우회합니다. 허용 팀이 비면 API는 AI를 호출하지 않으며, AI도 allowed_team_ids=[] 요청을 빈 결과로 즉시 반환합니다. 검색 자체는 W·S 락을 획득하지 않습니다.
