2026-10-24 · 1단계 안정화 반영 · 등록·수정·삭제·검색 현재 코드 기준

문서 안내: 설계·구현·테스트 종합 보고서 · 운영 인덱스 전환 절차

조회할 업무일지 작업 선택
업무 락 W공간 락 SOutbox별도 실행 / 결과 전달

등록 흐름

원본 + Outbox 커밋 → 201 응답 / 워커 → 문서 락 → STAGING·기존 정리 → 전역·팀 색인 → COMPLETED → 결과

업무 DB 상태와 LightRAG 공개 상태는 별개STAGING·COMPLETED는 전역 LightRAG doc-status의 metadata.indexing_status입니다. 업무 DB의 처리 상태나 native status=processed를 대체하지 않습니다.

W는 전체, S는 단계별W는 원본 조회부터 색인·보상 종료까지 유지합니다. S는 전역·팀 workspace마다 본문·KG·소유권·공개 상태 변경 단계별로 잡았다 풉니다. 팀 본문과 KG 전체를 한 번에 묶는 팀 ID 락이 아닙니다.

문서별 보상 · 기본 Redis 비의존보상은 workspace·문서 ID로 첫 쓰기 전에 등록합니다. 팀 삭제 실패 시 전역 소유권을 보존합니다. 기본 등록 색인 경로는 응답 캐시를 생성하거나 Redis 버전을 갱신하지 않습니다.

예시로 따라가기 · 업무일지 1001 등록

가상 예시: 업무일지 1001, 팀 101, 제목 “재고 조회 API 개선”. 실제 API 호출이나 DB 변경은 실행하지 않습니다.

  1. API 원본 + Outbox → 커밋 → 201: 원본·연관 정보와 등록 후처리 Outbox를 같은 트랜잭션에 저장합니다. 커밋 후 사용자에게 201 Created로 응답합니다. AI 완료는 기다리지 않습니다.
  2. 스케줄러 → AI 요청: 등록 Outbox 워커가 미완료 작업을 선점하고 색인 단계에서 AI에 업무 ID 1001을 보냅니다. 파일 요약 등 다른 후처리는 이 그림에서 생략했습니다.
  3. 문서 락 → 자료 준비: AI는 worklog:1001 락을 획득하고 현재 DB 본문·관계를 읽어 본문 문서와 Custom KG를 만듭니다. 문서별 빈 메모리 보상 목록을 생성합니다.
  4. 기존 공개 닫기 → 사본 정리: 색인 당시 팀 소유권을 확인하고 기존 전역 문서의 metadata.indexing_status=STAGING을 저장합니다. 신규 상태 레코드가 없으면 이 저장은 생략합니다. 이전 팀·현재 팀·전역의 잔존물을 정리합니다.
  5. 전역 보상 등록 → 전역 색인: 전역 문서 삭제 보상을 등록한 뒤 전역 본문을 색인하고 native processed를 확인합니다. 이어 Custom KG를 반영하고 metadata.indexed_team_id=101을 저장합니다. 각 변경은 전역 workspace 락 S를 별도로 획득·해제합니다.
  6. 팀 보상 등록 → 팀 색인: 팀 101의 문서 삭제 보상을 등록합니다. 팀 본문과 팀 내 Custom KG를 순서대로 반영하고, 각각 팀 workspace 락 S를 획득·해제합니다.
  7. 전역 COMPLETED → 락 해제 → 응답: 모든 색인이 성공하면 전역 문서에 metadata.indexing_status=COMPLETED를 저장하고 다시 읽어 확인합니다. W 해제 후 indexed=true를 반환합니다. 전사·팀 검색은 이 공통 완료 게이트와 현재 업무 DB 검증을 통과한 문서만 답변 문맥에 사용합니다.
  8. API 결과 기록: AI 문서별 결과를 검증해 성공 단계를 checkpoint합니다. 전체 후처리 결과로 완료 상태·알림·Outbox 정리 또는 실패·재시도를 처리합니다. 색인 성공과 전체 후처리 완료는 구분합니다.

중간 쓰기 실패: 등록된 보상을 역순으로 실행해 팀 → 전역 순으로 부분 색인을 삭제합니다. 팀 보상 삭제가 실패하면 전역 소유권을 지우지 않고 LIGHTRAG_COMPENSATION_FAILED로 보고합니다. 완료 게시를 시도했다면 먼저 STAGING으로 닫아야 하며 이 단계도 실패할 수 있습니다.

추적 정보 복구: 상태 쓰기 실패로 chunks_list가 부족하면 메모리에 보관한 청크·상태를 이용해 STAGING 추적 정보를 저장하고 검증한 뒤 삭제합니다. 복구 실패를 성공으로 숨기지 않습니다.

한계: 보상·추적 정보는 메모리이며 서버 강제 종료 후 자동 재개는 미구현입니다. 락은 단일 프로세스용이고 재색인 중 검색 공백이 생길 수 있습니다. 검색 후보 자체를 제거하는 것이 아니라 완료·DB 검증에서 답변 문맥 사용을 차단합니다.

수정 흐름

DB + Outbox 커밋 → 원본 조회·공개 닫기·잔존물 정리 → 전역·팀 색인 → COMPLETED

예시로 따라가기 · 업무일지 1001 본문 수정

가상 예시: 팀 101의 업무 1001 본문을 “페이지 단위 조회와 응답 필드를 정리했다.”로 변경합니다.

  1. 업무 수정과 REINDEX Outbox를 같은 트랜잭션에 커밋하고 사용자는 먼저 응답받습니다.
  2. AI는 W를 잡은 뒤 최신 원본을 먼저 읽습니다. 전역의 기존 소유권을 확인하고 STAGING으로 공개를 닫은 다음 이전 팀·현재 팀·전역 잔존물을 정리합니다.
  3. 전역 보상 등록 → 전역 본문·KG → 소유권 → 팀 보상 등록 → 팀 본문·KG 순으로 처리합니다. 단계별 workspace 락 S를 사용합니다.
  4. 전체 성공 후 전역 COMPLETED를 저장·확인하고 W를 해제해 응답합니다. API는 성공 Outbox를 제거하고 실패는 재시도합니다. 기본 경로에서 Redis 응답 캐시 버전을 갱신하지 않습니다.

쓰기 실패는 등록과 같은 문서별 보상 경로를 사용합니다. 팀 삭제 실패 시 전역 소유권을 보존합니다. 원본이 이미 없으면 저장된 소유권으로 삭제를 시도하며, 원본도 소유권도 복구할 수 없으면 실패로 보고합니다. 이전 색인 자동 복원·검색 무공백은 보장하지 않습니다.

삭제 흐름

DB 소프트 삭제 + Outbox 기록 → 워커 선점 → AI에서 팀·전역 문서 삭제 → 완료·재시도

예시로 따라가기 · 업무일지 1001 삭제

가상 예시: 업무 1001이 전역·팀 101에 완료 상태로 색인되어 있습니다.

  1. API는 업무 DB is_deleted=true와 DELETE Outbox를 함께 커밋합니다. 사용자의 삭제 응답과 AI 저장소 삭제 완료는 별개입니다.
  2. AI는 문서 락 W를 잡고 기존 전역 문서를 STAGING으로 닫은 뒤 색인 당시 소유권 indexed_team_id=101을 확인합니다.
  3. 팀 101 사본을 먼저 지우고 전역 문서를 정리합니다. 각 변경은 workspace 락 S를 사용합니다. 팀 삭제 실패 시 전역 소유권을 지우지 않습니다.
  4. W를 해제해 ID별 deleted 결과를 반환합니다. API는 성공 Outbox를 완료하고 실패는 재시도합니다. 기본 삭제 경로는 응답 캐시 생성·버전 갱신을 하지 않습니다.

물리적 색인이 남아 있더라도 전사·팀 일반/SSE 검색은 현재 DB 생존 검증에서 삭제 문서를 제외합니다. 검증 직후의 동시 삭제나 이미 전송한 토큰의 철회까지 보장하지 않습니다.

검색 흐름

전사·팀 후보 검색 → 공통 COMPLETED·현재 DB·소유권 검증 → 일반/SSE 생성 · 응답 캐시 비활성

예시로 따라가기 · 재고 조회 API 개선 검색

업무 1001은 팀 101, 업무 2002는 팀 202 소속이라고 가정합니다. 가상 예시이며 실제 모델 응답을 고정하지 않습니다.

  1. API는 사용자의 가시성으로 allowed_team_ids를 계산합니다. [101]이면 팀 101만 검색하고, null이면 전역에서 검색합니다. []이면 사용자 API는 AI를 호출하지 않습니다.
  2. LightRAG는 답변이 아니라 후보 ID를 찾습니다. 전사·팀 모두 공통 전역 processed+COMPLETED를 요구합니다.
  3. 업무 DB에서 현재 생존·팀을 읽고 색인 당시 소유권·현재 팀 native processed·전역 완료 재확인을 수행합니다. 업무 1001이 삭제·이동·미완료 상태면 답변 문맥에서 제외합니다.
  4. 통과한 현재 DB 본문·태그·작성자·팀·검증된 선행 관계로 문맥을 구성해 답변합니다. 일반 JSON과 내부 SSE 모두 같은 검증을 거칩니다.

전사·팀 모두 응답 캐시는 임시 비활성화입니다. no_results만 정상 빈 결과이며 다른 failure는 오류로 보고합니다. SSE는 검증 전 토큰을 내보내지 않지만, 이후 동시 삭제를 매 토큰 재검증하거나 이미 전송한 토큰을 회수하지 않습니다.

내부 query/stream SSE는 사용자 REST 검색의 프록시가 아닙니다. SSE 문맥 검색·생성 시작·토큰 수신에는 전체 시간 제한을 적용합니다.

그래프는 가로로 밀어서 볼 수 있습니다. 각 선의 화살표 방향을 따라 읽어주세요.

W는 업무 전체, S는 각 변경 단계W는 획득부터 해제까지 유지합니다. S는 해당 변경 단계마다 획득·해제합니다. 검색은 W·S를 사용하지 않으며 다중 저장소의 동일 시점 snapshot을 보장하지 않습니다.

AI 락은 프로세스 내부용W·S는 같은 이벤트 루프에서만 공유됩니다. 원본 DB의 @Version, Outbox의 선점·lease와는 다른 보호 장치입니다.

현재 구현의 실행·복구 경로인덱싱 설정 활성화 기준이며 운영 부하는 측정하지 않았습니다. 재색인 삭제 실패는 해당 문서의 삽입을 중단합니다. 이전 색인은 자동 복원하지 않습니다. PG 삭제 오류 전파·잔존 레코드 후조건을 확인하며 팀 삭제 실패 시 전역 소유권을 보존합니다.

PostgreSQL로 옮긴 책임PGKVStorage는 본문·청크·추출/응답 캐시·삭제 추적을, PGDocStatusStorage는 상태와 metadata를 저장합니다. 전역 doc_status.metadata.indexed_team_id만 색인 당시 팀 소유권으로 보존합니다. 앱 전용 원본 snapshot·schema marker는 저장하지 않습니다.

서로 다른 저장소Qdrant는 벡터, Neo4j는 그래프, 업무 원본 DB는 현재 업무 데이터, Redis 응답 캐시는 현재 전사·팀 모두 비활성화입니다. PG의 LightRAG 내부 캐시와 Redis 응답 캐시는 별개입니다. 전역·팀은 workspace로 구분합니다.

마이그레이션 · 최신성 한계JSON 일괄 이관이 아니라 새 workspace 전체 재색인으로 전환합니다. 팀 검색도 과거 색인과 최신 원문이 섞일 수 있으며 다중 SQL·저장소의 동일 시점 snapshot을 보장하지 않습니다.

팀 검색의 결과 범위허용 팀별 top_k 후보를 합치므로 전사 단일 검색의 global top-k와 같은 계약이 아닙니다. 현재 DB에서 소속·삭제 여부가 확인된 업무와 접근 가능한 선행업무만 문맥에 사용합니다.

사용자 REST ≠ 내부 SSE사용자는 GET /api/worklogs/search/semantic의 JSON 응답을 받습니다. AI 내부 POST /ai/light/worklogs-v4/query/stream SSE는 사용자 API 프록시가 없습니다. 검색·문맥 구성 완료 후 토큰 생성을 시작합니다.

공통 검색 검증·응답 캐시 비활성전사·팀 모두 전역 COMPLETED, 현재 DB 생존·팀, 색인 소유권, 팀 processed를 검증합니다. 허용 팀이 비면 AI를 호출하지 않으며 AI 내부도 빈 결과로 반환합니다. 기본 색인·삭제는 Redis 응답 캐시를 생성·갱신하지 않습니다. 검색은 W/S 락을 사용하지 않습니다.
