01 / PROBLEMS

문제사항: 저장 성공과 검색 가능 상태가 분리되지 않았습니다

업무일지 하나를 전역·팀 workspace에 각각 본문과 KG로 저장합니다. 여러 저장소를 한 DB 트랜잭션으로 묶을 수 없어 중간 실패와 재전송을 별도로 처리해야 합니다.

문제원인·발생 조건영향
부분 색인 잔존전역 또는 팀의 본문·KG 중 일부만 성공. 기존 전체 삭제 경로는 전역에 팀 소유권이 기록됐다고 가정.소유권 기록 전 실패한 문서의 정리가 막히거나 다음 실행이 부분 문서를 건너뛸 위험.
배치 전체 실패 처리문서 여러 개의 작업을 묶어 처리하고 한 단계 실패를 대상 전체의 실패로 반환.성공 문서까지 재처리하게 되어 실패 단위와 재시도 단위가 맞지 않음.
완료 기준 부족native processed는 전역·팀의 본문·KG 전체 성공을 의미하지 않음.아직 작업 중인 문서가 답변 문맥에 들어갈 수 있음.
전사 답변의 DB 검증 우회LightRAG가 생성한 답변을 바로 사용. 캐시 적중도 현재 원본 확인을 우회할 수 있음.삭제된 업무 내용이 답변에 남음. 참조 링크만 제거해도 본문 노출은 해결되지 않음.
추적 상태 저장 실패 후 재시도 차단메모리의 청크 목록과 저장소의 chunks_list가 다르면 삭제를 거부.저장소 복구 뒤에도 같은 프로세스에서 반복 실패.
검색 실패 은폐모든 native status=failure를 결과 없음으로 취급.실제 장애도 정상적인 빈 응답처럼 보임.
캐시 비활성화 후 Redis 의존 잔존색인·삭제 후 불필요하게 응답 캐시 버전을 갱신.색인 변경이 성공했어도 Redis 오류로 호출이 실패할 수 있음.
02 / SOLUTION DESIGN

해결 설계: 문서별 복구 + 공통 완료 + 답변 전 DB 검증

A. 문서별 Saga 보상

문서와 팀 ID가 확보된 현재 실행에서 workspace × document_id 단위 삭제 작업을 첫 쓰기 전에 등록합니다. 실패하면 역순으로 팀 → 전역을 정리합니다.

과거 색인을 복원하는 롤백이 아니라 이번 부분 데이터를 제거하는 보상입니다. 보상 목록은 메모리입니다.

B. 전역 COMPLETED 공통 게이트

전역·팀 본문과 KG, 팀 소유권 기록이 모두 성공한 뒤 전역 메타데이터에 한 번 완료를 게시합니다. 전사·팀 검색이 같은 게이트를 사용합니다.

native status와 별도입니다. 팀 사본은 native processed를 확인하며 팀별 COMPLETED 게시를 따로 열지 않습니다.

C. 후보 검색과 답변 생성을 분리

LightRAG는 후보 ID를 찾습니다. 완료 상태·현재 DB 생존·허용 팀·색인 소유권·팀 처리 상태를 검증하고, 현재 DB 데이터로 답변 문맥을 구성합니다.

일반 응답과 SSE에 동일 적용. 검색 결과의 오래된 본문을 그대로 답변에 넣지 않습니다.

D. 안전 우선의 최소 운영 범위

답변 캐시는 임시 비활성화합니다. 단일 프로세스 메모리 락을 유지하고 분산 락 도입은 worker 확장 전 과제로 둡니다. 기존 인덱스는 별도 세대로 재구축합니다.

기존 문서에 COMPLETED를 일괄 추가해 불완전 데이터를 통과시키지 않습니다.

기존 API 구조와 이번 변경을 구분합니다. 업무 원본과 등록 Outbox를 같은 트랜잭션에 저장하는 API 구조는 이번 AI 안정화의 신규 구현이 아닙니다. 기존 연결을 포함해 실제 등록 경로가 정상 동작하는지 함께 검증했습니다.
03 / RESOLUTION METHOD

해결 방법: 실패를 정리하고, 완료를 확인하고, 사용 전에 다시 검증합니다

색인·보상 처리

  1. 문서 락과 잔존물 정리

    원본 조회부터 문서 락 W를 유지합니다. 기존 공개를 닫고 이전 팀·현재 팀·전역의 사본을 정리합니다. 중복 등록 요청이나 실패 후 재시도도 같은 경로를 사용합니다.

  2. 첫 쓰기 전 보상 등록

    전역 본문 전에 전역 보상, 팀 본문 전에 팀 보상을 등록합니다. 본문·KG마다 전체 문서 삭제를 중복 등록하지 않습니다.

  3. 모든 단계 후 완료 게시

    native 본문 processed와 KG 성공을 확인합니다. 전역 COMPLETED 저장 결과를 다시 읽습니다.

  4. 팀 → 전역 역순 정리

    팀 삭제 실패 시 전역 삭제를 멈춰 indexed_team_id를 보존합니다. 보상 실패는 COMPENSATION_FAILED로 반환합니다. 요청 취소와 보상을 분리하고 제한 시간 안에서 종료를 기다립니다.

추적 복구·검색 처리

  1. 추적 레코드 유실 보완

    상태 upsert 전에 청크 ID와 시도 레코드를 메모리에 보관합니다. 삭제 시 누락 목록을 합쳐 STAGING으로 저장하고 읽기 검증 후 native 삭제를 진행합니다.

  2. 후보와 현재 사실 분리

    전역 또는 허용 팀에서 후보 ID를 찾고, 전역 완료 → 업무 DB 생존·팀 → 색인 소유권 → 팀 processed → 전역 완료 재확인을 거칩니다.

  3. 검증된 DB 문맥으로 생성

    현재 본문·작성자·팀·태그·검증된 직접 선행 관계만 LLM에 전달합니다. SSE의 첫 토큰도 이 검증 이후에 나갑니다.

  4. 오류·캐시 경계 보완

    no_results만 정상 빈 결과로 처리하고 다른 failure는 오류로 전달합니다. 응답 캐시를 비활성화하고 기본 색인·삭제의 Redis 버전 갱신을 제거했습니다.

예외 경계: COMPLETED 저장은 성공했지만 응답만 유실됐고, 이어 STAGING으로 닫는 작업도 실패하면 완료 표시가 남을 수 있습니다. 이때 보상 실패를 보고하며 삭제를 강행하지 않습니다. 오류가 발생하면 언제나 즉시 비공개가 된다는 절대 보장은 아닙니다.
