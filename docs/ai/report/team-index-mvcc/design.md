## 1. 왜 하는가

업무일지를 등록하거나 수정하면 api가 업무 DB에 저장하고, AI 서버가 비동기로 LightRAG 색인을 만든다. LightRAG는 업무일지 하나를 Qdrant(벡터), Neo4j(그래프), PG KV(청크 원문, 문서 상태) 세 곳에 서로 다른 순간에 나눠 쓴다. 지금 구조의 문제는 다음과 같다.

1. **색인 중에는 세 저장소가 서로 어긋난다.** 그 상태에서 챗봇이 검색하면 반쯤 바뀐 데이터를 본다.
2. **수정 중에 챗봇에서 사라진다.** 재색인을 `STAGING → 옛 문서 삭제 → 새 문서 저장 → COMPLETED` 순서로 하므로 그동안 챗봇이 그 업무일지를 모른다. 실패하면 보상 삭제 뒤에도 옛 내용이 돌아오지 않는다.
3. **색인과 답변 내용이 어긋난다.** 챗봇은 LightRAG로 업무일지 번호만 찾고 본문은 업무 DB에서 최신으로 읽는다.
4. **워커 병렬화가 막혀 있다.** 업무일지 하나를 전사 공용 workspace와 팀 workspace 두 곳에 쓰는데, 전사 칸은 모든 팀이 같이 고치므로 팀별 락으로 병렬 처리할 수 없다.

LightRAG 공식 저장소와 1.4.10 코드에서 확인한 사실:
- 세 저장소를 하나의 트랜잭션으로 묶을 수 없다 (#3400). 조회 격리는 보장하지 않는다.
- 버전을 고려한 문서 수정 기능이 없다. 옛 버전과 새 버전이 같이 남으면 틀린 답이 나온다 (#3831, #2219, #3181).
- 청크 ID는 청크 내용의 해시다. 문서 삭제(`adelete_by_doc_id`)는 그 문서의 청크 목록을 통째로 지운다.
- 문서 삭제 중 공유 엔티티와 관계를 다시 만드는 데 실패해도 오류를 삼키고 `success`를 돌려주며 문서 기록까지 지운다. Codex가 메모리 저장소로 재현했다 (`operate.py` `rebuild_knowledge_from_chunks`, `lightrag.py` `adelete_by_doc_id`).
- LLM 추출 캐시 키는 프롬프트 해시이고 workspace를 포함하지 않는다. 같은 캐시 저장소를 공유하면 다른 workspace에서도 캐시를 그대로 쓴다. Codex가 사본 a에서 1회 추출, 사본 b에서 0회 추출을 확인했다.

전사 인덱스를 검색에 쓰는 사람은 DIRECTOR(`WorklogVisibilityScope.All`)뿐이다. 부서 총괄(`Department`)은 이미 소속 팀 인덱스 여러 개를 동시에 검색해 합친다.

## 2. 목표

- 재색인하는 동안에도 챗봇은 **완성된 인덱스만** 본다. 검색 단계(후보 선정, 순위, 결과 개수)와 답변 내용 모두 반쯤 쓴 데이터의 영향을 받지 않는다.
- 챗봇은 **기다리지 않는다.**
- 챗봇 답변 내용은 **검색한 인덱스와 같은 시점의 스냅샷**으로 만든다.
- 색인이 실패해도 그 업무일지는 **이전 내용으로 계속 보인다.** 새로 등록하다 실패한 업무일지는 성공할 때까지 안 보인다.
- 한 업무일지의 반복 실패가 **같은 팀의 다른 업무일지 색인을 막지 않는다.**
- 삭제한 업무일지는 **즉시** 답변에서 빠진다.
- 전사 인덱스를 없앤다. **모든 사람이 권한 범위의 팀 인덱스로만 검색한다.** DIRECTOR는 전체 팀을 검색한다.
- api의 자동 재시도(총 4회), 실패 알림, 작성자 수동 재시도는 **지금 그대로** 쓴다.

## 3. 하지 않는 것

- 색인 워커 병렬화(워커 여러 개). 이번 구조는 팀별 쓰기 락을 Redis로 만들기 때문에 나중에 워커만 늘리면 팀 단위로 병렬화된다.
- 한 질문이 여러 팀을 볼 때 팀들 사이의 시점을 하나로 맞추는 것. 팀마다 각자의 완성된 사본을 본다.
- 실제 DB MVCC처럼 버전을 여러 개 두는 것. 사본은 두 벌뿐이다 (8절).
- api 쪽 재시도, 알림, Outbox 구조 변경.

## 4. 이러면 실패다 (기능은 돌아가도)

- 챗봇이 쓰기 중인 사본을 읽는다.
- 업무일지가 빠지거나 망가진 사본이 읽기 사본으로 게시된다.
- 태그나 선행 업무만 바뀐 변경이 반영되지 않는다.
- 늦게 처리된 옛 요청이 최신 내용을 덮어쓴다.
- 한 업무일지가 계속 실패해서 같은 팀의 다른 색인이 전부 멈춘다.
- 팀을 옮긴 업무일지가 옛 팀 사람의 답변에 나오거나, 볼 수 있는 사람의 답변에서 사라진다.
- 삭제한 업무일지가 답변에 나온다.
- 두 쓰기 프로세스(워커와 스크립트)가 같은 팀 사본을 동시에 고친다.
- 색인 워커가 죽은 질문의 읽기 표시 때문에 영원히 기다린다.
- 포트폴리오 프로젝트 범위를 넘는 안전 장치가 늘어난다. 2026-11-12에 과한 예외 처리를 걷어내기로 했으므로, 위 실패만 막는다.

## 5. 제약

- 업무 DB의 `tb_worklog.version`은 업무일지 행이 바뀔 때만 오른다. **태그(`worklog_tag`)와 선행 업무는 다른 테이블이라 바뀌어도 `version`이 그대로다.** AI 태그 콜백(`InternalTagAiCallbackService.applyAiGeneratedTags`)은 새 태그를 연결하면 `REINDEX`를 요청하지만 업무일지 행은 바꾸지 않는다.
- LightRAG는 업무 DB와 분리된 PostgreSQL DB(`LIGHTRAG_PG_DSN`)를 쓴다. AI 서버 Alembic은 업무 DB 대상이다.
- 챗봇 조회는 FastAPI 프로세스, 색인은 Celery 워커 프로세스에서 돈다. 지금 락(`worklog_mutation_locks`)은 프로세스 안에서만 통한다. Redis(`settings.redis_url`)는 Celery 브로커로 이미 쓰고 있다.
- 시간 제한: 색인 작업 하나 300초(`worklog_light_index_timeout_seconds`), Celery 강제 종료 540초, LightRAG 쓰기 한 번 120초(`lightrag_insert_timeout_seconds`), 조회 300초(`lightrag_query_timeout_seconds`).
- 팀 workspace 이름은 `LightRagTeamScopeAdapter.adapter_for`가 `worklog_scope_v1_{hash}_team_{team_id}`로 만든다. 어댑터 초기화 때 모든 저장소의 workspace가 기대값과 같은지 검사한다(`_verify_storage_workspaces`).
- 챗봇 문맥은 LightRAG 검색 결과가 아니라 원본 행(`LightWorklogSourceRow`)으로 만든다(`_indexed_context_from_data`). LightRAG의 엔티티 설명은 프롬프트에 들어가지 않는다.
- 아직 운영 배포 전이다. 다만 로컬과 개발 환경에 쌓인 팀 인덱스는 다시 색인하는 비용을 피하려고 그대로 살린다.

## 6. 검토한 방식

| 방식 | 내용 | 판단 |
|---|---|---|
| 한 인덱스 + 버전 표로 검색 후 거르기 | v3, v4를 한 팀 칸에 같이 두고 결과를 버전 표로 거름 | 커밋 안 된 버전이 검색 상위 자리를 차지해 원래 결과를 밀어냄 |
| 한 인덱스 + 검색 전 가리기 | LightRAG 저장소 함수를 감싸 안 보일 항목을 빼고 검색 | 공유 엔티티의 설명과 벡터가 이미 새 버전으로 덮어써져 순위가 흔들림. LightRAG 내부 의존이 큼 |
| 팀 읽기/쓰기 락 | 색인하는 동안 그 팀 검색을 막음 | 격리는 완벽하지만 챗봇이 수십 초에서 분 단위로 기다림 |
| 세대 전환 (팀 전체 새로 만들기 또는 복사) | 새 workspace에 팀 전체를 만들고 포인터 전환 | 수정 한 건마다 팀 전체 비용. 복사하려면 세 저장소 내부 구조 전체를 복제해야 함 |
| **두 벌 번갈아 쓰기** | 팀마다 사본 두 벌. 쓰기 사본에 반영 → 포인터 전환 | **채택.** 격리 완벽, 챗봇 대기 없음, 바뀐 업무일지만 다시 넣음, LightRAG를 원래 쓰던 대로 씀 |

## 7. 결정 사항

### 7-1. 팀 사본 두 벌

- 팀마다 사본 `a`, `b` 두 벌을 둔다. 각 사본은 LightRAG workspace 하나다.
- **사본 `a`의 workspace 이름은 지금 팀 workspace 이름 그대로**, 사본 `b`는 뒤에 `_b`를 붙인다. Codex가 이 이름이 Qdrant payload 필터, Neo4j workspace 라벨, PG workspace 칸 분리와 충돌하지 않음을 확인했다.
- 각 사본 안에서는 업무일지마다 한 내용만 있다. LightRAG 문서 ID는 지금처럼 `worklog-{id}`다.
- 한 시점에 하나는 **읽기 사본**(챗봇이 읽음), 다른 하나는 **쓰기 사본**(색인 워커가 고침)이다.

### 7-2. 읽기 포인터 표 (LightRAG DB)

| 칸 | 내용 |
|---|---|
| 팀 ID | 기본 키 |
| 읽기 사본 | `a` 또는 `b` |
| 망가진 사본 | 없음, `a`, `b` 중 하나 (7-9) |

- 포인터 전환이 **커밋**이다. 전환은 **처음 읽은 값이 그대로일 때만** 한다: `UPDATE ... SET 읽기 사본 = :쓰기 WHERE 팀 = :팀 AND 읽기 사본 = :읽기`. 0건이면 다른 쓰기가 끼어든 것이므로 작업을 실패로 끝낸다.
- 행이 없는 팀은 읽기 사본 `a`로 본다.

### 7-3. 사본 내용 표 (LightRAG DB)

| 칸 | 내용 |
|---|---|
| 팀 ID, 사본, 업무일지 ID | 기본 키 |
| 상태 | `READY`(반영 완료) 또는 `WORKING`(반영 중이거나 반영이 끊김) |
| 지문 | 스냅샷의 해시 (태그, 선행 업무 순서를 정규화한 뒤 계산). `WORKING`이면 비움 |
| 스냅샷 | 반영할 때 쓴 `LightWorklogSourceRow` 전체 (JSON). `WORKING`이면 비움 |
| 삭제 전 기록 | `WORKING`일 때만: 삭제하기 전 그 문서의 청크 ID, 엔티티 이름, 관계 목록 (7-6). 프로세스가 죽어도 다음 작업이 확인에 쓴다 |

- 행이 없으면 그 사본에 그 업무일지가 없다는 뜻이다.
- **사본을 건드리기 전에 행을 먼저 `WORKING`으로 바꾸고, 성공해야 `READY`로 바꾼다.** 실패하거나 프로세스가 죽으면 `WORKING`이 남으므로 표가 실제를 속이지 않는다.
- 역할: (1) 챗봇 답변 내용(읽기 사본의 `READY` 스냅샷), (2) 두 사본 비교, (3) 어느 팀에 들어 있는지 기록(전사 `doc_status`의 완료 여부와 `indexed_team_id`를 대신함).
- **변경 여부는 버전 번호가 아니라 지문으로 판단한다.** 태그나 선행 업무만 바뀌어도 지문이 달라진다.

### 7-4. Redis 락 두 가지

| 락 | 키 단위 | 누가 | 동작 |
|---|---|---|---|
| 팀 쓰기 락 (배타) | 팀 | 색인 워커, 스크립트 | 한 팀의 쓰기는 한 번에 하나. 잡은 쪽이 작업하는 동안 **주기적으로 만료를 연장**한다. **사본에 반영 하나를 시작하기 전, 보상하기 전, 포인터를 바꾸기 전마다 소유를 확인**하고, 잃었으면 그 자리에서 멈춘다. 잡은 쪽이 죽으면 연장이 멈춰 만료 뒤 풀린다 |
| 사본 읽기 표시 (공유) | 팀 + 사본 | 챗봇 질문 | 질문마다 고유 토큰과 만료 시각을 등록한다. 여러 질문이 동시에 등록한다. 만료 시각이 지난 토큰은 없는 것으로 본다 |

- 읽기 토큰 만료 시각의 계산과 정리는 **Redis 서버 시계**(`TIME`, Lua 스크립트)로 한다. 프로세스마다 시계가 달라 살아 있는 토큰을 지우는 일을 막는다.
- 읽기 토큰 수명 = 조회 전체 기한 + 여유. 조회는 토큰 등록부터 문맥 생성까지 하나의 기한(`lightrag_query_timeout_seconds`) 안에서 끝낸다.
- 순서 규칙 두 가지를 지킨다: (1) 챗봇은 토큰 등록이 끝난 **뒤에** 포인터를 다시 읽는다. (2) 색인 워커는 포인터 전환이 커밋된 **뒤에** 옛 사본의 토큰 수를 센다.

### 7-5. 쓰기 흐름 (업무일지 하나, 팀 하나)

```text
팀 T의 쓰기 락을 잡는다 (작업 내내 연장)
  1. 읽기 사본 R, 쓰기 사본 W를 정한다 (포인터 기준)
  2. W를 읽는 질문이 없을 때까지 기다린다 (최대 대기 시간을 넘으면 실패로 끝냄 → api 자동 재시도)
  3. 청소
     - W가 망가짐 표시면 W를 R로 통째로 다시 만든다 (7-9)
     - 아니면 W와 R이 다른 업무일지를 모두 찾아 (지문이 다르거나, 한쪽에만 있거나, W가 WORKING),
       W를 R의 READY 스냅샷 상태로 되돌린다 (R에 없으면 W에서 지움)
     → 이제 W = R
  4. 업무 DB에서 이 업무일지의 현재 행을 다시 읽는다 (락 안에서)
     원하는 상태 = 현재 행이 있고 팀이 T면 그 행, 아니면 "없음"
  5. 건너뛰기: 원하는 상태의 지문 = R의 지문이면 끝 (재시도, 늦게 온 옛 요청, 중복)
              R의 행이 WORKING이면 지문이 비어 있으므로 "다름"으로 보고 건너뛰지 않음
  6. W에 반영 (7-6)
     실패하면 바로 보상: W의 이 업무일지를 R의 상태로 되돌리고 끝 (포인터 안 바꿈, 오류 응답 → api 자동 재시도)
  7. 소유 확인 후 포인터를 W로 바꾼다 (조건부 UPDATE)   ← 커밋
  8. 조회 캐시 버전을 올린다
쓰기 락을 푼다
```

- **옛 읽기 사본(R)은 이 작업에서 고치지 않는다.** 포인터 전환 뒤 R은 한 건 뒤처진 쓰기 사본이 되고, **다음 작업의 2, 3번**이 읽는 질문이 빠진 것을 확인한 뒤 맞춘다. 아무도 읽지 않으므로 뒤처져 있어도 챗봇에 영향이 없다.
- **늦게 온 옛 요청이 최신을 덮을 수 없다.** 4번에서 항상 락 안에서 업무 DB 최신 행을 읽기 때문이다. 요청에 실린 내용은 쓰지 않는다.
- **남의 실패는 되돌리기만 한다.** 3번 청소는 다른 업무일지의 `WORKING`을 R의 상태로 되돌릴 뿐 그 업무일지의 새 내용을 색인하지 않는다. 새 내용 반영은 그 업무일지 자신의 요청(첫 시도, 자동 재시도, 수동 재시도)만 한다. 그래서 한 업무일지의 반복 실패가 팀 전체를 막지 않는다. R의 내용은 이미 한 번 성공한 내용이라 LLM 캐시도 남아 있다.
- 6번의 보상이 끝까지 못 돌면(프로세스 종료, 강제 취소, 보상 실패) `WORKING`이 남고, 다음 작업의 3번이 같은 방식으로 되돌린다.

### 7-6. 사본에 반영하기

```text
1. 락 소유 확인
2. 삭제 전 기록을 읽는다: 그 문서의 청크 ID 목록, 엔티티 이름 목록, 관계 목록
   (LightRAG doc_status의 chunks_list, full_entities, full_relations)
   표의 행이 이미 WORKING이고 삭제 전 기록이 있으면 그것을 쓴다 (앞 작업이 삭제 직후 죽은 경우)
3. 표의 (T, W, 업무일지) 행을 WORKING + 삭제 전 기록으로 바꾼다
4. LightRAG 문서 삭제 (adelete_by_doc_id 기반 기존 delete_document)
5. 삭제 후 확인 (그래프만): 2번의 엔티티, 관계의 source_id가 2번 청크를 아직 가리키면 → W를 망가짐으로 표시하고 실패 (7-9)
   단, 같은 workspace의 다른 문서가 그 청크 ID를 쓰고 있으면 제외한다 (내용이 같은 청크는 ID가 같음)
6. 원하는 상태가 있으면 본문 문서와 custom KG를 넣는다 (선행 업무는 같은 팀 것만, 지금 index_source_rows 규칙)
7. 표 행을 READY + 지문 + 스냅샷으로 바꾸고 삭제 전 기록을 지운다. 원하는 상태가 "없음"이면 행을 지운다
```

- 반영은 "그 업무일지 문서를 지우고 원하는 상태로 다시 넣기"다. 몇 번을 다시 해도 결과가 같다.
- 삭제 후 확인은 **그래프만** 본다 (사용자 결정). 벡터 쪽 재구성 실패는 놓친다 (12절).

### 7-7. 팀이 여러 개 걸리는 경우

업무일지 하나의 색인 작업이 건드릴 팀 = {업무 DB의 현재 팀} ∪ {사본 내용 표에서 그 업무일지가 들어 있는 팀}.

- 현재 팀부터 처리한 뒤 나머지 팀을 처리한다(새 팀 등록 먼저, 옛 팀 삭제 나중). 팀 순서를 정할 때만 락 밖에서 업무 DB를 읽고, 내용은 각 팀 락 안에서 다시 읽는다(7-5 4번).
- 팀 쓰기 락은 한 번에 하나만 잡는다. 교착이 없다.
- 두 처리 사이에 잠깐 두 팀 모두에 들어 있을 수 있다. 챗봇은 업무 DB의 현재 팀으로 권한을 확인하므로 옛 팀 사람에게 보이지 않는다.

### 7-8. 챗봇 조회

```text
허용 팀마다:
  ① 읽기 포인터를 읽고 그 사본에 읽기 토큰을 등록한다
     등록한 뒤 포인터를 다시 읽어, 바뀌었으면 토큰을 지우고 새 사본으로 다시 등록한다
  ② 그 사본 workspace에서 LightRAG 검색 (기존 query_data, 가리기나 거르기 없음)
  ③ 결과에서 업무일지 번호를 뽑는다 (기존 _candidate_worklog_ids)
  ④ 그 사본의 READY 스냅샷을 (팀, 업무일지) 단위로 읽는다
모든 팀 결과를 모은다 (번호 하나로 합치지 않고 (팀, 업무일지) 단위로 유지)
  ⑤ 권한 확인 (업무 DB 최신): 삭제 안 됨, 현재 팀 = 그 스냅샷의 팀, 허용 팀 안
     → 업무일지마다 현재 팀과 같은 팀의 스냅샷 하나만 남긴다
  ⑥ 남은 스냅샷으로 LLM 문맥을 만든다. 직접 선행 업무도 같은 방식
  ⑦ 읽기 토큰을 지운다
  ⑧ LLM 답변 생성 (스트리밍 포함)
```

- **내용은 스냅샷, 볼 수 있는지는 업무 DB 최신**으로 나눈다.
- 사본을 읽는 일은 ⑥에서 끝난다. ⑧은 이미 만든 문맥으로 LLM만 부르므로 토큰을 들고 있지 않는다. 스트리밍이 끊겨도 토큰이 남지 않는다.
- 답변 생성(`complete_scoped`)은 전사 어댑터가 아니라 팀 사본 어댑터로 한다.

### 7-9. 망가진 사본 다시 만들기

LightRAG 삭제가 실패를 숨기는 경우(1절) 7-6 5번에서 발견한다. 그 사본은 쓰기 사본이라 아무도 읽지 않는다.

```text
1. 포인터 표에 "망가진 사본 = W"를 적는다   ← 비우기 전에 반드시 먼저
2. (다음 쓰기 작업 3번에서) W의 LightRAG 저장소를 비운다
   - llm_response_cache는 비우지 않는다 (사본 a, b가 공유. 내용 기반 키라 남겨도 무해)
   - 각 저장소 drop의 반환 결과를 확인한다. 하나라도 status가 success가 아니면 실패로 멈추고 망가짐 표시를 유지한다
     (LightRAG drop은 실패해도 예외 대신 {status: error}를 돌려준다)
3. 표의 W 행을 모두 지운다
4. R의 READY 스냅샷 전부를 W에 반영한다 (LLM은 공유 캐시, 비용은 임베딩)
5. 다 되면 "망가진 사본"을 비운다
```

- 다시 만드는 동안 그 팀의 쓰기 락을 잡고 있으므로 그 팀의 다른 색인 요청은 기다린다. 챗봇은 계속 R로 정상 동작한다.
- 큰 팀은 4번이 작업 기한(300초) 안에 끝나지 않을 수 있다 (12절 한계, 보류).

### 7-10. LLM 캐시 공유

- 사본 `b` 인스턴스의 `llm_response_cache`를 같은 팀 사본 `a`의 캐시 저장소로 바꿔 끼운다(지금 `ValidatedWorklogExtractionCache`로 감싸는 자리).
- 어댑터 초기화 검사(`_verify_storage_workspaces`)는 다른 모든 저장소에 대해 사본 workspace를 그대로 요구하고, **`llm_response_cache` 하나만** 명시적으로 지정한 같은 팀 사본 `a` workspace를 허용한다.
- custom KG 추적 코드도 `rag.llm_response_cache`에 쓰므로 공유 캐시에 쓴다. 키가 내용 기반이라 두 사본이 같은 값을 쓴다.

### 7-11. api 변경

- `LightRagWorklogSearchService.resolveAllowedTeamIds`에서 `All`도 `findVisibleTeamIds(scope)`로 전체 팀 목록을 보낸다.
- AI 서버의 `allowedTeamIds`는 `null`과 빈 목록을 받지 않는다.

### 7-12. 처음 전환 (초기화 스크립트)

> 전환 조건 확정 (사용자 결정, 2026-11-19). 처음 사본 두 벌을 만들 때 한 번만 적용한다. 평소 운영에는 이 조건이 필요 없다.

1. **전제: 업무 DB의 색인 Outbox(`tb_worklog_light_outbox`)에 처리 대기 중인 요청이 없어야 한다.** 스크립트가 직접 확인하고, 남아 있으면 거부한다. 그래야 "지금 팀 인덱스 내용 = 업무 DB 최신 내용"이 성립한다.
2. 색인 워커를 멈춘다.
3. 지금 팀 workspace를 사본 `a`로 쓴다. 읽기 포인터 = `a`.
4. 사본 `a`의 표를 채운다. 대상은 전사 `doc_status`가 `processed` + `COMPLETED`이고, `indexed_team_id`가 업무 DB 현재 팀과 같고, 그 팀 workspace `doc_status`도 `processed`이고, **Outbox에 행이 없는**(대기도 최종 실패도 아닌) 업무일지. 상태 `READY`, 스냅샷과 지문은 업무 DB 현재 행. Gemini 비용 없음.
5. 채운 뒤 Outbox를 다시 확인한다. 그사이 행이 생긴 업무일지는 사본 `a` 표에서 지운다. 이 업무일지들은 표에 없으므로 챗봇에 안 보이다가, 워커를 다시 띄운 뒤 대기 요청이 처리되면(최종 실패였던 것은 작성자 수동 재시도로) 보인다.
6. 팀마다 사본 `b`를 망가짐으로 표시하고 7-9로 채운다. LLM 캐시를 공유하므로 임베딩 비용만 든다.
7. 색인 워커를 다시 띄운다.
- 대기 요청 수는 `tb_worklog_light_outbox`에서 `terminal_failed`가 아닌 행 수로 센다. 완료된 요청은 Outbox에서 지워지고, 최종 실패는 `terminal_failed = true`로 남는다 (Codex 확인).
- 4번이 끝나면 챗봇은 바로 동작한다.

### 7-13. 기존 전사 인덱스 데이터

새 구조가 정상 동작하는 것을 확인한 뒤 별도 스크립트로 지운다. 실행은 사람이 한다. 팀 workspace(`worklog_scope_` 접두사)는 절대 건드리지 않는다.

### 7-14. 재구축 스크립트

`rebuild_light_worklogs_v4.py`를 단순화한다.

- **전제 (사용자 결정)**: 초기화와 같다. Outbox 대기 요청 0을 스크립트가 확인하고, 색인 워커를 멈춘 상태에서 실행한다. 재구축이 팀 락을 오래 잡는 동안 들어온 수정이 락 대기로 재시도를 다 써 버리는 것을 막기 위해서다.
- 팀마다:
  1. 쓰기 락을 잡고 쓰기 사본의 읽기 배출을 확인한다.
  2. 쓰기 사본을 망가짐으로 표시한 뒤 비운다 (7-9 2, 3번 규칙 그대로).
  3. 업무 DB의 그 팀 생존 업무일지를 전부 넣는다.
  4. 소유 확인 후 **포인터 전환과 반대쪽 망가짐 표시를 한 번의 UPDATE로** 한다.
  5. 이어서 반대쪽 사본도 같은 스크립트 안에서 7-9로 끝까지 다시 만든다 (두 번째 단계는 필수).
- 재구축 중에도 챗봇은 읽기 사본으로 정상 동작한다. 별도 target workspace, manifest 대조는 없앤다. Gemini 전송 승인 플래그(`--confirm-real-data-export`)는 남긴다.

## 8. 실제 MVCC와의 관계

이 설계는 실제 DB의 MVCC(버전을 필요한 만큼 쌓고 트랜잭션마다 스냅샷 시점을 고름)가 아니라 **섀도 페이징(더블 버퍼링)**이다. LMDB의 두 메타 페이지와 독자 표 구조와 같다.

| | 실제 MVCC | 이 설계 |
|---|---|---|
| 버전 수 | 필요한 만큼 | 최대 2개 |
| 읽기가 보는 것 | 자기 스냅샷 시점 | 항상 완성된 최신 |
| 쓰기가 읽기를 기다리나 | 안 기다림 | 쓰려는 사본을 읽는 옛 질문만 기다림 |

버전 하나가 행 하나가 아니라 팀 인덱스 전체(Qdrant, Neo4j, PG)라서 두 벌로 제한했다. 챗봇은 최신 완성본만 보면 되고, 쓰기는 팀마다 한 줄이며, 질문이 짧으므로 두 벌로 충분하다.

## 9. 완료 조건

- [ ] 쓰기 사본에 반영하는 도중 챗봇에 물으면, 검색과 답변 모두 읽기 사본 기준이다. 새 내용에만 있는 단어로는 그 업무일지가 검색되지 않는다
- [ ] 포인터 전환 후 새 질문은 새 내용으로 검색하고 답한다
- [ ] 포인터 전환 전에 시작한 질문은 옛 사본으로 끝까지 답하고, 그동안 어떤 작업도 그 사본을 고치지 않는다
- [ ] 반영 중 실패하거나 프로세스가 죽어도, 그 업무일지는 이전 내용으로 계속 보이고 빠진 사본이 게시되지 않는다
- [ ] 한 업무일지가 계속 실패해도 같은 팀의 다른 업무일지는 정상 색인된다
- [ ] AI 태그만 추가된 `REINDEX`가 반영되어 스냅샷과 인덱스에 태그가 들어간다
- [ ] 같은 업무일지의 요청이 순서가 뒤바뀌어 처리돼도 최종 사본은 업무 DB 최신 내용이다
- [ ] 팀을 옮긴 업무일지는 옛 팀 범위 답변에 나오지 않고, 두 팀을 다 보는 사람에게는 새 팀 것으로 나온다. 옛 팀의 읽기 사본에서는 바로 지워지고, 옛 팀의 다른 사본에서는 그 팀의 다음 쓰기 때 지워진다
- [ ] 업무일지를 삭제하면 AI 서버 삭제 작업이 끝나기 전이라도 답변에 나오지 않는다. 읽기 사본에서는 삭제 작업 때 지워지고, 다른 사본에서는 그 팀의 다음 쓰기 때 지워진다
- [ ] LightRAG 삭제가 공유 엔티티의 그래프 복구 실패를 숨겨도 그 사본은 게시되지 않고 다시 만들어진다. 삭제 직후 프로세스가 죽어도 다음 작업이 저장된 삭제 전 기록으로 확인한다
- [ ] 사본을 비워도 공유 LLM 캐시는 남는다. 저장소 비우기가 실패하면 망가짐 표시가 유지되고 게시되지 않는다
- [ ] 쓰기 락을 잡은 프로세스가 오래 걸려도 다른 프로세스가 같은 팀을 고치지 않고, 죽으면 만료 뒤 풀린다
- [ ] 읽기 토큰을 남긴 채 죽은 질문이 있어도 색인 워커는 만료 뒤 진행한다
- [ ] DIRECTOR 검색이 전체 팀 사본 검색으로 동작하고, 전사 인덱스를 읽거나 쓰는 코드가 없다
- [ ] 초기화 스크립트 실행 후 기존 업무일지가 챗봇 답변에 그대로 나오고, 사본 `b`를 채울 때 추출 LLM 호출이 캐시로 대체된다
- [ ] 관련 테스트를 새 구조에 맞게 고치고 통과한다. api 변경은 `api/AGENTS.md`의 주석/Javadoc 규칙을 지킨다

## 10. 빌더에게 맡기는 것

- 두 표의 테이블 이름, 칸 이름, 생성 방법 (첫 사용 때 `CREATE TABLE IF NOT EXISTS` 등).
- Redis 자료 구조 (쓰기 락은 `SET NX PX` + 토큰 비교 연장/삭제 Lua, 읽기 토큰은 만료 시각을 점수로 둔 정렬 집합 + `TIME` Lua).
- 락 연장 간격, 읽기 배출 최대 대기 시간 (작업 기한 300초 안에서), 배출 확인 간격.
- 지문 계산 방식 (기존 `rebuild_light_worklogs_v4.py`의 `source_fingerprint` 정규화 규칙을 옮겨 써도 된다).
- 사본 어댑터 캐시와 종료 처리 (팀 수 × 2개 LightRAG 인스턴스).
- 조회 캐시(`worklog_query_cache.py`)의 `None` 범위 처리 정리. 지금 `get_exact`, `get_semantic`, `put`은 호출하는 곳이 없다. 나중에 연결할 때는 질문 시작 시 읽은 캐시 버전으로 저장해야 한다.
- 테스트 구성과 파일 배치.

## 11. 확인이 필요한 것 (구현 초반에 테스트로)

1. 사본 `b`의 LLM 캐시 공유가 실제 PG 저장소에서도 동작하는지 (메모리 저장소로는 확인됨).
2. 7-6 4번의 삭제 후 확인이 LightRAG의 숨겨진 실패를 실제로 잡는지 (Codex 재현 시나리오: 공유 `Tag` 노드 복구 중 `upsert_node` 실패 주입).
3. 각 저장소 `drop`이 그 workspace 데이터만 지우는지 (사본 `a`와 다른 팀을 건드리지 않는지).
4. 팀 수 × 2개 LightRAG 인스턴스가 PG 연결 수와 메모리 안에서 감당되는지.
5. 전체 팀 수와 DIRECTOR 검색 응답 시간 (팀 수만큼 검색함). 이번에는 측정만 한다.
6. 팀 하나의 사본 다시 만들기에 걸리는 시간 (12절 2번 한계가 실제로 문제가 되는 팀 크기). 이번에는 측정만 한다.
