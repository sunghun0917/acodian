## 1. 개요 및 종합 요약 (Executive Summary)

물류 업무일지 질의응답 시스템의 검색·답변 품질과 지연시간을 평가한 기록입니다. **벤치마크 데이터 버전 V4와 구현 경로 `app.light.v4`는 서로 다른 개념**입니다. 9월 평가는 V4 데이터를 v3 기반 실행기로 평가했고, 10월 평가는 실제 v4 서비스의 전사 normal query 경로를 사용했습니다. Ragas 점수는 확정 정답률이 아니며, 구성 조건이 다른 실행 사이의 차이를 개별 변경의 인과 효과로 해석하지 않습니다.

### 최신 비교 요약 (2026-10-15)

- 같은 질문·기준답변 50개를 대응 비교했습니다. 이전 Reranker ON 대비 **Context Recall 0.6983 → 0.8617 (+16.33%p)**, **Answer Relevancy 0.8116 → 0.8961 (+8.45%p)**입니다.
- 반면 **Faithfulness 0.8717 → 0.7682 (−10.35%p)**로 하락했습니다. 관계 정보 회수와 구체적 답변에는 개선이 있지만 전체 품질이 일괄 향상됐다고 결론 내리지 않습니다.
- 관계 부재 6문항을 제외한 44문항에서도 Recall은 **+18.56%p**, Relevancy는 **+5.37%p**입니다. 전체 Relevancy 증가분의 약 44%는 부재 문항에서 발생했습니다.
- 평균 검색+생성 시간은 Reranker ON의 **106.01초 → 10.79초**지만 이번에는 Reranker가 OFF입니다. 이전 OFF 실행의 **2.65초**와 비교하면 오히려 느리므로 v4 자체의 속도 개선으로 주장하지 않습니다.
- 채점 오류 0건, 종료 입력 검증은 `source_changed`입니다. 아래 최신 비교는 시작 시점 코드에 한정됩니다.

### 기존 최적화 및 9월 평가 기록

아래 기록과 2~3절의 SSE 수치는 기존 문서에 적힌 과거 실험입니다. 원본 SSE 보고서가 현재 작업 트리에 없으며, 이번 50문항 normal query 실행에서 SSE/TTFT 개선을 재검증하지 않았습니다.
1. **체감 대기시간 70.5% 극적 단축 (8.3초 ➔ 2.45초 TTFT)**:
   - `asyncio.TaskGroup`을 통한 비동기 완전 병렬화로 백엔드 처리 시간을 **51.7% 단축 (8.3s ➔ 4.0s)**했습니다.
   - FastAPI `EventSourceResponse` 기반 SSE 스트리밍을 결합하여, 거대 컨텍스트(2.5만 자) 환경에서도 **첫 단어가 2.45초 만에 타이핑**되도록 구현했습니다.
2. **지식그래프 및 복합 의존관계 답변 품질의 획기적 향상**:
   - 관계 탐색에서 답변 생성에 실패하던 Naive RAG 대비, LightRAG Mix + Reranker는 답변 관련성(`Answer Relevancy`)을 **0.3015 ➔ 0.8496으로 대폭 도약**시켰습니다.
   - 복합 의존관계 폐포 탐색(`dependency_closure`)에서 Cross-Encoder Reranker 적용 후 관련성이 **+0.1104p 급상승 (0.6435 ➔ 0.7539)**했습니다.
3. **평가 범위 분리 (전체 50문항 / 부재 제외 44문항)**:
   - 일부 부재 답변이 회피형으로 판정되어 관련성 점수가 낮아지는 사례를 구분합니다. 44문항 집계는 추가 진단 지표이며, 부재 6문항의 점수를 삭제하거나 전체 50문항 평가를 대체하지 않습니다.

## 2. RAG 파이프라인 아키텍처 및 기존 병목 진단

LightRAG Mix 모드는 사용자 질문의 문맥을 복원하기 위해 지식그래프(Neo4j)와 벡터 DB(Qdrant)를 상호 교차 조회합니다.

```mermaid
flowchart TD
    subgraph Bottleneck ["기존 순차 파이프라인 (총 8.3초 대기)"]
        B0["질의 접수"] --> B1["임베딩 API 계산 (대기...)"]
        B1 --> B2["1. 로컬 노드 탐색 (Qdrant + Neo4j 순차 대기)"]
        B2 --> B3["2. 글로벌 엣지 탐색 (Qdrant + Neo4j 순차 대기)"]
        B3 --> B4["3. 벡터 청크 검색 (Qdrant 원문 순차 대기)"]
        B4 --> B5["4. LLM 전체 답변 완성 블로킹 (Gemini...)"]
        B5 --> B6["거대 JSON 일괄 전송 (8.3초 후 첫 글자 표시)"]
    end
```

### 기존 구조의 3대 핵심 병목
1. **직렬 I/O 대기 오버헤드**: 노드, 엣지, 청크 검색이 상호 독립적임에도 순차적으로 `await`되어 저장소 왕복 대기시간이 누적되었습니다.
2. **임베딩 계산의 병렬성 차단**: 질문을 벡터로 변환하는 임베딩 API 호출이 끝날 때까지 Neo4j 지식그래프 검색이 시작조차 하지 못하고 블로킹되었습니다.
3. **Non-Streaming 블로킹 UX**: LLM이 모든 문장을 디코딩할 때까지 HTTP 소켓을 닫아두어 사용자는 최대 8초 이상 로딩 스피너만 보며 대기해야 했습니다.

## 3. 처리 속도 최적화: `asyncio.TaskGroup` 병렬화 & SSE 스트리밍

### 3.1 `asyncio.TaskGroup` 기반 다중 저장소 완전 동시 출발
* **구조적 동시성(Structured Concurrency)**: Python 3.11의 `asyncio.TaskGroup`을 도입하여 태스크 수명주기를 안전하게 바인딩하고, 단 하나라도 예외 발생 시 다른 코루틴을 즉시 취소하는 Fail-Fast 체계를 구축했습니다.
* **완전 동시 출발 (Embedding Concurrency)**: 임베딩 생성과 키워드 기반 그래프 탐색의 의존성을 분리하여 노드, 엣지, 청크 3개 경로가 0초 시점에 동시에 네트워크 요청을 출발하도록 최적화했습니다.

### 3.2 FastAPI SSE(Server-Sent Events) 스트리밍 구현
* **`EventSourceResponse` 토큰 제너레이터**: Gemini LLM의 비동기 스트림 이터레이터를 감싸 실시간 토큰 조각을 SSE 이벤트 형식(`data: {"type": "content", "content": "..."}`)으로 브라우저에 연속 송출했습니다.
* **Nginx 리버스 프록시 버퍼링 최적화**: 중간 게이트웨이가 토큰 청크를 가두지 않고 즉시 플러시(Flush)하도록 `X-Accel-Buffering: no` 헤더 및 프록시 버퍼링 무효화 설정을 결합했습니다.
* **고아 코루틴(Orphan Coroutine) 방어**: 클라이언트가 탭을 닫거나 네트워크가 단절되었을 때 백그라운드에서 LLM 토큰이 계속 소모되는 문제를 방지하기 위해, 연결 단절 감지 시 즉시 생성 제너레이터를 안전하게 강제 종료하도록 설계했습니다.

## 5. 심층 엔지니어링 분석 및 인사이트

### 5.1 RAG의 진짜 병목: LLM 추론(35%) vs DB I/O(65%)
기존 SSE 프로파일링 대상 쿼리에서는 저장소 I/O 병목을 확인했습니다. 이 비율을 모든 구성과 최신 실행에 일반화하지 않습니다. 이번 v4 기록은 평균 검색 1.6840초 / 검색+생성 10.7933초로, 기존의 I/O 65% 가정을 그대로 적용할 수 없습니다.

### 5.2 부재 검증(`verified_absence`)의 Ragas 채점 결함 및 Main Overall 분리
* **현상**: 선행 업무가 없음을 확인하는 문항에서, 모델이 "등록된 선행 업무가 확인되지 않습니다"라고 정답을 서술했음에도 Ragas가 이를 회피형(`noncommittal=1`)으로 판정하여 코사인 유사도와 무관하게 **강제 0점 패널티**를 부여하는 결함이 발견되었습니다.
* **조치**: 전체 50문항, 부재 제외 44문항, 부재 6문항을 함께 보고합니다. 분리 집계가 점수를 보정하거나 신뢰성을 자동 확보하는 것은 아니며, 실제 관계 부재 정답은 별도 검증이 필요합니다.

### 5.3 Cross-Encoder Reranker의 품질 vs 연산 지연(Latency) 트레이드오프
* **품질**: 복합 의존관계 답변 관련성을 11.04%p 끌어올리며 품질 향상 효과는 탁월했습니다.
* **지연 시간**: 반면 CPU Docker 환경에서 53개 후보 청크를 순차 추론할 경우 건당 100초 수준의 지연이 발생했습니다.
* **해석 범위**: 당시 모델·후보 수·CPU 환경의 측정입니다. GPU 배포의 필요 여부나 대체 모델의 효과는 이 기록만으로 확정하지 않습니다. 이번 Reranker OFF 실행으로 Reranker 자체의 최적화를 검증한 것도 아닙니다.

## 6. 종합 결론 및 향후 운영 권장 사항

1. **품질 개선은 축별로 판단**:
   - 관계 근거 회수와 관련성 점수에는 개선이 있지만 근거 충실성은 하락했습니다. 긴 답변의 불필요한 추가 주장과 관계 경로/방향/집합 오류를 다음 검증 대상으로 구분합니다. 구현 완료나 구조화 정답률 향상으로 보고하지 않습니다.
2. **검색 미검출과 관계 부재를 구분**:
   - top-k 문맥에서 관계를 찾지 못했다는 이유만으로 등록된 관계가 없다고 단정하지 않습니다. 검증된 범위에서 부재를 확인한 경우와 현재 근거가 부족한 경우를 구분하며, 관련성 점수를 높이기 위한 단정적 프롬프트 변경은 피합니다.
3. **조건을 고정한 후 개별 효과 확인**:
   - 생성 모델·프롬프트·인덱스·캐시를 고정한 비교가 있어야 Reranker, 모델 분리, 구조화 추출 등의 개별 효과를 판단할 수 있습니다. 동일 실행의 부재 문항을 별도 집계하고 judge 1회 채점의 한계를 유지합니다.
4. **최신 코드 검증과 비용 경계 유지**:
   - 이번 점수는 시작 시점 코드의 결과입니다. 변경된 최신 코드는 별도 실행으로 평가해야 하며 기존 계약을 바꾸어 재개·병합하지 않습니다. 이번 문서 갱신에서는 유료 재평가·인덱스 재색인·운영 변경·커밋을 수행하지 않았습니다.
