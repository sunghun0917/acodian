# RAG 검색 품질과 평가 (RAGAS, 벤치마크, 응답 속도)

> **현재 상태:** 평가 완료, 기록 보존. 마지막 평가는 2026-10-15 (`app.light.v4` 실서비스 경로). 그 뒤 v3 코드는 삭제됐고, 9월의 다중 홉 계획과 관계 보완 실험은 v3 코드 기준이라 지금 코드에는 그대로 남아 있지 않다.
> **기간:** 2026-09-26 (V1) → 09-28 (V2) → 09-29 (V3) → 09-30 (V4 Reranker) → 10-15 (v4 서비스 평가)
> **한 줄 요약:** 업무일지 200건, 50~80문항으로 Naive RAG와 LightRAG Mix를 비교했다. 관계 질문에서는 Mix가 확실히 낫고, 응답 속도는 병렬화와 SSE로 첫 글자까지 8.3초 → 2.45초가 됐다. 단, 평가마다 조건이 달라 개별 변경의 효과를 따로 증명하지는 못했다.

---

## 1. 배경: 무엇이 문제였나

- 업무일지 질의응답에서 "업무 158의 선행 업무 작성자는?" 같은 **관계 질문**이 많다. 본문 검색(Naive)만으로는 이런 질문에 답하기 어렵다.
- LightRAG Mix(지식 그래프 Neo4j + 벡터 Qdrant)가 정말 나은지, 어떤 질문에서 나은지 **측정할 데이터가 없었다.**
- 응답이 느렸다. 저장소 3곳을 순서대로 조회하고, LLM 답변이 다 만들어질 때까지 화면이 비어 있었다(8.3초).

## 2. 목표와 완료 기준

- 같은 질문을 Naive와 Mix에 넣어 **질문 유형별로** 비교한다. 그래프가 낫다고 미리 가정하지 않는다.
- 평가 데이터(질문, 기준답변)는 검색 코퍼스에 넣지 않는다.
- 응답 지연을 줄이되, 전체 완료 시간과 첫 글자 시간(TTFT)을 구분해서 잰다.

## 4. 구현: 어떻게 동작하나

### 응답 속도 최적화
```text
[전] 임베딩 → 노드 탐색 → 엣지 탐색 → 청크 검색 → LLM 답변 전체 → 응답  (순차, 8.3초)
[후] 임베딩 / 노드 / 엣지 / 청크를 asyncio.TaskGroup으로 동시 출발
     → LLM 토큰을 SSE로 바로바로 전송
```
- **`asyncio.TaskGroup`**: 하나가 실패하면 나머지를 바로 취소한다(구조적 동시성).
- **SSE (`EventSourceResponse`)**: `data: {"type": "content", "content": "..."}` 형식으로 토큰을 보낸다.
- **Nginx**: `X-Accel-Buffering: no`로 프록시 버퍼링을 꺼야 토큰이 막히지 않는다.
- **연결 끊김 처리**: 사용자가 탭을 닫으면 생성을 멈춰서 LLM 토큰 낭비를 막는다.

### 평가 방식
- 지표: RAGAS의 Faithfulness(근거 충실도), Answer Relevancy(답변 관련성), Context Recall(근거 회수율). V2에서는 Chunk Precision, Factual F1도 봤다.
- 생성 모델 `gemini-3.5-flash-lite`(이후 `gemini-3.6-flash`), 채점 모델 `gemini-3.8-flash`, temperature 0.
- 문항별로 Naive와 Mix 실행 순서를 번갈아 바꿨다. 응답 캐시는 끔.
- 평가 데이터 무결성은 SHA-256 manifest와 검증 스크립트로 확인한다.

## 5. 결과와 검증

### 응답 속도 (최장 지연 질문 1개, 2.5만 자 문맥)
| 단계 | 전체 완료 | 첫 글자(TTFT) |
|---|---:|---:|
| 기존 | 8.30초 | 8.30초 |
| TaskGroup 병렬화 | 4.00초 (-51.7%) | 4.00초 |
| + SSE | 3.84초 | **2.45초 (-70.5%)** |

### 버전별 Naive vs Mix (부재 문항 제외 기준 Answer Relevancy)
| 평가 | Naive | Mix |
|---|---:|---:|
| V2 (72문항) | 0.27 | **0.90** |
| V3 (44문항) | 0.32 | **0.82** |
| V4 Mix (44문항) | 0.30 | **0.83** (Reranker ON 0.85) |

- **단순 사실 질문**은 둘 다 Recall 1.0. 차이가 거의 없고 V1에서는 오히려 Naive가 정밀도가 높았다.
- **관계 질문**에서는 Naive의 관련성이 0에 가까울 정도로 낮고 Mix가 확실히 낫다.

### v4 서비스 평가 (10-15, 50문항, 9-30 Reranker ON 대비)
| 지표 | 9-30 | 10-15 | 변화 |
|---|---:|---:|---:|
| Context Recall | 0.698 | 0.862 | +16.3%p |
| Answer Relevancy | 0.812 | 0.896 | +8.5%p |
| Faithfulness | 0.872 | 0.768 | **-10.4%p** |

- 직접 관계 Recall 0.67 → 1.00, 의존관계 폐포 0.49 → 0.76
- 하지만 **근거 충실도가 떨어졌다.** 평균 답변 길이가 153자 → 578자로 늘면서 근거 없는 추가 설명이 늘었을 가능성이 있다(확정 아님).
- 이 실행은 도중에 v4 소스 4개가 바뀌어 종료 검증이 `source_changed`로 실패했다. **시작 시점 코드 기준 결과**다.

## 6. 진행 중 발견한 문제와 바뀐 결정

| 시점 | 내용 |
|---|---|
| V1 | "Mix가 일괄적으로 낫다"는 확인되지 않음. 본문 질문은 Naive가 정밀도와 재현율이 약간 높았다 |
| V1 개선 | 관계 질문 근거 누락이 큰 문제 → DB 관계 보완으로 Recall 1.0. 단, 본문 질문의 Faithfulness는 약간 하락 |
| V2~V3 | **RAGAS 채점 결함 발견:** "선행 업무가 없습니다"라는 정답을 회피형(noncommittal)으로 판정해 관련성 0점. 그래서 전체 / 부재 제외 / 부재만 세 가지로 나눠 보고 |
| V3 | 질문에서 ID를 빼고 자연어로만 질문 |
| V4 | 작성자, 팀 질문의 기준답변에 ID를 병기하고 재채점 (예: 답변이 `User:15`처럼 ID로 답한 경우를 채점 기준과 맞추기 위한 것으로 보인다) |
| 09-30 | Reranker: 품질은 좋지만 CPU 지연 100초 → 서비스 평가에서 OFF |
| 다중 홉 | 처음에는 "선행 업무 → 팀" 2홉만 계획했다가, 작성자, 태그, 역방향, 분기까지 질문에 맞게 탐색하는 계획으로 확대 (v3 기준, 이후 v4 전환) |

## 7. 한계와 위험

- **같은 코퍼스로 튜닝하고 평가했다.** 독립 holdout이 없다. 일반화 성능을 주장할 수 없다.
- **채점 모델 1회 채점.** judge 자체의 오차와 편향이 있다.
- **Recall이 높다고 정답은 아니다.** 예: v4-034는 Recall이 양쪽 1.0인데 이전 답은 틀렸고 이번 답은 맞았다.
- **관련성 상승이 정답성 상승은 아니다.** 예: v4-039는 "관계가 없다"고 단정해서 관련성은 올랐지만 Faithfulness는 1.0 → 0.2.
- **검색에 안 나온 것 ≠ 관계가 없는 것.** top-k에 없다고 "없다"고 단정하지 않도록 해야 한다.
- **미평가:** 팀 권한 범위 검색, SSE 실측(v4), 운영 데이터, 정확한 비용.
- **보안:** 평가 SQL은 평가 전용 DB에만 쓴다. 합성 데이터의 연락처, 인증정보는 복사하지 않고 LLM에는 제목, 내용, 관계만 보낸다.

## 8. 앞으로 개선할 점

1. 모델, 프롬프트, 인덱스, 캐시를 고정한 통제 비교로 개별 변경 효과 확인
2. 답변 길이 제한이나 근거 인용 강제로 Faithfulness 회복
3. 독립 holdout 세트 구축
4. Reranker를 GPU나 더 가벼운 모델로 다시 측정
5. 최신 코드 기준 재평가 (10-15 결과는 시작 시점 코드 기준)

## 9. 스스로 점검 질문

- **Q. Naive RAG와 LightRAG Mix의 차이는?**
  A. Naive는 질문과 비슷한 본문 청크만 벡터로 찾는다. Mix는 엔티티와 관계를 지식 그래프에서 같이 찾아서 "A의 선행 업무의 작성자" 같은 연결 질문에 답할 수 있다.
- **Q. Faithfulness, Answer Relevancy, Context Recall은 각각 무엇을 보나?**
  A. Faithfulness는 답변이 검색 문맥에 근거하는지, Answer Relevancy는 답변이 질문에 맞는지, Context Recall은 정답에 필요한 근거가 검색됐는지를 본다.
- **Q. 왜 부재 문항을 따로 집계하나?**
  A. RAGAS가 "없습니다"라는 정답을 회피형으로 보고 0점을 주는 결함이 있었다. 섞으면 평균이 왜곡된다.
- **Q. TaskGroup 병렬화가 효과 있었던 이유는?**
  A. 노드, 엣지, 청크 검색이 서로 독립인데 순서대로 기다리고 있었다. 동시에 보내면 가장 느린 것 하나만 기다리면 된다.
- **Q. SSE로 전체 시간은 거의 그대로인데 왜 의미가 있나?**
  A. 사용자가 체감하는 건 첫 글자가 나오는 시간이다. 8.3초 빈 화면 대신 2.45초 뒤부터 글자가 나온다.
- **Q. 이 평가 결과로 말할 수 없는 것은?**
  A. "v4가 더 좋다", "Reranker 덕분이다" 같은 인과 주장. 조건이 여러 개 동시에 바뀌었기 때문이다.
