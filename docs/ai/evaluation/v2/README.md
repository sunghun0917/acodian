# V2: Naive RAG와 LightRAG Mix의 관계 검색 가치 평가

## 목적과 구성

같은 질문에 대해 **본문 사실 → 직접 관계 → 다중 관계**로 필요한 탐색이 복잡해질 때 Mix의 이점이 있는지 측정한다. 그래프 우위를 전제하거나 특정 구현에 맞춰 정답을 바꾸지 않는다. 총 **80문항**, 원천은 동결된 V1의 합성 업무일지 **200건·직접 선행관계 77개**이다.

| 분류 | 문항 수 | 세부 구성 | 주요 평가 기준 |
|:---|---:|:---|:---|
| 단순 사실 | 20 | 본문에 명시된 구체 사실 | 기준 사실 일치·근거 충실도 |
| 직접 관계 | 20 | 작성자 7 / 소속 팀 7 / 직접 선행업무 6 | 정답 ID·방향 일치 |
| 다중 관계 | 20 | 선행업무 작성자 7 / 팀 7 / 선행의 선행 6 | 최종 답·관계 경로 일치 |
| 전체 선행 탐색 | 12 | 모든 직·간접 선행업무, 최대 4단계 | 업무 ID 집합 Precision·Recall·F1·완전 일치 |
| 가까운 관계 부재 | 8 | 실제 존재하는 업무에 등록된 선행관계 없음 | 잘못된 관계 생성률 |

`hop_count`는 정답에 필요한 관계 수이다. 전체 선행 탐색에서는 가장 긴 경로의 깊이이다. `dependency_paths`는 업무 사이의 의존 경로만 기록하고 작성자·팀 연결은 `relation_evidence`에 기록한다.

## 질문 예시

- 단순 사실: 「WMS 로그 누락 보정 작업 진행」에서 수정 작업과 번갈아 수행한 활동은 무엇인가?
- 직접 관계: 제목과 시작 업무 ID로 지정한 업무의 작성자는 누구인가?
- 다중 관계: 그 업무의 직접 선행업무 제목과 각 선행업무의 소속 팀은 어디인가?
- 전체: 현재 200건 코퍼스에 등록된 모든 직·간접 선행업무를 빠짐없이 알려 달라.
- 부재: 실제 업무에 등록된 직접 선행업무가 있는지 물어본다. 정답은 빈 목록이다.

**부재 8문항은 답변 불가능 문항이 아니다.** 코퍼스 전체의 등록 관계를 확인하면 답할 수 있으므로 `answerable=true`, `answer_kind=verified_absence`다. 일반적인 정보 부족 거절과 혼합 채점하지 않는다. 전체 탐색과 부재는 전체 운영 DB가 아니라 **200개 업무로 제한한 유도 부분그래프** 기준이다.

## 기존 인덱스를 이용한 시스템 비교

| 실험군 | 기존 입력 | 해석 |
|:---|:---|:---|
| Naive | V1 본문 인덱스 | 기존 본문 검색 시스템 |
| LightRAG Mix | V1 본문 + 등록된 그래프 관계 인덱스 | 그래프를 추가한 시스템 |

새 코퍼스·동일 정보 텍스트·smoke 데이터셋은 만들지 않는다. 현재 인덱스를 그대로 사용할 평가 질문 80개만 준비한다. 실제 실행 전에는 인덱스가 원천 200건·77관계와 일치하는지 확인해야 한다. 이번 작업은 인덱스를 변경하거나 그 현재 상태를 실시간 검증하지 않는다.

**입력 정보량이 다른 시스템 수준 비교**이므로 그래프 구조만의 효과라고 주장하지 않는다. 본문에 작성자·팀 등이 자연스럽게 언급된 경우도 보존하며, 모든 관계 문제가 Naive에 불가능하다고 전제하지 않는다.

신규 질문은 제목과 **시작 업무 ID**로 대상을 식별한다. 기존 본문에 없는 작성일을 요구하지 않는다. 시작 ID는 조회할 대상을 지정하는 정보이지 선행업무·작성자·팀의 정답 ID를 제공하는 것이 아니다. 이 평가에서는 모호한 제목만으로 대상을 식별하는 능력을 별도로 평가하지 않는다.

## 파일과 실행

| 파일 | 사용처 |
|:---|:---|
| `benchmark-v2.jsonl` | 평가용 4필드: `id`, `category`, `question`, `reference`. **인덱싱 금지** |
| `validation-details.jsonl` | `id`로 연결하는 split·세부분류·구조화 정답·원천 근거. 질문·기준답변 중복 없음. **인덱싱 금지** |
| `manifest.json` | 원천/산출물 SHA-256·분포·topology·한계 |
| `build_benchmark.py` | 표준 라이브러리만 사용하는 재현 생성기 및 검증기 |
| `test_benchmark.py` | 순환·분기·정답 변조·누락·방향·split·유출 회귀 검사 |

```powershell
# 저장소 루트에서 실행. API·DB 연결·비용 발생 없음.
ai/.venv/Scripts/python.exe -B -X utf8 docs/ai/evaluation/v2/build_benchmark.py
ai/.venv/Scripts/python.exe -B -X utf8 docs/ai/evaluation/v2/build_benchmark.py --check
ai/.venv/Scripts/python.exe -B -X utf8 -m unittest discover -s docs/ai/evaluation/v2 -p 'test_*.py' -v
```

RAGAS 입력은 `question` → `user_input`, `reference` → `reference`, 실제 생성 답변 → `response`, 실제 모델에 제공한 검색 문맥 → `retrieved_contexts`로 연결한다. `validation-details.jsonl`의 정답 ID·근거 인용·경로를 검색 문맥에 주입하면 안 된다.

V1 `run_ragas.py`에 직접 넘기지 않고 신규 `run_evaluation.py`에서 필드를 매핑한다. RAGAS 채점은 연결했으며 `structured_gold`의 ID·방향·집합 결정적 비교는 아직 구현하지 않았다. 실행 명령과 제한은 아래 절을 참고한다.

## 정답 구조와 채점 주의

아래 상세 필드는 `validation-details.jsonl`에만 저장한다. 평가 파일과 `id`로 1:1 연결한다. 관계 질문은 업무 ID 및 요청한 작성자·팀 ID도 응답하도록 명시하며, 정답에도 ID를 병기한다. 같은 제목의 서로 다른 업무를 합쳐 채점하지 않는다.

- `root_worklog_id`: 질문의 시작 업무.
- `structured_gold.worklog_ids`: 반환해야 할 업무 집합. 작성자·팀 단일 질문에는 대상 업무를 포함한다.
- `structured_gold.author_ids/team_ids`: 기대 작성자·팀 ID. 최종 답의 이름도 원천 사전과 대조한다.
- `structured_gold.relations`: 중간 의존 경로 및 최종 팀·작성자 관계. 작성자/팀이 어느 업무에 속하는지 보존한다.
- `expected_worklog_ids`: 근거를 제공하는 업무 집합이며 **답 목록과 다를 수 있다**. 전체 선행업무 정답에 시작 업무를 포함시키면 안 된다.
- `evidence`는 검증 가능한 원문 인용, `relation_evidence`는 SQL의 확정 관계에서 파생한다.

RAGAS는 근거 충실도·답변 관련성 등 보조 지표로 쓰고, 관계 질문은 ID/방향/집합 채점을 우선 병행한다. 본문만 대상으로 한 Context Precision을 그래프 검색 정확도로 해석하지 않는다. 유형별 평균과 세부유형 평균을 먼저 보고 전체 점수로 관계 개선을 숨기지 않는다. 시간·토큰과 반복 채점 변동성도 기록한다.

## 분할 및 한계

- 의존관계의 **전체 weak connected component** 단위로 development/evaluation을 분리한다. 두 split의 근거 업무 ID는 겹치지 않는다. 팀·작성자 노드는 공통일 수 있다.
- 정확한 split/category 수치는 `manifest.json`을 기준으로 한다. split을 맞추기 위해 관계를 잘라내지 않는다.
- 단순사실 20개 중 **15개는 V1 문항 그대로 재사용**하고 5개는 원문에서 새로 작성했다. 신규 문항 중 유사한 화면·로그 질문은 운영 영향·잔여 리스크 질문으로 교체했다. `reused_v1_question_id`, `v1_exposed_worklog_ids`로 표시한다.
- 전체 원천은 V1에서 이미 인덱싱·평가한 합성 코퍼스다. 따라서 evaluation split은 **새로운 독립 코퍼스 holdout이 아니다**. 질문 재사용 여부와 무관하게 과거 노출이 있다.
- 같은 업무를 직접/다중 질문에 재사용한다. 문항들이 완전 독립인 80개 실험이라고 주장하지 말고, 통계적 비교 시 component/업무 단위 상관성을 고려한다.
- 실제 최대 깊이 4, 분기 노드 **0**, 순환 **0**이다. 분기·순환은 테스트용 작은 그래프에서만 검증하며 실제 평가 커버리지는 없다.
- 신규 질문의 제목+시작 업무 ID는 대상 식별용이다. 기존 V1 본문에 포함된 ID를 사용하고 작성일은 질문에서 제외한다.
- 원천에 등록된 작성자는 업무일지 작성자이지 별도 담당자라는 보장은 없다. 작성자와 담당자를 혼용하지 않는다.
- 권한/실시간 변경/운영 DB 전체 탐색은 이번 평가 범위 밖이다. 독립 사람 검수는 아직 수행하지 않았으며, 실제 모델 평가 결과는 실행별 보고서에서 확인한다.

## 관계 보완 OFF 전체 평가 실행

`run_evaluation.py`는 V2 80문항 × naive/mix = 160개 응답을 실행한다. 별도 smoke/limit 옵션은 없다. PostgreSQL 관계 보완·anchor 치환·추가 Neo4j 확장·reranker는 끄고 Mix 내장 그래프 검색은 유지한다. 기존 V1 실행기의 검색/생성/4지표를 재사용하고 FactualCorrectness F1을 추가한다.

```powershell
# 유료 모델 호출. ai/.env 사용, 기존 인덱스를 읽고 신규 결과 디렉터리에만 기록.
ai/.venv/Scripts/python.exe -B -X utf8 docs/ai/evaluation/v2/run_evaluation.py
# 중단 후 같은 명령: 성공 응답/점수 재사용, 누락/실패 항목만 재시도.
# API 키/SDK 초기화 없이 저장 결과만 재집계.
ai/.venv/Scripts/python.exe -B -X utf8 docs/ai/evaluation/v2/run_evaluation.py --report-only
```

기본 출력: `results-judge-gemini-3.8-flash-20260928/`. `run.json`에 코드·벤치마크·원천·로컬 인덱스·모델 설정 계약을 저장하며 변경 시 resume을 거부한다. `rows/`에 생성 직후 답변/실제 문맥을 저장하고 채점 후 점수를 추가한다. `report.md`는 유형별 평균·대응 차이·유효 n·오류·시간, `summary.json`은 완료 개수를 기록한다. 모델 과금 소진은 중단하고 성공 결과를 보존한다. 실패 점수는 null이며 평균에서 제외한다.

관계 부재 8문항은 답변 가능한 빈 목록 정답으로 별도 집계한다. 이 실행기는 RAGAS 5지표 평가이며 구조화 ID/경로/집합의 결정적 채점은 아직 구현하지 않았다. 메타데이터의 정답은 검색/생성에 전달하지 않는다. 외부 Neo4j/Qdrant 원천 일치 여부는 별도 preflight 증거가 필요하다. 실행기 구현 자체가 실제 평가 완료를 의미하지 않는다. 실행 전에 출력 디렉터리에 `index-preflight.json`을 준비하면 그 해시도 실행/resume 계약에 포함한다.

### 생성/평가 모델 분리

답변 생성은 `ai/.env`의 기존 LightRAG 모델을 유지하고, RAGAS 5지표 judge는 `gemini-3.8-flash`로 고정합니다. `run.json`과 보고서에 두 모델을 별도로 기록하며, 동일 모델 사용 또는 judge가 바뀐 결과의 resume을 거부합니다. 모델 계약이 달라진 경우 새 결과 폴더에서 전체 응답을 다시 생성·채점합니다.
