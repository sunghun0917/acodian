# LightRAG v4 1단계 인덱스 전환 절차

## 보장 범위

기존 검색 서비스를 유지하면서 **다른 workspace**에 새 인덱스를 만든다. 기존 인덱스에 `COMPLETED`를 일괄 추가하지 않는다. 재구축 CLI는 대상 세대만 색인·정리하고 manifest의 준비 여부를 기록하며, **라우팅 변경·업무 DB 동결·서비스 배포를 실행하지 않는다.**

이 절차는 최초 인덱스 전환을 위한 것이다. 평상시 delete-first 재색인 공백, 원본 변경의 revision/fencing, 서버 강제 종료 후 자동 보상 재개는 별도 과제다.

## 1. 실행 전 확인

- 구 서비스 이미지·설정·인덱스를 보존하고 정상 검색을 확인한다. 새 안정화 코드를 구 workspace에 먼저 배포하면 완료 표시 없는 기존 문서가 검색에서 빠질 수 있다.
- target은 비활성 전용 workspace여야 한다. `--active-workspace`는 실행 프로세스 설정의 `LIGHTRAG_WORKSPACE`와 일치해야 하며 target과 달라야 한다. working directory도 구 서비스와 분리한다.
- CLI는 별도 프로세스로 실행한다. 실행 중 기존 서비스의 전역 settings/env/singleton을 변경하지 않는다. PG/Qdrant/Neo4j의 workspace 격리와 환경 override가 target을 침범하지 않는지 확인한다.
- 각 workspace에 writer는 하나만 둔다. 기존 HTTP·Celery·CLI 중 누가 색인/삭제하는지도 확인한다. 구/신 writer가 서로 다른 workspace를 쓰는 병행 구축만 허용한다.
- 같은 target에는 같은 manifest 경로를 계속 사용한다. manifest에는 성공뿐 아니라 시도한 문서의 ID·팀·원본 지문이 있으므로 실패 문서가 나중에 삭제되더라도 target 정리를 재시도할 수 있다. manifest를 버리고 같은 target을 재사용하지 않는다.
- 새 인덱스 1세대의 추가 저장소 용량과 Gemini 비용을 확인한다. 아래 명령은 실제 원본을 외부 Gemini로 전송하므로 별도 명시적 실행 승인이 필요하다. 토큰/DSN 값은 터미널 기록이나 문서에 붙이지 않는다.

## 2. 비활성 인덱스 구축

`ai/`에서 실행한다. 예시 workspace 이름은 실제 활성 설정에 맞춘다.

```powershell
.\.venv\Scripts\python.exe -m app.util.rebuild_light_worklogs_v4 `
  --active-workspace axwms_pg_v1 `
  --target-workspace axwms_pg_phase1_20261024 `
  --working-dir .\data\lightrag-phase1-20261024 `
  --manifest .\data\lightrag-phase1-20261024-manifest.json `
  --batch-size 5 `
  --confirm-real-data-export
```

- 제목·요청·본문·작성자/팀 표시·태그·직접 선행 관계 전체의 지문을 남긴다. 순서가 의미 없는 태그/선행 관계는 정규화한다.
- manifest 지문과 실제 색인은 같은 고정 source batch를 사용한다. 구축이 끝나면 전체 현재 원본과 전역 COMPLETED·팀 native processed·소유권을 다시 대조한다.
- 이전 manifest에는 있지만 현재 원본에서 사라진 ID는 target의 확보된 팀 → 전역 순서로 정리한다. 팀 이동 시 이전 manifest 팀 사본도 정리한다. 실패는 `failures`에 남기고 ready를 차단한다.
- 원본 쓰기 동결을 선언하지 않은 일반 구축은 색인에 성공해도 `ready=false`, 종료 코드 **2**가 정상이다. 원본이 계속 바뀌는 동안 준비 완료를 선언하지 않기 때문이다.
- 다음 실행은 같은 target/manifest에 재구축·대조한다. 실패나 미완료 상태를 완료로 덧칠하지 않는다.

## 3. 최종 대조의 필수 운영 경계

색인 전달만 멈추면 마지막 대조 직후 원본이 바뀔 수 있으므로 충분하지 않다. 전환 준비를 승인할 담당자가 다음을 직접 확인해야 한다.

1. **검색은 구 서비스에서 유지**한다.
2. 업무일지 생성/수정/삭제, 팀 이동, 태그/선행 관계 변경과 source에 영향을 주는 팀·작성자 표시 변경을 동결한다. 관련 DB 직접 쓰기와 배치도 포함한다.
3. 진행 중 업무 DB 쓰기 트랜잭션을 완료/취소하고, 진행 중 구 인덱스 mutation 및 outbox 전달을 배출한다. 외부 요청에만 동결 안내를 띄우고 내부 batch는 계속 쓰는 상태를 허용하지 않는다.
4. 변경 의도가 유실되지 않도록 outbox를 보존하고, 새 대상 전환 후에만 전달을 재개할 수 있게 한다.
5. 그 상태를 유지한 채 위 명령에 **`--source-writes-frozen`**을 추가해 최종 재구축·대조한다.

`--source-writes-frozen`은 **실행자의 확인 선언**일 뿐 자동 잠금이나 동결 증거가 아니다. 도구는 운영 동결의 진위를 입증할 수 없다. 원본 쓰기를 재개하면 기존 ready 결과는 전환 승인 근거로 재사용하지 않고 다시 동결·대조한다.

## 4. manifest 판정

- 종료 코드 **0**: `ready=true`. 동결 확인 선언, 전체 원본 지문 일치, 실패 없음, 전역 완료·팀 상태·소유권 일치를 확인했다.
- 종료 코드 **2**: 구축/대조는 수행했지만 준비 조건이 부족하다. `blockers`를 확인하고 기존 검색을 유지한다.
- 종료 코드 **1** 또는 예외: 검증 실패다. 같은 manifest가 이전에 ready였어도 첫 DB 조회 전에 `ready=false`로 무효화한다. 대상 정리 실패는 복구 완료로 처리하지 않는다.
- manifest는 같은 디렉터리의 임시 파일을 원자적으로 교체한다. 본문이나 비밀 설정 대신 ID·팀·지문과 실패 분류만 기록한다.
- `ready=true`는 아래 HTTP/SSE 전환 검증을 대신하지 않는다. 실제 전환 전 기존 고정 질의의 결과와 팀 격리·삭제 차단도 별도로 확인한다.

## 5. 실제 전환 — 별도 운영 승인 필요

현재 저장소에서 API 내부 주소(`AI_WORKLOG_SEARCH_BASE_URL`, `AI_WORKLOG_LIGHT_INDEX_BASE_URL`)와 외부 Nginx `/ai/` 경로는 다르다. **외부 Nginx만 바꾸는 것으로 전환을 완료했다고 판단하면 안 된다.** 실제 환경이 내부 안정 주소의 LightRAG 경로 전환을 지원하지 않으면 먼저 그 라우팅을 마련한다.

1. 동결을 유지하고 새 서비스가 target 전역/팀 workspace를 사용함을 확인한다.
2. 구/신 서비스에서 같은 고정 질의를 실행한다. 일반/SSE, 전사/팀 범위, 삭제 문서, 팀 이동 문서를 확인한다. 새 인덱스가 미완료이면 전환하지 않는다.
3. 내부/외부 query·stream·index·delete 경로가 같은 새 세대로 향하도록 전환한다. 다른 summary/polish/pipeline 기능은 불필요하게 변경하지 않는다.
4. 기존 HTTP/SSE 연결은 구 인스턴스에서 끝까지 배출한다. 구 인스턴스를 먼저 종료하지 않는다.
5. 전환 전·중·후 고정 질의를 반복해 인덱스 교체로 인한 빈 결과/오류 0건을 확인한다. 삭제/권한 변경에 따른 정당한 제외와 구분해 기록한다.
6. 새 대상으로 outbox 전달을 재개하고 원본 쓰기 동결을 해제한다. 구 인덱스는 즉시 삭제하지 않는다.

## 6. 롤백

- **새 세대 쓰기 재개 전**: 동결을 유지한 상태에서 내부/외부 LightRAG 경로를 구 대상으로 되돌릴 수 있다. 구 코드에는 새 완료/DB 검증 보장이 없다는 점을 별도 위험으로 기록한다.
- **새 세대 쓰기 재개 후**: 구 세대가 뒤처질 수 있다. 단순 역전환하지 말고 차이 대조·보정, 삭제/권한 검증을 먼저 수행한다. 동결을 재확보할 수 없다면 무중단·무유실 롤백을 보장하지 않는다.
- target 구축 실패·대조 불일치·내부/외부 경로 혼용이 있으면 기존 서비스에서 검색을 계속하고 전환을 보류한다.

## 검증하지 않은 것

단위 테스트는 target 보호, 지문 정규화, 실패/원본 변경/상태 미완료의 ready 차단, manifest 재실행 정리를 검증한다. 운영 PG/Qdrant/Neo4j 실장애, 실제 라우팅 전환의 검색 연속성, SSE 배출, SIGKILL 복구는 실행하지 않았다. 이 문서와 readiness artifact만으로 무중단 전환 완료를 주장할 수 없다.
