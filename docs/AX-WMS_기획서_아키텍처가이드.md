# AX-WMS 통합 아키텍처 가이드

- 프로젝트: `S14P31S209`
- 문서 목적: AX-WMS의 미래 상태 기준 아키텍처를 설명하는 작업 기준 문서
- 대상 구조: `web` / `api` / `ai` / `nginx`
- 문서 상태: Markdown 작업 기준 문서

## 1. 문서 목적과 범위

이 문서는 AX-WMS의 목표 시스템 구조, 서비스 경계, 데이터 소유권, 주요 처리 흐름을 설명하는 아키텍처 기준 문서다.
핵심 목적은 다음과 같다.

- 구현 이전에 서비스 책임과 경계를 명확히 정한다.
- 조직/업무/AI 처리 모델을 하나의 미래 상태 기준으로 정리한다.
- 기존 문서의 오래된 기술 전제를 걷어내고, 이후 설계·개발·리뷰가 참조할 수 있는 Markdown 기준 문서를 만든다.

이 문서는 다음을 포함한다.

- 시스템 구성 요소와 역할
- 서비스 간 경계와 데이터 소유권
- 업무일지/첨부파일/AI 파이프라인의 주요 처리 흐름
- ERD 초안과 일치해야 하는 도메인 정책
- 목표 디렉터리 구조와 문서화 원칙

이 문서는 다음을 포함하지 않는다.

- 상세 API 라우트 목록
- `.env` 예시, 로컬 실행 명령, 배포 명령
- 실제 폴더 생성 지침
- 코드/스키마 변경 지침

## 2. 목표 시스템 요약

AX-WMS는 본부/사업부/팀 단위의 조직 운영과 업무일지 관리를 중심으로 동작하며, AI 기능은 요약/태그/청킹/임베딩/시맨틱 검색을 담당한다.

목표 시스템은 다음 네 개의 애플리케이션 역할로 구성한다.

| 영역 | 기술 | 역할 |
|---|---|---|
| `web` | Next.js | 사용자 UI, 화면 조합, 사용자 상호작용 진입점 |
| `api` | Spring Boot | 비즈니스 규칙, 인증/인가, 조직/업무/파일 메타데이터/알림의 기준 시스템 |
| `ai` | FastAPI | AI 파이프라인, 요약/태그/청킹/임베딩/시맨틱 검색 |
| `nginx` | Nginx | 외부 진입 게이트웨이, 라우팅, 보안 경계 |

핵심 원칙은 다음과 같다.

1. 비즈니스 데이터의 기준 저장과 규칙 집행은 `api`가 맡는다.
2. AI 생성 결과와 임베딩 처리는 `ai`가 맡지만, 비즈니스 진실원장은 `api`가 소유한다.
3. 외부 요청은 `nginx`를 통해 진입하고, 사용자는 `web`을 기본 접점으로 사용한다.
4. 이 문서는 현재 구현 상태가 아니라 목표 구조를 기준으로 한다.

## 3. 아키텍처 원칙

### 3.1 미래 상태 기준 우선

기존 문서의 세부 구현 묘사보다 현재 합의된 목표 구조를 우선한다. 시스템 설명은 `S14P31S209` 루트와 `web / api / ai / nginx` 역할 분리를 기준으로 통일한다.

### 3.2 비즈니스 데이터와 AI 처리의 분리

- `api`는 조직, 사용자, 팀, 업무일지, 첨부파일 메타데이터, 알림 등 운영 데이터의 기준 소유자다.
- `ai`는 요약/태그/청킹/임베딩/검색과 같은 AI 처리 책임을 갖는다.
- AI 결과가 비즈니스 데이터에 반영될 때는 비즈니스 서비스 경계를 존중해야 한다.

### 3.3 문서 친화성과 유지보수성

이 문서는 diff, 리뷰, 재작성, 후속 자동화를 고려한 Markdown 기준 문서다. 구현 세부보다 경계, 책임, 정책, 흐름을 우선 기술한다.

### 3.4 구조적 진실원 우선순위

아키텍처 설명의 기준은 다음 순서를 따른다.

1. `docs/ax-wms-erd-draft.sql`
2. 확정된 deep-interview / ralplan 산출물
3. 기존 `.docx`의 재사용 가능한 설명

즉, 오래된 운영 세부와 경로 예시는 기준이 아니며, 구조·정책·도메인 정합성이 우선이다.

## 4. 상위 구조와 배치 관점

### 4.1 고수준 구성

```text
사용자 브라우저
    ↓
  nginx
 ├─ web  (Next.js)
 ├─ api  (Spring Boot)
 └─ ai   (FastAPI)

공용/연계 인프라
- PostgreSQL: 비즈니스 데이터 저장
- pgvector: 임베딩 저장 및 벡터 검색
- Object Storage: 첨부파일 원본 저장
- Redis: 비동기 처리/캐시 지원 계층
- Neo4j: 선택적 그래프 확장 계층
```

### 4.2 서비스 책임 요약

| 서비스 | 핵심 책임 | 직접 소유하는 것 | 소유하지 않는 것 |
|---|---|---|---|
| `web` | 화면 렌더링, 사용자 입력 처리, 사용자 흐름 구성 | 프론트엔드 UI 상태 | 비즈니스 원본 데이터, 임베딩 저장 |
| `api` | 인증/인가, 조직/업무/파일 메타데이터/알림 규칙 집행 | PostgreSQL 기반 비즈니스 데이터와 업무 규칙 | 임베딩 생성/검색 엔진 자체 |
| `ai` | 요약, 태그, 청킹, 임베딩, 검색, 파일 분석 | 임베딩 생성/검색 처리, AI 파이프라인 상태 | 비즈니스 진실원장 전체 |
| `nginx` | 외부 진입점, 라우팅, 보안 경계 | 진입 경로 제어 | 업무 규칙, AI 처리 |

## 5. 서비스 경계와 데이터 소유권

### 5.1 `web` (Next.js)

`web`은 사용자 경험 계층이다.

- 로그인, 대시보드, 조직 조회, 업무일지 작성/조회, 검색 UI를 제공한다.
- 도메인 규칙을 직접 소유하지 않는다.
- 업무 생성/수정/조회는 `api` 또는 합의된 서비스 경계를 통해 수행한다.
- AI 검색이나 요약 결과 표시가 필요할 때도 직접 데이터베이스에 접근하지 않는다.

### 5.2 `api` (Spring Boot)

`api`는 AX-WMS의 핵심 비즈니스 서비스다.

- 인증/인가와 사용자 권한 판단을 담당한다.
- 부서, 팀, 사용자, 업무일지, 첨부파일 메타데이터, 알림의 기준 데이터를 관리한다.
- 업무 상태 전이, 열람 범위, 팀 소속 정책, 파일 소속 정책과 같은 비즈니스 규칙을 집행한다.
- AI 처리 결과가 비즈니스 데이터에 반영될 때 최종 소유권을 가진다.

### 5.3 `ai` (FastAPI)

`ai`는 AX-WMS의 AI 처리 전담 서비스다.

- 업무일지 요약과 메타 태그 생성을 수행한다.
- 텍스트/파일 기반 지능형 청킹과 임베딩 생성을 담당한다.
- 시맨틱 검색을 수행하며, 메타데이터 필터와 벡터 유사도를 결합한다.
- 필요 시 파일 분석, OCR, 검색 확장, 그래프 기반 보강 기능을 담당한다.

### 5.4 `nginx` (Nginx)

`nginx`는 외부 트래픽의 단일 게이트웨이다.

- 외부 요청을 `web`, `api`, `ai`에 적절히 분배한다.
- 보안 경계, 라우팅, 스트리밍 전달과 같은 게이트웨이 역할을 담당한다.
- 내부 서비스 구현 규칙은 소유하지 않는다.

## 6. 데이터 저장소와 소유권

| 저장소 | 주 용도 | 주 소유 서비스 | 비고 |
|---|---|---|---|
| PostgreSQL | 조직/사용자/팀/업무일지/파일 메타데이터/알림 | `api` | 운영 데이터의 기준 저장소 |
| pgvector | 업무일지/파일 임베딩 저장 및 유사도 검색 | `ai` | 검색 보조 저장소 |
| Object Storage | 첨부파일 원본 저장 | `api` 중심, `ai`가 읽기 연계 가능 | 파일 메타데이터와 분리 |
| Redis | 비동기 처리/캐시 보조 계층 | `api` + `ai` | 큐/캐시 용도는 서비스 경계에 맞춰 분리 |
| Neo4j | 선택적 그래프 확장 검색 | `ai` | 필요 시 도입하는 보강 계층 |

원칙적으로 비즈니스 데이터의 기준은 PostgreSQL이며, 검색용 임베딩이나 그래프 데이터는 보조 인덱스/확장 계층으로 취급한다.

## 7. 도메인 모델 정렬 원칙

본 문서는 `docs/ax-wms-erd-draft.sql`과 충돌하지 않아야 하며, 특히 다음 정책성 사실을 아키텍처 수준에서 유지해야 한다.

### 7.1 조직 구조

핵심 엔티티는 다음과 같다.

- `tb_department`: 부서
- `tb_team`: 팀(프로젝트 그룹)
- `tb_user`: 사용자
- `tb_user_team`: 사용자-팀 연결

아키텍처 관점에서 중요한 사실은 다음과 같다.

- 사용자는 여러 팀에 참여할 수 있다.
- 팀 대표자는 `tb_team.leader_id` 같은 별도 컬럼이 아니라 `tb_user_team.team_authority = LEADER` membership 으로 표현하며, `teamAuthority = LEADER`가 대표자 의미를 직접 가진다.
- 사용자는 자신의 주 소속 부서와 다른 부서의 팀에도 참여할 수 있다.
- 즉, `tb_user.department_id` 와 `tb_team.department_id` 일치 여부는 강제하지 않으며, 교차 부서 협업은 `tb_user_team` 연결로 표현한다.

### 7.2 업무일지와 상태 관리

핵심 엔티티는 다음과 같다.

- `tb_worklog`: 업무일지
- `tb_worklog_status_history`: 상태 변경 이력
- `tb_worklog_dependency`: 선행 업무 관계
- `tb_worklog_tag`: 업무일지-태그 연결

아키텍처 관점에서 중요한 사실은 다음과 같다.

- 업무일지는 작성자(`author_id`)와 수행 팀(`team_id`)에 귀속된다.
- 상태 이력은 별도 엔티티로 관리된다.
- 선행 업무 관계는 자기참조 연결 구조로 관리된다.
- 태그는 관리형 태그 풀과 연결되는 구조를 따른다.

### 7.3 첨부파일 정책

핵심 엔티티는 `tb_file`이다.

- 첨부파일은 업무일지에 직접 소속된다.
- 파일 연결은 별도 `tb_worklog_file` 중간 테이블이 아니라 `tb_file.worklog_id`로 표현한다.
- 파일 원본 저장과 파일 메타데이터 관리는 분리하되, 비즈니스 기준 데이터는 `api`가 관리한다.

### 7.4 임베딩과 검색 메타데이터

핵심 엔티티는 다음과 같다.

- `tb_worklog_embedding`
- `tb_file_embedding`

아키텍처 관점에서 중요한 사실은 다음과 같다.

- 임베딩은 원본 업무일지/파일과 연결된다.
- 검색 필터를 위해 작성자, 팀, 부서, 상태, 중요도, 태그 같은 메타데이터가 함께 관리된다.
- 임베딩 계층은 검색 성능과 의미 검색을 위한 보조 계층이며, 운영 데이터의 원본은 아니다.

## 8. 주요 처리 흐름

### 8.1 조직/사용자/팀 관리

기본 조직 관리 흐름은 다음과 같다.

1. 사용자는 `web`에서 조직 정보를 조회하거나 관리 작업을 수행한다.
2. 외부 요청은 `nginx`를 거쳐 `api`로 전달된다.
3. `api`는 권한, 부서/팀 제약, 조직 규칙을 검증한 뒤 PostgreSQL에 반영한다.
4. 결과는 다시 `web`에 반환된다.

이 흐름에서 `ai`는 직접 개입하지 않는다.

### 8.2 업무일지 등록 및 AI 후처리

업무일지 처리 흐름은 동기 저장과 비동기 AI 후처리로 분리한다.

1. `web`에서 업무일지를 생성/수정한다.
2. `api`가 업무일지 원본과 상태를 기준 저장소에 반영한다.
3. `api`는 AI 후처리가 필요한 이벤트를 `ai`에 전달한다.
4. `ai`는 요약, 태그, 청킹, 임베딩 생성을 수행한다.
5. 요약/태그/처리 상태처럼 비즈니스 데이터에 속하는 결과는 `api`의 경계를 통해 반영한다.
6. 임베딩은 `ai`가 검색 계층에 저장한다.

즉, 업무 원본은 `api`, AI 해석은 `ai`, 검색용 벡터 저장은 `ai`가 맡는다.

### 8.3 파일 업로드 및 파일 분석

파일 처리 흐름은 다음과 같다.

1. 사용자가 `web`에서 첨부파일을 업로드한다.
2. `api`는 파일 메타데이터와 업무일지 연계를 기록한다.
3. 파일 원본은 Object Storage에 저장한다.
4. 필요 시 `ai`가 파일 내용을 분석하고 요약/청킹/임베딩을 수행한다.
5. 파일 임베딩은 파일과 업무일지 양쪽에 추적 가능해야 한다.

### 8.4 시맨틱 검색

시맨틱 검색은 `ai` 중심으로 수행한다.

1. 사용자의 검색 요청은 서비스 경계를 통해 `ai`에 전달된다.
2. `ai`는 질의를 임베딩하고, 메타데이터 필터와 벡터 유사도를 결합해 결과를 찾는다.
3. 검색 결과는 원본 업무일지/파일로 역추적 가능해야 한다.
4. 역할, 부서, 팀 범위 같은 접근 제약은 비즈니스 권한 문맥과 충돌하지 않아야 한다.

### 8.5 알림과 대시보드

- 대시보드 집계는 비즈니스 기준 데이터에 기반해 `api`가 중심이 된다.
- 알림 역시 사용자 귀속 비즈니스 데이터로서 `api`가 기준 소유권을 가진다.
- AI 처리 상태나 후처리 결과는 대시보드/알림에 반영될 수 있으나, 기준 저장은 비즈니스 경계를 따른다.

## 9. 목표 디렉터리 구조

이 문서가 기준으로 삼는 목표 구조는 다음과 같다.

```text
S14P31S209/
├── web/      # Next.js 프론트엔드
├── api/      # Spring Boot 비즈니스 API
├── ai/       # FastAPI AI 서비스
├── nginx/    # Nginx 게이트웨이 및 배포 설정
└── docs/     # 프로젝트 문서
```

이 구조는 설명용 기준이며, 이 문서 자체가 실제 폴더 생성 지시를 의미하지는 않는다.

## 10. 문서화 원칙

이 가이드는 다음 규칙을 따른다.

- 구조와 책임을 먼저 설명하고, 세부 구현은 후속 설계 문서에서 다룬다.
- 현재 기준이 아닌 운영 상세는 포함하지 않는다.
- 경로/환경 변수/실행 명령처럼 쉽게 오래되는 정보는 별도 운영 문서로 분리한다.
- 도메인 정책은 ERD 초안과 충돌하지 않게 유지한다.

## 11. 범위 밖 항목

이 문서는 다음을 확정하지 않는다.

- 상세 REST API 명세
- 프론트엔드 화면별 라우팅 구조
- 배포 스크립트와 인프라 프로비저닝 세부
- 개발용 실행 명령과 환경 변수 템플릿
- Graph 확장 기능의 구체 구현 시점

## 12. 결론

AX-WMS의 목표 아키텍처는 `web`, `api`, `ai`, `nginx`의 명확한 역할 분리를 중심으로 한다.

- `web`은 사용자 경험을 담당한다.
- `api`는 비즈니스 규칙과 운영 데이터의 기준 시스템이다.
- `ai`는 AI 파이프라인과 검색 보조 계층을 담당한다.
- `nginx`는 외부 진입을 통제한다.

이 문서는 이후 AX-WMS 아키텍처 설명의 작업 기준 문서로 사용하며, 기존 Word 문서는 참고 입력으로만 취급한다.
