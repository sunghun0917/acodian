# LightRAG endpoint versioning 병행 도입 구현 계획

관련 문서:

- [[2026-05-12-065231-search-lightrag-전환-조사와-구성-선택지]]
- [[2026-05-12-073814-search-lightrag-전환-결정-기존-pgvector-유지와-병행-도입]]

## 목표

AX-WMS `ai`의 기존 업무일지 semantic search endpoint는 그대로 유지하고, LightRAG 기반 검색은 별도 endpoint와 별도 코드 폴더에서 버전 단위로 병행 도입한다.

핵심 결정은 다음과 같다.

1. 기존 `/ai/search/worklogs`는 v1 compatibility endpoint로 유지한다.
2. LightRAG 검색은 `/ai/light/worklogs-v2`, `/ai/light/worklogs-v3`처럼 endpoint 이름에 version suffix를 붙여 추가한다.
3. LightRAG 관련 코드는 기존 `app/router`, `app/service`, `app/client` 계층에 흩뿌리지 않고 `ai/app/light/vN` 아래에 version별로 격리한다.
4. `v2`, `v3` 등 version 폴더는 서로 import/참조하지 않는다.
5. version별 폴더는 독립적으로 되돌릴 수 있어야 하며, 한 version의 실험/수정이 다른 version을 오염시키지 않아야 한다.
6. 이번 V3 계획은 endpoint skeleton과 폴더 격리 전략을 먼저 고정한다.
7. 실제 LightRAG client, ingestion, infra, API 서버 연동은 후속 문서/작업에서 결정한다.

## 현재 기준점

현재 업무일지 semantic search의 외부 endpoint는 다음과 같다.

```text
POST /ai/search/worklogs
```

현재 코드 흐름은 다음과 같다.

```text
api
  -> /ai/search/worklogs
  -> ai/app/router/search.py
  -> ai/app/service/search_service.py
  -> GeminiClient.embed
  -> ai/app/store/embedding_store.py
  -> WorklogEmbedding.embedding Vector(768)
  -> SemanticWorklogSearchResponse
```

주요 파일:

- `ai/app/router/search.py`
- `ai/app/service/search_service.py`
- `ai/app/store/embedding_store.py`
- `ai/app/store/models.py`
- `ai/app/model/search.py`
- `ai/app/config/settings.py`
- `ai/tests/test_search_router.py`
- `ai/tests/test_semantic_search_fixtures.py`
- `ai/tests/fixtures/semantic_search_queries.yaml`
- `ai/tests/fixtures/semantic_search_query_set.md`

이 endpoint는 LightRAG 실험과 별개로 v1 compatibility endpoint 역할을 계속 수행한다. 따라서 V3 작업에서 기존 `/ai/search/worklogs` 내부 구현을 리팩토링하거나 contract를 바꾸지 않는다.

## 새 구조 결정

### 1. URL versioning은 endpoint suffix 방식으로 한다

LightRAG endpoint는 `/ai/light` 하위에 두고, version은 endpoint 이름에 suffix로 드러낸다.

```text
기존 v1 compatibility endpoint:
  POST /ai/search/worklogs

LightRAG versioned endpoints:
  POST /ai/light/worklogs-v2
  POST /ai/light/worklogs-v3
```

이 방식은 다음을 의도한다.

- 클라이언트/API 서버가 어떤 검색 version을 호출하는지 URL에서 바로 볼 수 있다.
- 기존 `/ai/search/worklogs` 경로를 건드리지 않는다.
- LightRAG version을 추가할 때 기존 version endpoint를 덮어쓰지 않는다.

### 2. 코드 versioning은 `ai/app/light/vN` 폴더 방식으로 한다

URL은 endpoint suffix 방식이지만, 코드 배치는 version segment를 분리한다.

```text
ai/app/light/
  __init__.py
  v2/
    __init__.py
    router.py
    model.py
    service.py
    client.py      # 실제 구현 시점에 필요하면 v2 내부에 둔다
  v3/
    __init__.py
    router.py
    model.py
    service.py
    client.py      # v3가 필요로 하는 구현은 v3 내부에 둔다
```

원칙:

- `ai/app/light/v2`는 `ai/app/light/v3`를 import하지 않는다.
- `ai/app/light/v3`는 `ai/app/light/v2`를 import하지 않는다.
- 공통화가 필요해 보여도 초기에는 version 간 직접 공유보다 독립성을 우선한다.
- 불가피한 공통 util이 필요하면 version 독립성을 해치지 않는지 별도 결정 후 도입한다.
- version별 폴더는 Git revert 단위가 될 수 있도록 변경 범위를 작고 명확하게 유지한다.

### 3. 기존 layered 구조에 LightRAG 파일을 분산하지 않는다

이번 방향에서는 LightRAG 관련 파일을 아래처럼 기존 계층에 분산하는 방식을 기본 계획으로 삼지 않는다.

```text
ai/app/client/lightrag_client.py
ai/app/service/lightrag_worklog_search_engine.py
ai/app/service/worklog_search_engine_registry.py
```

LightRAG 관련 endpoint, DTO, service, client 초안은 우선 `ai/app/light/vN` 내부에 둔다. 이렇게 해야 version별 실험과 rollback 경계가 명확해진다.

## 명시적 non-goals

이번 V3 계획에서는 다음을 제외한다.

- `WORKLOG_SEARCH_ENGINE` / `WORKLOG_SEARCH_ENGINE_VERSION` 기반 runtime engine switching
- `WorklogSearchEngineRegistry` 도입
- 기존 `/ai/search/worklogs` 내부 구현 리팩토링
- 실제 LightRAG HTTP client 구현
- 실제 LightRAG ingestion 구현
- API 서버가 `/ai/light/worklogs-v2`를 호출하도록 바꾸는 작업
- infra compose, LightRAG storage backend, 운영 배포 설정 결정
- runtime automatic fallback
- 결과 부족 시 자동 pgvector 복구
- pgvector/LightRAG 자동 hybrid merge
- 요청별 동적 engine 선택

## 구현 원칙

### 1. 기존 endpoint는 compatibility boundary로 둔다

`/ai/search/worklogs`는 현재 stable/v1 endpoint로 취급한다. V3에서 이 endpoint의 router, request DTO, response DTO, service 흐름을 바꾸지 않는다.

### 2. LightRAG endpoint는 새 boundary에서 시작한다

LightRAG v2의 첫 진입점은 다음 형태를 목표로 한다.

```text
POST /ai/light/worklogs-v2
  -> ai/app/light/v2/router.py
  -> ai/app/light/v2/service.py
```

후속 v3는 v2를 수정하거나 상속하지 않고 별도 폴더에서 시작한다.

```text
POST /ai/light/worklogs-v3
  -> ai/app/light/v3/router.py
  -> ai/app/light/v3/service.py
```

### 3. version 간 공유보다 되돌리기 쉬운 격리를 우선한다

LightRAG 도입 초기는 검색 품질, 응답 contract, ranking, score, source mapping 정책이 바뀔 가능성이 크다. 따라서 초기에 공통 abstraction을 먼저 만들기보다 version별 독립성을 우선한다.

공통화 판단은 다음 조건을 만족할 때만 후속 작업으로 검토한다.

- 최소 두 version에서 동일한 요구가 반복된다.
- 공통화가 version rollback을 어렵게 만들지 않는다.
- 공통 module 변경이 여러 version endpoint의 동작을 동시에 바꾸지 않는다.

### 4. 권한과 원본 데이터 기준은 후속 구현에서도 PostgreSQL/API를 따른다

이번 V3는 실제 LightRAG 검색 구현을 다루지 않지만, 후속 구현에서 LightRAG를 권한 source of truth로 삼지 않는다는 원칙은 유지한다.

후속 구현 시 최종 응답은 다음 원칙을 따라야 한다.

```text
LightRAG candidate result
  -> worklog_id/source_id 추출
  -> PostgreSQL/API 기준 접근 가능 여부 확인
  -> 허용된 업무일지만 최종 응답
```

이 항목은 V3의 구현 범위가 아니라, 후속 LightRAG 검색 구현 문서에서 구체화한다.
