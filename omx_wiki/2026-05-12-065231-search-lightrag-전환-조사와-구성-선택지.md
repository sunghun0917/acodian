# LightRAG 전환 조사와 구성 선택지

# LightRAG 전환 조사 및 구성 선택지

## 배경

AX-WMS `ai` 영역은 현재 pgvector 기반 semantic search를 사용한다.

현재 검색 흐름은 대략 다음과 같다.

```text
/api worklog search
  -> ai `/ai/search/worklogs`
  -> `SearchService.search_worklogs`
  -> `GeminiClient.embed`
  -> `EmbeddingStore.search_worklogs`
  -> `WorklogEmbedding.embedding Vector(768)` cosine ranking
```

주요 현재 구현 지점:

- `ai/app/router/search.py`
- `ai/app/service/search_service.py`
- `ai/app/service/embedding_service.py`
- `ai/app/store/embedding_store.py`
- `ai/app/store/models.py`
- `ai/app/config/settings.py`
- `ai/requirements.txt`
- `ai/tests/*search*`
- `docs/ai/worklog-semantic-search-strategy.md`
- `docs/ai/worklog-embedding-strategy.md`

## LightRAG란

LightRAG는 단순 vector similarity RAG가 아니라, 문서에서 `entity`와 `relationship`를 추출해 knowledge graph를 만들고, 이를 vector index와 함께 사용하는 graph-enhanced RAG 방식이다.

기존 pgvector 방식이 다음에 가깝다면:

```text
query -> embedding -> vector top-k -> result
```

LightRAG는 다음에 가깝다.

```text
source documents
  -> chunking
  -> LLM 기반 entity / relationship extraction
  -> entity / relation merge
  -> knowledge graph 구성
  -> chunk / entity / relation vector 저장
  -> query 시 graph + vector retrieval
```

따라서 LightRAG 전환은 기존 `tb_worklog_embedding` 또는 `WorklogEmbedding.embedding`을 그대로 재사용하는 단순 교체가 아니라, 원문 워크로그를 기준으로 LightRAG storage에 재색인하는 작업으로 보는 것이 안전하다.

## LightRAG storage layer

LightRAG는 storage를 네 계층으로 분리한다.

| Layer | 역할 |
|---|---|
| `KV_STORAGE` | full docs, chunks, cache, document info |
| `VECTOR_STORAGE` | chunk/entity/relation embedding vector |
| `GRAPH_STORAGE` | entity-relation graph |
| `DOC_STATUS_STORAGE` | document indexing 상태 |

대표 backend:

- KV: `JsonKVStorage`, `PGKVStorage`, `RedisKVStorage`, `MongoKVStorage`, `OpenSearchKVStorage`
- Vector: `NanoVectorDBStorage`, `PGVectorStorage`, `MilvusVectorDBStorage`, `ChromaVectorDBStorage`, `FaissVectorDBStorage`, `MongoVectorDBStorage`, `QdrantVectorDBStorage`, `OpenSearchVectorDBStorage`
- Graph: `NetworkXStorage`, `Neo4JStorage`, `PGGraphStorage`, `AGEStorage`, `MemgraphStorage`, `OpenSearchGraphStorage`
- Doc status: `JsonDocStatusStorage`, `PGDocStatusStorage`, `MongoDocStatusStorage`, `OpenSearchDocStatusStorage`

중요 제약:

- storage implementation은 문서 추가 후 변경이 어렵다.
- storage 간 데이터 migration은 아직 일반적으로 지원된다고 보기 어렵다.
- embedding model과 dimension은 indexing/query에서 일관되어야 한다.
- PostgreSQL/pgvector 계열은 vector dimension 변경 시 재색인이 필요하다.

## 가능한 구성 방식

### 1. LightRAG 기본 local storage만 사용

```text
AX-WMS ai
  -> LightRAG Core 또는 LightRAG Server
    -> local/default storage
       - KV: JSON/local
       - Vector: NanoVectorDB
       - Graph: NetworkX
       - Doc status: local
```

용도:

- PoC
- 로컬 실험
- 검색 품질 1차 검증
- 기존 pgvector와 LightRAG 결과 비교

장점:

- 외부 DB 구성 없이 빠르게 시작 가능
- LightRAG ingestion/query 흐름을 가장 빨리 확인 가능

단점:

- 운영 부적합 가능성이 큼
- 백업/복구/동시성/멀티 인스턴스/관측성 측면에서 약함

### 2. PostgreSQL/pgvector 기반 LightRAG all-in-one

```text
AX-WMS ai
  -> LightRAG Server
    -> PostgreSQL
       - KV: PGKVStorage
       - Vector: PGVectorStorage
       - Graph: PGGraphStorage
       - Doc status: PGDocStatusStorage
```

예시 환경변수:

```bash
LIGHTRAG_KV_STORAGE=PGKVStorage
LIGHTRAG_VECTOR_STORAGE=PGVectorStorage
LIGHTRAG_GRAPH_STORAGE=PGGraphStorage
LIGHTRAG_DOC_STATUS_STORAGE=PGDocStatusStorage
```

의미:

- 사용자가 말한 `pgvector + LightRAG` 구성이 여기에 해당한다.
- 다만 기존 AX-WMS의 `tb_worklog_embedding`을 그대로 LightRAG가 읽는다는 뜻은 아니다.
- LightRAG가 자체 스키마와 내부 storage 구조를 만들고, vector layer로 PostgreSQL pgvector를 사용하는 것으로 이해해야 한다.

장점:

- 기존 PostgreSQL 인프라를 최대한 활용 가능
- 신규 운영 컴포넌트가 적음
- AX-WMS의 1차 운영 후보로 현실적

단점:

- graph 성능/표현력은 Neo4j보다 제한적일 수 있음
- 기존 pgvector embedding table 재사용은 어렵고 re-ingestion/re-index 필요

### 3. PostgreSQL pgvector + Neo4j graph 조합

```text
AX-WMS ai
  -> LightRAG Server
    -> PostgreSQL
       - KV: PGKVStorage
       - Vector: PGVectorStorage
       - Doc status: PGDocStatusStorage
    -> Neo4j
       - Graph: Neo4JStorage
```

용도:

- vector와 문서 상태는 PostgreSQL에 두고 graph만 Neo4j로 분리
- LightRAG의 graph retrieval 장점을 더 적극적으로 활용

장점:

- graph 탐색, 시각화, 운영 도구 측면에서 유리
- Cypher 기반 분석 가능
- 팀/사용자/업무/태그/워크로그 관계를 지식 그래프로 확장하기 좋음

단점:

- Neo4j 운영 컴포넌트 추가
- compose/deploy/backup/monitoring/security 복잡도 증가

### 4. Qdrant 또는 Milvus + Neo4j 조합

```text
AX-WMS ai
  -> LightRAG Server
    -> Qdrant 또는 Milvus
       - Vector storage
    -> Neo4j
       - Graph storage
    -> PostgreSQL / Redis / MongoDB
       - KV, doc status
```

용도:

- 대량 문서/워크로그/파일/회의록/이슈까지 RAG 범위를 확장할 때
- vector 검색 성능과 graph 검색 성능을 모두 전문 DB에 맡기고 싶을 때

장점:

- 대규모 vector search에 유리
- graph storage도 전문화 가능
- 검색 플랫폼으로 장기 확장 가능

단점:

- 현재 AX-WMS 규모에서는 과할 수 있음
- 운영 복잡도와 장애 지점 증가

### 5. 기존 pgvector 검색 유지 + LightRAG 병행

```text
AX-WMS ai
  -> 기존 `EmbeddingStore.search_worklogs`
  -> LightRAG adapter
  -> 결과 비교 / fallback / shadow logging
```

운영 전략:

1. Shadow mode
   - 사용자에게는 기존 pgvector 결과 반환
   - 내부적으로 LightRAG 결과를 같이 호출해 로그/평가만 수행

2. Fallback mode
   - LightRAG 실패 시 기존 pgvector 검색으로 fallback

3. Hybrid merge mode
   - 기존 pgvector top-k와 LightRAG reference 결과를 합쳐 재정렬

4. Mode comparison
   - LightRAG `naive` vs 기존 pgvector
   - LightRAG `hybrid` vs 기존 pgvector
   - LightRAG `mix` + reranker vs 기존 pgvector

장점:

- 가장 안전한 migration 방식
- 기존 검색 품질/기능을 보존하면서 점진 검증 가능
- 실제 query fixture와 사용자 질의 로그로 품질 비교 가능

단점:

- 한동안 검색 엔진이 이중 운영됨
- 결과 비교/평가 로깅 설계가 필요

### 6. LightRAG Server를 별도 internal service로 운영

```text
api
  -> ai FastAPI
    -> LightRAG Server REST API
```

권장도: 높음.

장점:

- 기존 `/ai/search/worklogs` contract 유지 가능
- `ai`는 adapter 역할만 수행
- LightRAG upgrade와 AX-WMS ai release cycle 분리 가능
- LightRAG Server의 Swagger, WebUI, document status API 활용 가능
- rollback이 비교적 쉬움

단점:

- service-to-service HTTP 호출 추가
- `LIGHTRAG_API_KEY` 등 내부 인증 필요
- timeout/retry/circuit breaker 필요

### 7. LightRAG Core를 `ai` FastAPI 내부에 직접 embed

```text
ai FastAPI
  -> import LightRAG
  -> LightRAG Core 직접 호출
```

장점:

- 네트워크 hop 없음
- 코드 레벨 제어가 좋음
- 기존 Celery task와 강하게 결합하기 쉬움

단점:

- startup/shutdown lifecycle 직접 관리 필요
- storage initialize/finalize 책임 증가
- LightRAG 내부 API 변경 영향이 큼
- FastAPI async concurrency와 충돌 가능성 검토 필요

용도:

- 실험/PoC에는 가능
- 운영은 별도 LightRAG Server 방식이 더 안전해 보임

## Retrieval mode 관점

LightRAG query mode 후보:

| Mode | 용도 |
|---|---|
| `naive` | 기존 vector search baseline에 가장 가까움 |
| `local` | 특정 entity 중심 질의 |
| `global` | 넓은 주제/관계/패턴 질의 |
| `hybrid` | local + global 결합 |
| `mix` | graph + vector retrieval 결합, 최종 후보 가능성 높음 |
| `bypass` | RAG 없이 LLM 직접 호출 |

AX-WMS migration 평가에서는 다음 순서가 적절하다.

1. 기존 pgvector vs LightRAG `naive`
2. 기존 pgvector vs LightRAG `hybrid`
3. 기존 pgvector vs LightRAG `mix` + reranker
4. 실제 워크로그 검색 UX 기준으로 mode 결정

## AX-WMS 추천 진행 순서

1. PoC
   - LightRAG local storage 또는 PostgreSQL all-in-one
   - 기존 semantic search fixture로 품질 비교

2. Shadow migration
   - 기존 pgvector 검색 유지
   - LightRAG 결과를 병렬 호출해 로그/평가

3. 1차 운영
   - LightRAG Server를 internal service로 분리
   - PostgreSQL 기반 `PGKVStorage + PGVectorStorage + PGGraphStorage + PGDocStatusStorage`
   - 기존 `/ai/search/worklogs` contract는 유지하고 adapter로 변환

4. 확장 운영
   - graph 활용도가 커지면 Neo4j 추가
   - vector 규모가 커지면 Qdrant/Milvus 검토

## 주요 migration risk

- 기존 pgvector embedding table은 LightRAG KG retrieval에 그대로 쓰기 어렵다.
- 원문 워크로그 기준 re-ingestion/re-index가 필요하다.
- LLM 기반 entity/relation extraction 비용과 latency가 증가한다.
- storage backend는 초기에 잘 결정해야 한다.
- embedding model/dimension 변경은 전체 재색인을 유발할 수 있다.
- 기존 `/ai/search/worklogs` 응답 스키마를 유지하려면 LightRAG response adapter가 필요하다.
- 삭제/수정 semantics는 기존 worklog update/delete 흐름과 별도 검증이 필요하다.
