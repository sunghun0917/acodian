# Change Report

기능 개발·수정 또는 리팩토링의 코드와 사용자 대화를 연결해 한국어 기술 보고서를 작성한다. 논의한 내용, 구현된 내용, 검증된 결과를 같은 것으로 취급하지 않는다.

## 범위와 산출물

- 사용자가 지정한 기능·파일·커밋·비교 구간을 우선한다. 지정이 없으면 현재 대화의 작업과 관련 diff로 범위를 좁힌다. 대상이 여러 개이고 선택에 따라 보고서가 달라질 때만 한 가지 질문으로 확인한다.
- 사용자가 제공 자료만 분석하도록 제한하면 저장소·실행 환경을 추가 조회하지 않는다. 아래 수집 절차 대신 제공된 코드·diff·로그를 사용하고, 직접 확인하지 않은 근거임을 표시한다.
- 기본 산출물은 아래 10개 항목을 갖춘 Markdown 파일이다. 사용자가 경로를 지정하면 그곳에 저장하고, 지정하지 않으면 `docs/reports/YYYY-MM-DD-<topic>.md`에 저장한다. 사용자가 채팅만 요청하면 파일을 만들지 않는다.
- 기존 보고서를 읽고 사용자가 해당 파일의 갱신을 명시한 경우에만 덮어쓴다. 기본 경로가 이미 존재하고 갱신 요청이 없으면 `-2`, `-3` 등을 붙여 새 파일에 저장한다. 사용자가 지정한 경로에 이미 파일이 있지만 갱신 여부가 불명확하면 확인한다. 제출 시 실제 저장 경로를 제공한다.
- 근거 분석은 read-only로 수행하고 보고서 산출물만 생성하거나 명시적으로 갱신한다. 보고서 작성 요청만으로 서비스 코드·설정·데이터 수정, 커밋·푸시, 유료 호출이나 운영 시스템 검증을 수행하지 않는다.

## 근거 수집

### 코드와 환경

1. 적용되는 `AGENTS.md`를 읽고 대상 진입점, 호출자, service/domain, 저장소·외부 연동, 응답 소비자와 관련 테스트를 필요한 범위에서 추적한다. diff만으로 서비스 동작을 단정하지 않는다.
2. `git status`, 범위가 제한된 `git diff`와 관련 이력을 읽어 현재 구현과 변경점을 구분한다. 기존 사용자 변경을 보존한다. Git이 없으면 제공된 코드·패치·스냅샷으로 비교하고 한계를 밝힌다.
3. 변경 전 기준은 사용자 지정 commit/branch/snapshot이 우선이다. 지정이 없으면 변경이 담긴 diff의 기준 버전을 확인한다. 로컬 미커밋 변경의 HEAD 기준 비교와 커밋 간 비교를 혼동하지 않는다. 선택한 기준과 현재 worktree의 포함 여부를 보고서에 기록한다. 근거가 없으면 이전 구현을 재구성하거나 HEAD~1을 임의 기준으로 삼지 않는다.
4. 환경은 관련 manifest·lockfile·build 설정·실제로 확인한 실행 정보에서 수집한다. 선언된 버전과 실행 중인 버전을 구분하며, 무관한 전체 환경 목록은 생략한다. 비밀값은 읽거나 보고서에 복사하지 않는다.

### 사용자 대화

- 현재 접근 가능한 대화와 사용자가 제공한 로그에서 요구사항, 문제 제보, 제약, 대안, 선택 이유, 정정사항을 뽑는다. 다른 세션·삭제된 메시지·접근 불가 대화를 알고 있다고 주장하지 않는다. 전체 대화 저장소를 무차별 탐색하지 않는다.
- 사용자의 결정과 에이전트의 제안을 구분한다. 에이전트가 완료했다고 말한 것만으로 구현·검증 완료를 확정하지 않는다. 후속 정정이나 새 로그가 있으면 이전 주장과 무엇이 달라졌는지 반영한다.
- 대화 근거는 접근 가능한 메시지의 화자·짧은 발언·대화상 순서 또는 제공된 로그 위치로 식별한다. 존재하지 않는 메시지 ID·날짜·사용자 승인을 만들지 않는다.

### 근거 표기

- 주요 결론 바로 옆에 `path:line`, `commit:path`, 테스트 이름·명령·결과, 또는 대화 근거를 붙인다. 이전 버전 코드를 현재 파일의 줄 번호로 인용하지 않는다.
- 내용은 필요에 따라 **확인 사실 / 대화상 요구·의도 / 추론 / 제안 / 미확인**으로 구분한다. 코드와 대화가 다르면 어느 쪽을 숨기지 말고 의도와 현재 구현의 차이를 설명한다.
- 테스트·벤치마크의 과거 로그는 제공된 실행 결과로 표시한다. 새 실행 여부, 범위, 실패·미실행 이유를 분리한다. 읽기만 한 테스트는 통과한 테스트가 아니다. 안전한 로컬 검증은 필요할 때만 실행하고, 외부 연동·파괴적 fixture·데이터 변경이 필요한 검증은 권한과 격리 환경이 없으면 수행하지 않는다.

## 보고서 형식

제목 아래에 대상 기능, 분석 범위, 변경 전/후 기준, 사용한 대화 범위와 근거의 한계를 짧게 적는다. 다음 항목은 순서대로 유지한다. 해당 사항이나 근거가 없으면 그 이유를 명시하고 억지로 채우지 않는다.

### 1. 환경

관련 기술 스택·의존성·실행 조건·외부 연동과 확인한 버전 출처를 기술한다. 환경 설정 자체가 변경 대상이면 전후 차이도 포함한다.

### 2. 문제사항

사용자가 겪은 증상, 기존 동작, 영향 범위, 근본 원인을 구분한다. 확인되지 않은 원인은 가설로 적는다. 순수 리팩토링이면 기능 장애를 만들어내지 말고 실제 중복·복잡도·변경 위험을 제시한다.

### 3. 해결아이디어

대화에서 논의된 대안과 선택 기준을 정리한다. 분석 중 떠오른 대안은 사후 제안이라고 표시한다. 논의되지 않은 대안을 당시 검토한 것처럼 쓰지 않는다.

### 4. 해결방식

실제로 선택·구현한 방식, 변경 책임과 적용 범위, 선택 이유를 연결한다. 예정·구현 중·구현 완료 상태를 근거에 맞게 구분한다. 계획만 존재하면 구현됐다고 서술하지 않는다.

### 5. 핵심코드

동작 차이 또는 설계 결정을 설명하는 최소 코드만 언어 표시 코드 블록으로 인용한다. 각 블록에 파일·심볼·버전 근거와 의미를 붙인다. 전체 파일 나열은 피한다. 설명용 의사코드는 실제 코드와 명확히 구분한다. 기능 추가라 이전 코드가 없으면 '신규 기능으로 대응 구현 없음'이라고 적는다.

### 6. 전후 해당 서비스 로직

동일한 입력·사용자 시나리오로 **변경 전 → 변경 후** 흐름을 나란히 설명한다. 진입점 → 검증·인가 → 핵심 처리 → 저장·외부 호출 → 응답·실패 처리를 관련 범위에서 추적한다. 적용되는 경우 트랜잭션·동시성·부수효과를 포함한다.

- 동작 변경이면 무엇이 달라졌는지와 호환성 영향을 적는다.
- 동작 보존 리팩토링이면 유지해야 하는 계약과 내부 구조 차이를 구분하고, 동일 동작이라고 판단한 검증 근거 또는 미검증 범위를 적는다.
- 변경 전 코드가 없으면 '변경 전 로직 미확인'으로 남긴다. 아이디어를 과거 로직으로 둔갑시키지 않는다.

### 7. 평가 및 결과

요구사항별 충족·부분 충족·미충족·미검증을 코드와 테스트 근거로 평가한다. 확인한 정상·실패·경계 경로, 실행 명령·환경·결과와 남은 검증 공백을 기술한다. 측정값과 기대 효과를 구분하며, 측정하지 않은 성능 향상률·비용 절감·커버리지·품질 점수를 만들지 않는다. 실패가 있으면 숨기거나 전체 성공으로 요약하지 않는다.

### 8. 트레이드오프

선택으로 얻은 점과 감수한 비용·제약을 짝지어 적는다. 당시 합의한 선택과 코드에서 추론한 한계를 구분한다. 관련 없는 일반론이나 근거 없는 확장성 주장은 생략한다.

### 9. 추가 개선점

현재 남은 문제에 근거해 우선순위, 기대 효과, 필요한 검증을 짧게 제안한다. 필수 후속 조치와 선택적 개선을 구분한다. 이 항목은 구현 권한이 아니며, 이미 적용된 것으로 쓰지 않는다.

### 10. 근거와 한계

주요 코드·diff·테스트·대화 출처를 정리한다. 접근하지 못한 이전 버전·대화, 실행하지 않은 검증과 그로 인한 결론의 한계를 남긴다. 앞 항목에 인접 인용이 있어도 누락된 근거를 확인하는 용도로 사용한다.

## 제출 전 확인

사용자가 요청한 항목이 모두 포함됐는지 확인한다. '대화에서 논의 → 코드에 반영 → 테스트로 확인'의 각 단계에 실제 근거가 있는지 점검하고, 근거가 끊기는 단계는 미확인으로 낮춘다. 민감정보·무관한 사용자 대화는 제외한다. 보고서와 저장 경로 또는 미해결 확인 사항을 전달하면 종료한다.

## 호출 예시

`$change-report 알림 읽음 처리 리팩토링을 현재 diff와 이 대화 기준으로 분석해 docs/reports/notification-refactor.md에 보고서를 작성해줘.`
