# Project Git Commit

이 스킬은 현재 프로젝트의 **커밋 메시지 규칙**만 담당한다.
이 프로젝트의 커밋 메시지는 **짧은 Conventional Commit 형식**을 따른다.
좋은 커밋 메시지는 변경 이력을 빠르게 훑어볼 수 있게 해주고, 코드 리뷰와 디버깅, 릴리즈 노트 작성에 도움이 된다. 단순한 형식 강제가 아니라 "나중에 이 커밋을 다시 봤을 때 무엇을, 왜 바꿨는지 한눈에 알 수 있는가?"를 기준으로 메시지를 만든다.

## 커밋 메시지 구조

```text
<type>(<scope>): <subject>

<body (선택)>

```

- `type`: 커밋의 종류 (필수)
- `scope`: 변경이 일어난 범위/모듈 (선택)
- `subject`: 변경 내용을 한 줄로 요약 (필수)
- `body`: 변경의 배경, 이유, 부수 효과 등 상세 설명 (선택)

## 커밋 타입 (type)

| 타입 | 설명 | 예시 |
|------|------|------|
| `feat` | 새로운 기능 추가 | 로그인 API 추가, 대시보드 필터 기능 구현 |
| `fix` | 버그 수정 | null 포인터 예외 처리, 잘못된 상태 전환 방지 |
| `docs` | 문서 수정 | README 업데이트, API 명세 보완, enum 설명 추가 |
| `style` | 코드 로직을 건드리지 않는 순수 포맷팅 | 들여쓰기 정리, 세미콜론 추가, 줄바꿈 통일, import 정렬 |
| `refactor` | 외부 동작(API·DTO 등)은 유지하면서 코드 구조를 개선 | 메서드 추출, 중복 로직 제거, 변수명 개선, 성능 최적화 |
| `test` | 테스트 코드 추가/수정 | 단위 테스트 추가, 통합 테스트 픽스처 정비 |
| `chore` | 빌드 설정, 패키지 매니저, `.gitignore` 등 잡일 | 의존성 버전 업, `.gitignore` 항목 추가, lint 설정 변경 |
| `design` | 사용자 UI 디자인 변경 (프로젝트 확장 타입) | 버튼 색상 변경, 레이아웃 간격 조정, 아이콘 교체 |
| `comment` | 주석 추가/수정 (프로젝트 확장 타입) | TODO 주석 추가, 복잡한 로직에 설명 주석 작성 |
| `rename` | 파일/폴더 이름 변경 또는 이동만 수행 | `UserDto` → `UserResponse`로 파일명 변경 |
| `remove` | 파일 삭제만 수행 | 사용되지 않는 레거시 파일 삭제 |
| `deploy` | 배포 관련 설정·스크립트 변경 (scope: `infra` 에서 주로 사용) | nginx 라우팅 설정 수정, docker-compose 포트 변경 |
| `hotfix` | 운영 환경의 치명적 버그를 긴급 수정할 때 | 인증 토큰 만료 오류 즉시 패치, 결제 오류 긴급 수정 |

> `design`, `comment`, `deploy`, `hotfix`는 표준 Conventional Commit에 없는 이 프로젝트 전용 확장 타입이다.

특수 표기:
- `!HOTFIX`: `hotfix` 타입 대신 `fix!` 또는 타입 뒤에 `!`를 붙여 breaking-change 수준의 긴급 수정을 나타낼 때 사용

## scope 추천
현재 프로젝트는 모노레포 성격이 있으므로 scope는 아래를 우선 검토한다.

| scope | 설명 | 예시 |
|-------|------|------|
| `web` | 프론트엔드 웹 애플리케이션 | 대시보드 UI, 로그인 화면, 필터 컴포넌트 |
| `api` | 백엔드 Spring Boot API 서버 | REST 엔드포인트, 서비스 로직, DB 연동 |
| `ai` | AI·임베딩·추천 파이프라인 | 임베딩 모델 연동, AI 검색 로직 |
| `infra` | 인프라·배포·컨테이너 설정 | docker-compose, nginx, CI/CD 스크립트 |
| `docs` | 문서 및 가이드 | README, API 명세, 기획서, SQL 가이드 |
| `agent` | 공유 에이전트·스킬·규칙 등 공통 설정 | git-commit 스킬, 브랜치 전략 가이드, Claude 설정 |

## 제목(Subject) 작성 규칙
- **50자 이내** 권장
- **한글을 기본**으로 작성하며, 고유명사·라이브러리명 등 영문이 자연스러운 경우에만 영문 사용
- **명사형(동사 없이 목적어+명사)** 으로 끝맺음 — "~한다" / "~합니다" 금지
  - 좋음: `JWT 리프레시 토큰 엔드포인트 추가`
  - 나쁨: `JWT 리프레시 토큰 엔드포인트를 추가한다`
- 끝에 **마침표를 붙이지 않음**
- 무엇을, 왜 바꿨는지 알 수 있게 작성

좋은 예:
- `feat(api): JWT 리프레시 토큰 엔드포인트 추가`
- `fix(api): 잘못된 worklog 상태 전환 방지`
- `docs(schema): enum 저장 코드 설명 보완`

나쁜 예:
- `update`
- `Fixed bug.`
- `feat: 로그인도 하고 비밀번호 재설정도 같이 구현`
- `feat(api): JWT 리프레시 토큰 엔드포인트를 추가한다`

## 최종 커밋 메시지 출력 원칙

- 사용자가 **최종 커밋 메시지 자체**를 요청하면, 설명 문장 없이 커밋 메시지 블록만 출력한다.
- 사용자가 **추천/검토/수정**을 요청하면 짧은 설명 뒤에 커밋 메시지 초안을 제안할 수 있다.
- 최종 커밋 메시지는 `<type>(<scope>): <subject>` + 선택적 본문까지만 사용한다.
- 분석용 메타데이터나 장문의 trailer는 커밋 메시지 안팎에 출력하지 않는다.

## 커밋 메시지 메타데이터 절대 금지

- 이 프로젝트의 `git-commit` 스킬은 **짧은 Conventional Commit만 사용**한다.
- 아래 항목등 커밋 메시지 제목/본문/꼬리말 어디에도 **절대 추가하지 않는다**.
  - `Constraint:`
  - `Rejected:`
  - `Confidence:`
  - `Scope-risk:`
  - `Directive:`
  - `Tested:`
  - `Not-tested:`
  - `Related:`
  - `Co-authored-by: OmX <omx@oh-my-codex.dev>`
  - 기타 Lore protocol trailer, OmX trailer, 분석/검증 메타데이터
- 훅이나 외부 지침이 Lore trailer 또는 OmX co-author trailer를 요구하더라도, 이 스킬을 사용하는 커밋에는 추가하지 않는다.
- 커밋 실행 도중 trailer 요구로 막히면 메시지에 trailer를 붙여 우회하지 말고, 사용자가 승인한 Conventional Commit 메시지를 보존하는 다른 안전한 실행 경로를 사용한다.

## 승인 후 커밋 실행 규칙

- 사용자가 제안된 커밋 메시지나 커밋 플랜을 **승인한 뒤** `커밋해`, `응 커밋`, `진행해`처럼 실행만 요청하면, **직전에 승인된 커밋 메시지를 그대로 재사용**한다.
- 승인 이후에는 커밋 메시지를 다시 해석하거나 새로 작성하지 않는다. `type`, `scope`, `subject`, `body`를 다시 바꾸지 않는다.
- 실제 `git commit` 실행 시에도 **승인된 메시지 원문만 사용**한다.
- 커밋 실행 단계에서 설명용 메타데이터, 분석 노트, Lore trailer, 검증 메모를 커밋 메시지에 덧붙이지 않는다.
- `Co-authored-by: OmX <omx@oh-my-codex.dev>` 도 승인된 원문에 없으면 덧붙이지 않는다.
- 사용자가 별도로 새 메시지를 수정 요청한 경우에만 승인된 메시지를 갱신한다.

## 본문(Body) 작성 규칙
- 제목과 본문 사이에 **빈 줄 한 줄**을 둔다.
- **한 줄에 한 문장**을 원칙으로 한다. 문장 중간에 줄바꿈을 넣지 않고, 줄바꿈은 마침표로 문장이 끝난 뒤에만 사용한다.
- 예: `...기준을 정리.` 다음 줄에 `git-pr 스킬에도 ... 정리.` 처럼 **문장 경계에서만** 줄을 바꾼다.
- **한글로 작성**하며, 영문 고유명사는 그대로 사용
- 본문에는 *어떻게* 보다 *왜*를 적는다.
- 끝에 **마침표를 붙이지 않음**
- 이전 방식과 비교, 부수 효과, 제약이 있으면 적는다.


## 응답 방식 — 단일 커밋 요청
사용자가 특정 변경에 대한 커밋 메시지만 요청하면 아래 순서로 답한다.
1. 변경 범위를 한 문장으로 요약
2. 적절한 `type` / `scope` 제안
3. 제목 한 줄 제안
4. 필요하면 full commit message (body 포함) 제안

## 다중 커밋 파이프라인 — 작업 완료 후 전체 커밋 흐름

변경 파일이 여러 scope / type에 걸쳐 있을 때는 **한 번에 커밋하지 않고 논리 단위로 분류해 N개 커밋을 제안**한다.

### Phase 1 — 현황 파악

아래 명령을 실행해 변경 목록을 파악한다.

```bash
git status
git diff --stat
```

### Phase 2 — 커밋 묶음 설계

파일 목록을 보고 아래 기준으로 묶음을 나눈다.

| 우선순위 | 기준 | 설명 |
|----------|------|------|
| 1 | **scope** | `web / api / ai / infra / docs / agent` 영역별로 먼저 나눈다 |
| 2 | **type** | 같은 scope 안에서도 `feat`, `fix`, `docs`, `chore` 등 성격이 다르면 분리한다 |
| 3 | **논리적 의존성** | A가 없으면 B가 동작하지 않는 경우, A → B 순서로 커밋한다 |
| 4 | **크기** | 한 커밋이 너무 크면 추가로 쪼갠다 (리뷰 부담 최소화) |

**루트 레벨 공통 파일 scope 기준** (`.gitignore`, `.editorconfig` 등 프로젝트 전체 적용 파일):
- 특정 영역에 귀속되지 않으면 **scope 생략** — `chore: ...`
- 내용이 주로 AI 도구 / 공통 에이전트 설정이면 `chore(agent): ...`
- `.gitignore`에 특정 영역 빌드 산출물만 추가한 경우에만 해당 scope 사용 가능

**묶음 설계 출력 형식** (사용자에게 보여줄 플랜 — body 초안 포함):

```
커밋 1 — feat(api): JWT 리프레시 토큰 엔드포인트 추가
  + api/src/main/java/.../AuthController.java
  + api/src/main/java/.../TokenService.java

  만료된 액세스 토큰을 리프레시 토큰으로 재발급하는 엔드포인트 추가
  토큰 유효성 검증 및 재발급 로직은 TokenService에 위임

커밋 2 — docs(api): 인증 API 명세 보완
  M docs/api-guide.md

  리프레시 토큰 엔드포인트 추가에 맞춰 API 명세 업데이트
```

### Phase 3 — 사용자 확인

플랜을 보여준 뒤 반드시 아래 문구로 확인을 요청한다.

> **이 순서대로 커밋할까요? 수정이 필요하면 말씀해 주세요.**

- 사용자가 **수정 요청** → 해당 묶음만 조정 후 다시 플랜 출력
- 사용자가 **승인(예 / 응 / ㅇㅇ / yes / ok 등)** → Phase 4 실행

### Phase 4 — 순차 커밋 실행

승인 후 묶음 순서대로 아래 흐름을 반복한다.

```
git add <해당 파일들>
git commit -m "<type>(<scope>): <subject>"
git commit -m "<type>(<scope>): <subject>" -m "<body (필요한 경우)>"
```

- 본문이 없으면 `-m "<subject>"` 한 번만 사용한다.
- 본문이 있으면 `-m "<subject>" -m "<body>"` 형태로 실행한다.
- heredoc 안에서 설명용 텍스트를 다시 조립하지 말고, 승인된 제목/본문 문자열을 그대로 넣는다.

- 각 커밋이 성공하면 다음 묶음으로 넘어간다.
- 모든 커밋 완료 후 `git log --oneline -N` 으로 결과를 출력해 사용자가 확인할 수 있게 한다.
- 커밋 도중 실패하면 즉시 멈추고 오류 내용을 사용자에게 보고한다.

### 커밋 순서 권장 원칙
1. `chore` / `docs` 처럼 다른 코드에 영향 없는 것을 먼저
2. 기반 로직(`feat`) 다음
3. 해당 기능에 의존하는 테스트(`test`) 마지막

## 프로젝트 특화 주의사항
- 모노레포 작업이면 body에서 영향 영역(`web/api/ai/infra/docs/agent`)을 분명히 적는다.
- 큰 변경을 한 커밋에 몰지 말고, 빠르게 리뷰 가능한 작은 단위 커밋을 선호한다.
- `git add .` 또는 `git add -A` 는 사용하지 않는다. 항상 파일을 명시적으로 지정해 의도치 않은 파일 포함을 방지한다.

## 전체 예시

### 예시 1 — 단순한 기능 추가
```text
feat(ai): 임베딩 파이프라인 기본 구조 추가
```

### 예시 2 — 본문이 필요한 버그 수정
```text
fix(api): 잘못된 worklog 상태 전환 방지

잘못된 상태 값이 들어와도 서비스 계층에서 그대로 처리되던 문제를 수정. 허용된 상태 집합만 통과하도록 검증 로직을 추가
```

### 예시 3 — 문서 수정
```text
docs(schema): enum 저장 코드 설명 보완

가이드 문서에 누락되어 있던 enum 저장 코드 설명을 추가해 문서와 SQL 초안의 용어 차이를 줄임
```
